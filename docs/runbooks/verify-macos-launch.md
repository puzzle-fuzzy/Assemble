# 在 macOS 上真实启动并检查 Assemble

自动化测试覆盖不到窗口、托盘、系统钥匙串、真实浏览器和退出时的清理。这个仓库里已经有一条接一条的缺陷是测试全绿、实际运行之后才暴露的（见 [决策 0002](../decisions/0002-own-server-replaces-jarvis.md#从真实启动中学到的)）。涉及应用壳、服务端或生命周期的改动，除了 `bun run verify`，还要按本文实际跑一遍。

收发文件的整条路（事件、下载、核对、落盘、回执、重试；选文件、上传、撤回、对账；存进云盘、从云盘取回）有对着真实服务端跑的测试，在 `apps/desktop/src-tauri/src/transfers/tests.rs`。它们不算真实启动：窗口、通知、钥匙串只有真的跑起来才算数。

## 0. 先知道这几件事

- **模拟的浏览器不算浏览器。** 测试里的"浏览器"是 HTTP 客户端，请求头是人为构造的。凡是浏览器参与的流程（登录页、授权确认页），必须在真实的浏览器里走一遍。
- **屏幕锁定时做不了界面层面的验证。** 锁屏后没有前台应用，读不到窗口内容，截图也会失败。后台进程照常运行，所以进程层面、接口层面的检查仍然有效。读窗口之前先确认屏幕没锁：

  ```sh
  ioreg -n Root -d1 | grep -o '"CGSSessionScreenIsLocked"=[A-Za-z]*'
  ```

  答 `Yes` 就是锁着。锁着的时候"窗口里读不到网页内容"什么都说明不了：2026-11-24 对着一台刚启动三分钟、各方面都健康的应用复现过——主线程停在正常的事件循环里，系统把它登记成前台应用，网页内容进程也在，但窗口里一个元素都读不到，也截不到图。
- **区分"卡死"和"读不到"。** 窗口读不出来时，先用 `sample <进程号> 1 -file /tmp/sample.txt` 看主线程：停在正常的事件循环等待里是健康的；停在我们自己的代码里、或者在等一把锁，就是卡死。
- **已经跑过的迁移脚本不能再改。** sqlx 在库里记着每个脚本的校验和：同一个编号、内容不一样，服务端拒绝启动（"migration 1 was previously applied but has been modified"）。2026-11-24 凌晨迁移 1 提交后二十分钟被原地改过一次，那之前建的本机开发库从此就打不开了；2026-11-25 做日程的真实启动时才撞上，挪走重建。正式服务的库是用改完之后那一版建的，不受影响。结构要变就加新的脚本。
- **不要替桌面端往系统钥匙串里预置会话。** 桌面端没有登录就收不了文件，用 `security add-generic-password` 塞一条会话进去看着像个办法，实际会在屏幕上弹一次钥匙串确认框，等人来点。那是用户的屏幕，不是测试的。桌面端的登录只能走浏览器，由人来做。2026-11-24 这么干过一次，惊动了用户，已清理干净。

## 1. 主流程：一条命令

在仓库根目录、在你自己的终端里：

```sh
bun run acceptance
```

它把整套环境在本机起起来，引导你把主流程走一遍，能自动核对的都自动核对：

1. 编译服务端与替身设备（一台没有界面的设备，在面板和设备列表里叫"工作电脑"，看起来是 Windows）。
2. 起本地服务端：数据在 `data/local/server`，地址 `http://127.0.0.1:8787`。已经有一个在应答的就沿用。
3. 账户：没有叫 `dev` 的账户，就让你当场设一个密码建一个（至少 8 个字符，只在本机的登录页上用）。
4. 让"工作电脑"上线。它收到的文件会自动收下，存进 `data/local/acceptance/received-by-work-pc`。
5. 现场构建发布版桌面应用并启动。每次都重新构建，大约一两分钟。

之后要你亲手做的只有四件事，轮到的时候终端里会写明要做什么：

| 你做什么                                                     | 脚本核对什么                                                                                       |
| ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 在应用里点"使用浏览器登录"，在系统浏览器里登录，点"确认登录" | 桌面应用以这个账户上线                                                                             |
| （不用做）"工作电脑"发来两个文件                             | 应用回执"已收下"；`~/Downloads/Assemble` 里落盘的文件，摘要与发出的逐字节一致                      |
| 把任意一个文件拖进 Assemble 窗口，在面板里点"工作电脑"       | "工作电脑"收下了它，落盘后的摘要与声明的一致                                                       |
| 到点时看一眼系统通知；点它；在"日程"卡片里点那一条的"看过了" | 在线的"工作电脑"立刻收到名单更新；服务端在到点后十几秒内生成通知；点过之后这条提醒在服务端上已办完 |
| 点菜单栏图标 →"退出 Assemble"                                | 进程退出，服务端上这台电脑随即显示离线                                                             |

跑完会列出每一项的结果，外加几样脚本看不见、要你顺手看一眼的：收文件与到点提醒的通知、"传输"卡片里的说法、拖文件夹的提示、云盘、托盘里的"新建提醒…"、长时间挂在后台之后窗口是否正常。哪一项不对，把现象留下来，连同 `data/local/acceptance/` 里的三份日志（`desktop.log`、`work-pc.log`、`server.log`）。

- 换一个账户：`bun run acceptance --account <用户名>`。每一处等待最多等多久：`--timeout <秒>`（默认 600）。
- 应用已经在运行时它不启动：先从菜单栏退出，再运行。
- 中途想停：`Ctrl+C`。收摊：`bun run acceptance stop`，停掉替身设备与它起的服务端；桌面应用要自己从菜单栏退出。
- 它只显示文字、启动应用，不替你点任何东西，也不碰系统钥匙串。登录时如果系统弹出钥匙串的确认框，点"始终允许"，并把这件事记下来：没签名的应用每次重新构建之后都可能再问一次。这只是推断，还没有在真实运行里见到过；真是这样的话，它是打包与签名那一步要解决的。

## 2. 只起其中一样的时候

排查某一个问题、或者要反复试某一步时，不必每次都走整条命令。

### 服务端与账户

```sh
bun run server:dev          # 数据在 data/local/server，地址 http://127.0.0.1:8787
bun run server:account dev  # 建账户：密码从终端读两遍（不回显）；标准输入不是终端时只读一行
bun run server:accounts     # 列出全部账户的用户名
bun run server:check        # 只读取配置并连接数据库，报告后退出
```

账户只能从命令行建，不开放注册。密码不作为参数传入：参数会留在 shell 的历史里。

### 替身设备

```sh
cargo build -p assemble-server --bin assemble-server --example fake_device
F=./target/debug/examples/fake_device
```

每台替身用一个令牌文件（`--token`，仅本人可读）；令牌只对登记时的那个账户有效，换了账户会重新登记一台。它直接写服务端的数据库，所以只能用在本地开发的服务上。

| 命令                                                                                                      | 做什么                                                                                                  |
| --------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `$F --token a.json register --data-dir data/local/server --account dev --name 替身A [--platform windows]` | 登记这台替身设备                                                                                        |
| `$F --token a.json online --origin http://127.0.0.1:8787 [--receive-dir 某个目录]`                        | 上线并打印收到的事件，`Ctrl+C` 下线。带了接收目录就像桌面端一样把文件收下：核对长度与摘要，先落盘再回执 |
| `$F --token a.json devices --origin …`                                                                    | 列出账户里的设备与在线状态                                                                              |
| `$F --token a.json send --origin … --to 替身B --file 合同.pdf [--wait]`                                   | 发一个文件。`--to` 认设备名或标识；`--wait` 等到结局                                                    |
| `$F --token a.json sends --origin …`                                                                      | 列出它发出去的与收到的记录和各自的状态                                                                  |
| `$F --token a.json wait --origin … --until peer-online`（或 `peer-offline`）                              | 等到别的设备上线（或都下线）才退出                                                                      |
| `$F --token a.json remind --origin … --title 取快递 --in 60`                                              | 新建一条提醒，六十秒后到点。每次一个新的幂等键                                                          |
| `$F --token a.json planner --origin …`                                                                    | 列出日程名单：日程、提醒、没读的通知                                                                    |
| `$F --token a.json wait --origin … --until notification`（或 `reminder-closed --reminder <标识>`）        | 等到出现没读的通知（可以用 `--reminder` 限定是哪条提醒的）；或者等到那一条提醒办完、不办了              |
| `$F --token a.json forget --origin …`                                                                     | 从账户里删除这台替身，令牌文件一并清掉                                                                  |

`wait` 与 `send --wait` 是给脚本用的：等到了以 0 退出，到时没等到（或者对方没收下）以 3 退出，别的失败是 1；`--timeout` 限定秒数。给脚本读的结果各占一行，行首是固定的英文标记（`online`、`peer-online`、`peer-offline`、`received`、`send-settled`、`reminder`、`notification`、`reminder-closed`，`planner` 另有 `schedule`），后面用制表符分开；其余的输出是给人看的，措辞随时会改。

### 桌面应用

```sh
cd apps/desktop
ASSEMBLE_SERVER_ORIGIN=http://127.0.0.1:8787 bunx tauri build --no-bundle
cd ../..
./target/release/assemble-desktop 2>&1 | tee /tmp/assemble-run.log
```

连接哪个服务在构建时定下：不设 `ASSEMBLE_SERVER_ORIGIN` 的发布构建拒绝启动。调试构建加载的是开发服务器上的页面，需要先 `bun run dev:frontend`。

## 3. 脚本不覆盖、要手工试的

主流程之外的不顺利情况，以及只能靠人看的东西。桌面端要先登录（走第 1 节，或者按第 2 节自己起服务端与替身设备）。下面的"替身"带着接收目录在线，所以它那边收下了没有，能从它的输出里看到。

### 窗口与登录

- 窗口出现，左上角写着"本地开发服务"（按地址判断，不是按调试还是发布），账户卡片里有"使用浏览器登录"。
- 点"使用浏览器登录"：系统默认浏览器打开授权页；还没登录时会先跳到登录页。在浏览器里登录并点"确认登录"，回到应用时应当已登录，账户卡片下面写着"这台设备：<本机名>"。
- "设备"卡片列出账户里的全部设备，替身设备显示在线，本机带"本机"标记。停掉替身（`Ctrl+C`），列表里它变成离线。
- 关掉窗口：应用留在托盘（菜单栏右侧）。再运行一次可执行文件，第二个实例会把窗口叫回来然后自己退出，进程始终只有一个。

读窗口内容可以用系统自带的无障碍接口（Xcode 的"辅助功能检查器"，或任何读屏工具）：页面里的文字和按钮都应当读得到，主线程卡死时则什么都读不到。

**只想看某张卡片长什么样**（不必登录，也不启动应用）：界面测试的替身可以直接当数据源。在 `apps/desktop` 下临时放一个入口，用 Vite 起开发服务器，在浏览器里截图。

```html
<!-- apps/desktop/__preview.html：与 index.html 一样，只是脚本指向下面那个文件 -->
<script type="module" src="/src/__preview.tsx"></script>
```

```tsx
// apps/desktop/src/__preview.tsx
import { createRoot } from "react-dom/client";
import { PlannerCard } from "@/PlannerCard"; // 换成要看的卡片
import "@/styles/app.css";
import { FakeBridge, snapshot } from "@/test-support/fakes";
const which = snapshot({ phase: "signedIn" });
createRoot(document.getElementById("root")!).render(
  <div style={{ width: 720 }}>
    <main className="mx-auto flex min-h-screen w-full max-w-xl flex-col gap-4 bg-background px-6 py-6 text-foreground">
      <PlannerCard
        source={new FakeBridge(which)}
        snapshot={which}
        onError={console.error}
      />
    </main>
  </div>,
);
```

`bunx vite --port 1421 --strictPort`，打开 `http://localhost:1421/__preview.html`（它只监听 IPv6 的回环地址，`127.0.0.1` 连不上）。宽度取主窗口的最小值 720：最窄的时候排得下，更宽就没问题。看完把两个临时文件删掉。这是 Chromium 内核的渲染；应用里的 WebView 选择日期的控件长什么样，还是要到应用里看。

### 收文件

- 弹出一条系统通知，"收到文件"。点它，访达打开并选中那个文件（只选中，不打开）。
- 应用里"传输"卡片多了一条，写着"已保存"，右边有"在文件夹中显示"。
- 同一个文件再发一次：得到 `某个文件 (2).pdf`，原来那份不动。
- "本机"卡片里点"更改…"能挑一个接收文件夹，界面只显示那个文件夹的名字；"恢复默认"回到"下载/Assemble"。
- 把接收文件夹设成一个只读的位置再发一次：这一条显示"接收失败：文件没能写进接收文件夹"，替身的 `sends` 里是"对方接收失败（写入失败）"。
- 把设置的文件夹删掉再发：文件退回"下载/Assemble"，通知和应用里都说明了原因。

### 发文件

- 菜单栏图标 →"发送文件…"，或者主窗口"传输"卡片右上角的"发送文件…"。系统弹出文件选择框，挑一两个文件。
- 弹出"发送到…"面板：上面是挑好的文件（只有名字与大小），下面是账户里别的设备。离线的设备是灰的，点不了。
- 点一台在线的替身。每个文件一行进度；全部传完后面板显示"已发送"，过一两秒自己关掉。
- 点"取消"：这一条变成"已撤回"，替身那边出现 `send_updated`（`cancelled`）。
- 替身下线后再发：面板里它是灰的。如果它恰好在点下去的那一刻下线，这一条显示"发送失败：那台设备刚刚下线了"，有"重发"。
- 挑好之后把文件移走再点设备（面板开着时在访达里把文件拖走）：显示"发送失败：文件读不出来，可能已被移走或改动"；把文件放回去，点"重发"能发出去。
- 挑一个超过 100 MB 的文件：提示"超过 100 MB，发不出去"，面板不打开。

### 云盘

- 主窗口有一张"云盘"卡片：写着已用多少空间（例如"已用 1.5 MB，共 2.0 GB"）、一根用量条，下面是云盘里的文件（名字、大小、日期），新的在前。右上有"上传…"。
- 点"上传…"，在系统选择框里挑一个文件：这一条出现在"传输"卡片里，"正在上传到云盘…"，然后"已存到云盘"。云盘卡片里多出它，已用空间跟着涨。
- 把"接收位置"记下来，点某个文件的"取回"：文件出现在接收位置里，内容与原文件一致；"传输"卡片里这一条写着"已取回"，有"在文件夹中显示"；弹出一条通知。
- 点"删除"要先点"确认删除"才删。删掉之后另一台已登录的设备上，它也不会再出现（连上服务或重新打开应用时名单会换新）。
- 打开"发送到…"面板：最上面是"云盘"，下面才是设备。点"云盘"，面板显示"正在上传到云盘…"，存好后自己收起。
- 在发送面板里点"云盘"存一个超过剩余空间的文件（或者把服务端的 `ASSEMBLE_DRIVE_QUOTA_BYTES` 调小再试）：这一条写着"没能存进云盘：云盘空间不够"，有"重发"。

### 日程与提醒

- 主窗口有一张"日程"卡片。上面是"到点的提醒"：还没读的通知，写着多久之前来的；"知道了"把它标成已读，提醒的还能顺手点"看过了"。下面是"接下来的安排"：七天之内的日程与提醒按时间排在一份里，重复的日程写出后面还有哪几场。助手或别的设备记下的，标题旁边写着是哪一台。
- 点"新建提醒…"：标题、到点时间、备注。时间是这台电脑的本地时间。标题空着点"保存"，提示"先写一个标题。"。
- 点"新建日程…"：多出结束时间、重复、提前多久提醒、地点。
- 一条日程上：不重复的有"完成"；都有"改…"和"取消"，取消要先点"确认取消"。一条提醒上："办完了"（到点之后叫"看过了"）；没到点的能"改…"；"不办了"要先确认。
- 菜单栏图标 →"新建提醒…"：主窗口打开，直接摆出新建提醒的表单。
- 到点：弹出系统通知，标题底下带着几句话（日程先说几点开始，再是备注与地点）。点它，主窗口打开并滚到那一条。
- "本机"卡片里关掉"到点提醒"：到点不再弹，只留在"日程"卡片里；过一阵再打开，积压的不会一起弹出来。
- 到点之后一直没人点"看过了"的提醒，在"接下来的安排"里留七天，之后不再列出。
- 同一条在别的设备（或助手）那边改过，再在这边的表单里保存：提示"这一条在别的设备上被改过。已经换成最新的，请再看一眼。"，表单收起。

### 发起发送的入口

- **拖放**（macOS 与 Windows）：把一两个文件从访达拖进 Assemble 主窗口，松手后弹出"发送到…"面板，里面就是刚拖进来的文件。拖一个文件夹进来：主窗口提示"只能发送文件，不能发送文件夹。"。一摞东西里既有文件又有文件夹时，文件夹被略过，文件照发。
- **带着文件启动**：在终端里运行 `./target/release/assemble-desktop --send 某个文件.pdf`。应用没在运行时，它会启动并打开面板；已经在运行时，新启动的那个自己退出，面板由原来那个打开（单实例）。
- **右键菜单**（只有 Windows 上的打包运行有）：在任意文件上点右键 →"显示更多选项"→"用 Assemble 发送"，面板打开。主窗口"本机"卡片里有这一项的开关；Windows 11 上它在"显示更多选项"里，Shift+F10 也能到。

没登录的时候做这三个动作，不会打开面板，而是把主窗口叫到前面并提示"请先登录，再发送文件。"。

## 4. 服务端的生死

- 启动之后至少过十五秒，`curl http://127.0.0.1:8787/healthz` 仍然应答。曾经出现过服务端启动十秒后自己退出的情况。
- 对它发 `kill -TERM`，应当在一秒内结束，即使此刻有事件流连着。曾经出现过服务端收到信号后无限期挂着的情况。

## 5. 收尾

`bun run acceptance` 起的东西用 `bun run acceptance stop` 收摊。自己按第 2 节起的：

```sh
pkill -TERM -f 'fake_device --token data/local'
rm -f data/local/*.json      # 替身设备的令牌，仅本人可读
```

真实登录过的应用会在系统钥匙串里留一条 `assemble.device-session:http://127.0.0.1:8787`。在应用里"退出登录"会删掉它。

## 安装包从哪来

真机验收用的安装包由持续集成产出（`.github/workflows/release.yml`）：推送 `v` 开头的标签，或者在 GitHub 上手动运行"安装包"这个流程。产物在那一次运行的页面底下，分 `assemble-macos-arm64` 与 `assemble-windows-x64` 两份；打标签的话还会挂在发布页上。仓库变量 `ASSEMBLE_SERVER_ORIGIN` 是正式地址 `https://as.yxswy.com`，所以这样打出来的包连的是正式服务。

```sh
gh run list --workflow release.yml
gh run download <运行编号> -n assemble-windows-x64
```

- 桌面端连哪个服务在构建时定下：流程读仓库变量 `ASSEMBLE_SERVER_ORIGIN`；手动触发时可以填一个别的地址，临时打一个指向测试服务的包。仓库里还没设这个变量时，打标签的构建直接失败并说明原因，不去猜。
- 产出没有签名、没有公证。macOS 上第一次打开要在"系统设置 → 隐私与安全性"里点"仍要打开"；用浏览器下载的 Windows 安装包会有 SmartScreen 的提醒（`gh run download` 下来的没有这个标记）。
- 手边就有一台开发机时也可以本地打：`bun run build`，产物在 `target/release/bundle/`。在 macOS 上打出的是 macOS 的安装包，在 Windows 上打出的是 Windows 的。

2026-11-24 实际跑过的情况：Windows 那一份构建成功，压缩包里是 `nsis/Assemble_0.1.0_x64-setup.exe` 与 `msi/Assemble_0.1.0_x64_en-US.msi`；macOS 那一份被整个取消，原因是 GitHub 的 arm64 机器当天容量紧张，任务一直没被接走——遇到这种情况重新触发就行，不是我们的问题。macOS 的安装包还没有成功打出过。

## Windows 真机验收清单

Windows 上没法在这台 Mac 上自动验证。下面每一条都对应一段只做过类型检查的代码，请在 Windows 上逐条走：

1. **安装并启动。** 装上持续集成产出的 Windows 安装包（见"安装包从哪来"；装了开发环境的 Windows 上也可以 `bun run build` 自己打）。装好后启动：窗口出现，托盘里有图标，"本机"卡片里有"右键菜单"一项，默认开着。
2. **右键菜单。** 在资源管理器里对任意一个文件点右键 →"显示更多选项"：有"用 Assemble 发送"。点它：发送面板打开，里面是这个文件。
3. **单实例。** 应用已经在运行时再点一次右键菜单：面板被叫到前面，任务管理器里进程仍然只有一个。
4. **开关。** 在"本机"卡片里关掉"右键菜单"：右键菜单里那一项消失。重新打开：它回来。想直接看注册表：`reg query "HKCU\Software\Classes\*\shell\AssembleSend" /s`。
5. **拖放。** 把一个文件从资源管理器拖进 Assemble 窗口：面板打开。拖一个文件夹：提示"只能发送文件，不能发送文件夹。"。
6. **登录、收发、云盘。** 第 3 节各走一遍。收到的文件在 `下载\Assemble`；通知会弹出，点它在资源管理器里选中那个文件。
7. **开机启动。** "本机"卡片里打开开关，重启电脑确认应用随系统启动、不弹窗口只在托盘里。
8. **日程与提醒。** 登录后"日程"卡片里点"新建提醒…"，填一个两分钟后的时间并保存；到点时弹出系统通知，点它，主窗口打开并定位到那一条。日期与时间的选择框、下拉框在 Windows 的 WebView2 里是什么样子，只有真机看得到。
9. **退出。** 托盘图标 →"退出 Assemble"：进程消失；另一台设备的列表里这台电脑变成离线。

哪一条不对，把现象和 `reg query` 的输出发给我。应用本身不写日志文件，所以现象描述得越具体越好（点了什么、看到了什么、隔了多久）。

## 2026-11-25 做过的

都是日程规划第一批的。桌面端没有登录，所以界面层面一项都没有做。

- 服务端对着真实运行核对：全新的库上迁移 1、2 在启动时自动应用；建账户、登记替身设备、上线。
- 在线的替身设备建一条三十秒后到点的提醒：新建这一下它立刻收到 `planner_changed`；到点后 7 秒服务端生成通知（它每十秒查一次），又推来一份带着这条通知的名单；提醒的状态变成 `fired`、版本号加一。
- 替身设备离线时另一条提醒到点：服务端照常生成通知（到点后 8 秒）。替身设备重新上线时事件流不补送旧事件，它拉一次名单就拿到两条没读的通知。桌面端连上服务时也是先拉一次名单，再按本机的账本决定补弹哪几条。
- 桌面端（发布构建，连本地服务端）：进程稳定，主线程停在正常的事件循环里，已经连上服务端。当时屏幕是锁着的，所以只做到进程层面：窗口里有什么，没有读。
- `bun run acceptance` 加了"到点提醒"一段，替身设备多了 `remind`、`planner` 和两种等待。脚本本身还没有由真人从头跑过。
- 撞上并处理：本机 `data/local/server` 是迁移 1 的第一版建的，之后脚本被改过，库就再也打不开了（见第 0 节）。那个库里没有账户，挪走后重建。
- 界面在浏览器里按主窗口最窄的宽度看过（做法见第 3 节"窗口与登录"）：日程卡片的名单、新建、修改三种样子排得整齐，预填正确。看出并修掉一处：重复的截止日在另一年时没带年份。

## 2026-11-24 做过的

- 服务端与两台替身设备：两台都在线时互相可见，一台到时下线后另一台立刻看到它离线。
- 替身设备自动收文件，对着真实运行的服务端：两台替身互发，落盘后的摘要与原文件一致；同名再发得到 `(2)`，原文件不动；断线期间错过的文件，在重新连上时补收。
- `bun run acceptance` 不涉及登录的那一段：编译、起服务端、认账户、替身设备上线、构建并启动应用，五步都真实跑过。三样东西在脚本退出之后继续运行；等不到登录时如实报告并退出（等了 25 秒）；应用已经在运行时它拒绝启动；`stop` 只停它自己起的替身设备与服务端，不碰桌面应用。
- 桌面端（发布构建）：窗口与界面内容正确；点"使用浏览器登录"后进入等待状态并打开系统浏览器；关窗收起后由第二个实例唤回。
- 真实浏览器（Chromium 内核）里的登录页：登录成功。
- 服务端带着打开的事件流收到 `SIGTERM` 后 0.02 秒退出。
- 服务端启动十四秒之后仍在应答 `/healthz`（之前它启动十秒后会自己退出，已修）。
- 替身设备的 `register`、`devices`、`send`、`sends`、`wait` 五个命令（服务端与替身是各自的进程）：发给在线设备后对方的 `online` 输出里出现 `send_offered`；给自己发得到 `INVALID_REQUEST`，而不是"连不上服务"（之前是后者，已修）；等不到别的设备上线时以 3 退出。
- 带着文件启动（`--send`），没登录时：主窗口出现提示"请先登录，再发送文件。"，没有打开面板。两种情形都真实跑过——应用没在运行时由它自己启动；已经在运行时，第二个实例 0.09 秒就退出，全程只有一个进程，请求由原来那个处理。
- 一条曾经没查明白的观察有了解释：一个实例挂着没人动，十来分钟后读它的窗口，读不到网页内容（只剩窗口自己的按钮和菜单栏），而主线程停在正常的事件循环里。当天晚些时候在屏幕锁定时对着一台刚启动三分钟的健康实例复现了一模一样的现象（见第 0 节），所以当时多半是屏幕自动锁了，不是应用的问题。
- 抓到并修掉了一批测试全绿时藏着的缺陷，连同两条时过时不过的测试，逐条记在决策 0002 的"从真实启动中学到的"。
- 持续集成（仓库公开之后的当天）：`bun run verify` 在 macOS 与 Windows 上各跑通过一遍。Windows 那一栏是第一次有 Windows 环境跑这个项目的代码，它抓到的东西逐条记在决策 0002 的第 10 到 15 条。
