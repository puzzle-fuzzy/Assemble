# 在 macOS 上真实启动并检查 Assemble

自动化测试覆盖不到窗口、托盘、系统钥匙串、真实浏览器和退出时的清理。这个仓库里已经有一条接一条的缺陷是测试全绿、实际运行之后才暴露的（见 [决策 0002](../decisions/0002-own-server-replaces-jarvis.md#从真实启动中学到的)）。涉及应用壳、服务端或生命周期的改动，除了 `bun run verify`，还要按本文实际跑一遍。

收发文件的整条路（事件、下载、核对、落盘、回执、重试；选文件、上传、撤回、对账；存进云盘、从云盘取回）有对着真实服务端跑的测试，在 `apps/desktop/src-tauri/src/transfers/tests.rs`。它们不算真实启动：窗口、通知、钥匙串只有真的跑起来才算数。

## 0. 先知道这几件事

- **模拟的浏览器不算浏览器。** 测试里的"浏览器"是 HTTP 客户端，请求头是人为构造的。凡是浏览器参与的流程（登录页、授权确认页），必须在真实的浏览器里走一遍。
- **屏幕锁定时做不了界面层面的验证。** 锁屏后没有前台应用，读不到窗口内容，截图会超时。后台进程照常运行，所以进程层面、接口层面的检查仍然有效。
- **区分"卡死"和"读不到"。** 窗口读不出来时，先用 `sample <进程号> 1 -file /tmp/sample.txt` 看主线程：停在正常的事件循环等待里是健康的；停在我们自己的代码里、或者在等一把锁，就是卡死。
- **不要替桌面端往系统钥匙串里预置会话。** 桌面端没有登录就收不了文件，用 `security add-generic-password` 塞一条会话进去看着像个办法，实际会在屏幕上弹一次钥匙串确认框，等人来点。那是用户的屏幕，不是测试的。桌面端的登录只能走浏览器，由人来做。2026-11-24 这么干过一次，惊动了用户，已清理干净。

## 1. 准备：本地服务端、账户和一台替身设备

```sh
# 本地开发用的服务端：数据放在 data/local/server（不进仓库），地址 http://127.0.0.1:8787
bun run server:dev
```

另开一个终端，建一个账户并登记一台没有界面的"替身设备"，充当第二台电脑：

```sh
printf '你的密码\n' | ASSEMBLE_DATA_DIR=data/local/server ASSEMBLE_PUBLIC_ORIGIN=http://127.0.0.1:8787 \
  cargo run -p assemble-server -- create-account dev
cargo build -p assemble-server --example fake_device
F=./target/debug/examples/fake_device
$F --token data/local/fake-a.json register --data-dir data/local/server --account dev --name 替身A
$F --token data/local/fake-a.json online   --origin http://127.0.0.1:8787
```

`online` 会把收到的事件打印出来，`Ctrl+C` 下线。要同时扮演两台设备，给每台各指定一个 `--token` 文件。替身直接写服务端的数据库，只能用在本地开发的服务上。

替身还能当发送方（桌面端登录之后用，见第 3 节）：

```sh
$F --token data/local/fake-a.json send  --origin http://127.0.0.1:8787 --to <本机的设备名> --file 某个文件.pdf
$F --token data/local/fake-a.json sends --origin http://127.0.0.1:8787
```

`--to` 认设备名或设备标识；`sends` 列出它发出去的与收到的记录和各自的状态。替身登记时用 `--platform windows` 可以让它看起来像一台 Windows 电脑。

## 2. 构建并启动桌面端

```sh
cd apps/desktop
ASSEMBLE_SERVER_ORIGIN=http://127.0.0.1:8787 bunx tauri build --no-bundle
cd ../..
./target/release/assemble-desktop 2>&1 | tee /tmp/assemble-run.log
```

连接哪个服务在构建时定下：不设 `ASSEMBLE_SERVER_ORIGIN` 的发布构建拒绝启动。调试构建加载的是开发服务器上的页面，需要先 `bun run dev:frontend`。

## 3. 检查窗口与登录

- 窗口出现，左上角写着"本地开发服务"（按地址判断，不是按调试还是发布），账户卡片里有"使用浏览器登录"。
- 点"使用浏览器登录"：系统默认浏览器打开授权页；还没登录时会先跳到登录页。在浏览器里登录并点"确认登录"，回到应用时应当已登录，账户卡片下面写着"这台设备：<本机名>"。
- "设备"卡片列出账户里的全部设备，替身设备显示在线，本机带"本机"标记。停掉替身（`Ctrl+C`），列表里它变成离线。
- 关掉窗口：应用留在托盘（菜单栏右侧）。再运行一次可执行文件，第二个实例会把窗口叫回来然后自己退出，进程始终只有一个。

读窗口内容可以用系统自带的无障碍接口（Xcode 的"辅助功能检查器"，或任何读屏工具）：页面里的文字和按钮都应当读得到，主线程卡死时则什么都读不到。

## 3b. 收一个文件

桌面端登录之后，保持替身 `online`，另开一个终端让替身发一个不重要的文件过来：

```sh
$F --token data/local/fake-a.json send --origin http://127.0.0.1:8787 --to <本机的设备名> --file /path/to/某个文件.pdf
```

期望：

- 文件出现在 `~/Downloads/Assemble/` 里，内容与原文件一致；同名再发一次得到 `某个文件 (2).pdf`，原来那份不动。
- 弹出一条系统通知，"收到文件"。点它，访达打开并选中那个文件（只选中，不打开）。
- 应用里"传输"卡片多了一条，写着"已保存"，右边有"在文件夹中显示"。
- 替身那边：`online` 的输出里出现一条 `send_updated`，状态是 `delivered`；`sends` 里写着"对方已收下"。
- "本机"卡片里点"更改…"能挑一个接收文件夹，界面只显示那个文件夹的名字；"恢复默认"回到"下载/Assemble"。

把接收文件夹设成一个只读的位置再发一次：这一条显示"接收失败：文件没能写进接收文件夹"，替身的 `sends` 里是"对方接收失败（写入失败）"。把设置的文件夹删掉再发：文件退回"下载/Assemble"，通知和应用里都说明了原因。

## 3c. 发一个文件

桌面端登录之后，让替身 `online`，然后从这台电脑发一个不重要的文件给它：

- 菜单栏图标 →"发送文件…"，或者主窗口"传输"卡片右上角的"发送文件…"。系统弹出文件选择框，挑一两个文件。
- 弹出"发送到…"面板：上面是挑好的文件（只有名字与大小），下面是账户里别的设备。离线的设备是灰的，点不了。
- 点那台在线的替身。每个文件一行进度；全部传完后面板显示"已发送"，过一两秒自己关掉。
- 替身那边：`online` 的输出里出现 `send_offered`；它的 `sends` 里写着"等对方接收"。主窗口"传输"卡片里这一条写着"已发出，等对方接收"，右边有"取消"。
- 点"取消"：这一条变成"已撤回"，替身那边出现 `send_updated`（`cancelled`）。

再试三种不顺利的情况：

- 替身下线后再发：面板里它是灰的。如果它恰好在点下去的那一刻下线，这一条显示"发送失败：那台设备刚刚下线了"，有"重发"。
- 挑好之后把文件移走再点设备（面板开着时在访达里把文件拖走）：显示"发送失败：文件读不出来，可能已被移走或改动"；把文件放回去，点"重发"能发出去。
- 挑一个超过 100 MB 的文件：提示"超过 100 MB，发不出去"，面板不打开。

## 3d. 云盘

桌面端登录之后：

- 主窗口有一张"云盘"卡片：写着已用多少空间（例如"已用 1.5 MB，共 2.0 GB"）、一根用量条，下面是云盘里的文件（名字、大小、日期），新的在前。右上有"上传…"。
- 点"上传…"，在系统选择框里挑一个文件：这一条出现在"传输"卡片里，"正在上传到云盘…"，然后"已存到云盘"。云盘卡片里多出它，已用空间跟着涨。
- 把"接收位置"记下来，点某个文件的"取回"：文件出现在接收位置里，内容与原文件一致；"传输"卡片里这一条写着"已取回"，有"在文件夹中显示"；弹出一条通知。
- 点"删除"要先点"确认删除"才删。删掉之后另一台已登录的设备上，它也不会再出现（连上服务或重新打开应用时名单会换新）。
- 打开"发送到…"面板：最上面是"云盘"，下面才是设备。点"云盘"，面板显示"正在上传到云盘…"，存好后自己收起。

在发送面板里点"云盘"存一个超过剩余空间的文件（或者把服务端的 `ASSEMBLE_DRIVE_QUOTA_BYTES` 调小再试）：这一条写着"没能存进云盘：云盘空间不够"，有"重发"。

## 3e. 发起发送的入口

- **拖放**（macOS 与 Windows）：把一两个文件从访达拖进 Assemble 主窗口，松手后弹出"发送到…"面板，里面就是刚拖进来的文件。拖一个文件夹进来：主窗口提示"只能发送文件，不能发送文件夹。"。一摞东西里既有文件又有文件夹时，文件夹被略过，文件照发。
- **带着文件启动**：在终端里运行 `./target/release/assemble-desktop --send 某个文件.pdf`。应用没在运行时，它会启动并打开面板；已经在运行时，新启动的那个自己退出，面板由原来那个打开（单实例）。
- **右键菜单**（只有 Windows 上的打包运行有）：在任意文件上点右键 →"显示更多选项"→"用 Assemble 发送"，面板打开。主窗口"本机"卡片里有这一项的开关；Windows 11 上它在"显示更多选项"里，Shift+F10 也能到。

没登录的时候做这三个动作，不会打开面板，而是把主窗口叫到前面并提示"请先登录，再发送文件。"。

## 4. 退出并确认清理

带应用包的构建可以直接退出：

```sh
osascript -e 'tell application id "com.puzzlefuzzy.assemble" to quit'
```

不带应用包的可执行文件要把窗口置前后按 ⌘Q。期望：进程退出；替身设备收到一次"设备下线"的事件，`online` 的输出里本机变成离线。

再确认服务端不会自己退出：启动之后至少过十五秒，`curl http://127.0.0.1:8787/healthz` 仍然应答。曾经出现过服务端启动十秒后自己退出的情况。

最后确认服务端能按时退出：对它发 `kill -TERM`，应当在一秒内结束，即使此刻有事件流连着。曾经出现过服务端收到信号后无限期挂着的情况。

## 5. 收尾

```sh
pkill -TERM -f 'fake_device --token data/local'
rm -f data/local/fake-*.json      # 替身设备的令牌，仅本人可读
```

真实登录过的应用会在系统钥匙串里留一条 `assemble.device-session:http://127.0.0.1:8787`。在应用里"退出登录"会删掉它。

## Windows 真机验收清单

Windows 上没法在这台 Mac 上自动验证。下面每一条都对应一段只做过类型检查的代码，请在 Windows 上逐条走：

1. **安装并启动。** `bun run build` 打出安装包，装好后启动：窗口出现，托盘里有图标，"本机"卡片里有"右键菜单"一项，默认开着。
2. **右键菜单。** 在资源管理器里对任意一个文件点右键 →"显示更多选项"：有"用 Assemble 发送"。点它：发送面板打开，里面是这个文件。
3. **单实例。** 应用已经在运行时再点一次右键菜单：面板被叫到前面，任务管理器里进程仍然只有一个。
4. **开关。** 在"本机"卡片里关掉"右键菜单"：右键菜单里那一项消失。重新打开：它回来。想直接看注册表：`reg query "HKCU\Software\Classes\*\shell\AssembleSend" /s`。
5. **拖放。** 把一个文件从资源管理器拖进 Assemble 窗口：面板打开。拖一个文件夹：提示"只能发送文件，不能发送文件夹。"。
6. **登录、收发、云盘。** 第 3、3b、3c、3d 节各走一遍。收到的文件在 `下载\Assemble`；通知会弹出，点它在资源管理器里选中那个文件。
7. **开机启动。** "本机"卡片里打开开关，重启电脑确认应用随系统启动、不弹窗口只在托盘里。
8. **退出。** 托盘图标 →"退出 Assemble"：进程消失；另一台设备的列表里这台电脑变成离线。

哪一条不对，把现象和 `reg query` 的输出发给我。应用本身不写日志文件，所以现象描述得越具体越好（点了什么、看到了什么、隔了多久）。

## 2026-11-24 做过的

- 服务端与两台替身设备：两台都在线时互相可见，一台到时下线后另一台立刻看到它离线。
- 桌面端（发布构建）：窗口与界面内容正确；点"使用浏览器登录"后进入等待状态并打开系统浏览器；关窗收起后由第二个实例唤回。
- 真实浏览器（Chromium 内核）里的登录页：登录成功。
- 服务端带着打开的事件流收到 `SIGTERM` 后 0.02 秒退出。
- 服务端启动十四秒之后仍在应答 `/healthz`（之前它启动十秒后会自己退出，已修）。
- 替身设备的 `register`、`devices`、`send`、`sends` 四个命令（服务端与替身是各自的进程）：发给在线设备后对方的 `online` 输出里出现 `send_offered`；给自己发得到 `INVALID_REQUEST`，而不是"连不上服务"（之前是后者，已修）。
- 带着文件启动（`--send`），没登录时：主窗口出现提示"请先登录，再发送文件。"，没有打开面板。两种情形都真实跑过——应用没在运行时由它自己启动；已经在运行时，第二个实例 0.09 秒就退出，全程只有一个进程，请求由原来那个处理。
- 一次没有查明白的观察：一个带着文件启动、之后挂了十来分钟没人动的实例，后来读它的窗口时读不到网页内容（只剩窗口自己的按钮和菜单栏）。它的主线程停在正常的事件循环里，系统日志里没有它的任何记录，也没有崩溃报告。随后做的受控复现（启动后 7 秒读）内容正常。所以它到底是"内容真的没了"还是"只是读不到"，现在不知道。
- 抓到并修掉了一批测试全绿时藏着的缺陷，连同两条时过时不过的测试，逐条记在决策 0002 的"从真实启动中学到的"。

- **桌面端收一个文件**（第 3b 节的全部内容）：落盘、通知、点通知定位、回执、接收文件夹的设置。整条路有对着真实服务端跑的自动化测试，但窗口、通知、系统对话框没有在真实运行里看过。
- **桌面端发一个文件**（第 3c 节的全部内容）：选文件、发送面板、进度、取消、重发。发送这一路同样有对着真实服务端跑的自动化测试，但面板窗口、文件选择框、菜单栏里的"发送文件…"没有在真实运行里点过。

- **拖文件进窗口**：拖放只能靠人手做，没有在真实运行里试过。
- **带着文件启动或拖放之后，登录状态下真正打开发送面板**：没登录时的那一步在 macOS 上真实跑过（见上面）；登录之后打开面板、读文件的参数、对摘要的那一步只有代码与类型检查，没有真实跑过。

- 托盘菜单的逐项操作、开机启动开关。
