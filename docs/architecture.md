# 架构说明

本文描述 Assemble 当前的实际结构：哪些已经落地、为什么这样划分、边界在哪里。为什么选这条路、放弃了哪些备选，见[决策 0002](decisions/0002-own-server-replaces-jarvis.md)；计划中的内容在[路线图](plans/2026-11-23-roadmap.md)，这里不重复。

## 范围

- **服务端与桌面端都在这个仓库里。** 服务端是 Rust（axum + SQLite），桌面端是 Tauri 2；两者共用一份协议类型。Assemble 完全替换 jarvis；用户后来明确授权影视与日程的一次性业务数据导入，源站只读，身份和凭据不迁移。
- **优先级：文件传输与日程规划。** 文件传输已落地，正式服务已上线；日程规划的第一批（日程、提醒、到点通知）在服务端与桌面端都已写完，给助手用的对话入口（`assemble-mcp`）也写完了，都有自动化测试；手机上的提醒做完了第一期，靠本机提前排好的系统通知，远程推送留到第二期（[决策 0014](decisions/0014-iphone-client.md)）。宠物、壁纸排在最后。
- **已有端为 Windows 与 macOS 桌面端、助手入口 `assemble-mcp` 与网页管理端；本轮新增只读影视展示站，另有一个原生的 iOS 应用。** 普通用户身份网页仍由服务端渲染：邮箱登录、公开注册与验证、GitHub 授权、桌面授权确认、账户（主邮箱、头像、网页改密与找回）。管理端同源 `/admin/` 的账号与设备范围仍只读；用户后来确认增加共享影视维护，并新增同源 `/movies/` 海报墙与本人私人库只读展示（[决策 0008](decisions/0008-media-libraries-and-viewer.md)）。影视源码已接入，尚未正式发布。iOS 应用第一期只有日程与提醒（[决策 0014](decisions/0014-iphone-client.md)），在模拟器里走通过，真机上还没有人用过。

## 结构

云盘上传新增独立 `uploads` 契约和服务端会话/确认片；客户端只据持久确认继续，桌面 registry 保留当前进程内的稳定请求与源文件。新旧上传共用事务预留，最终仍由 BlobStore 的长度、摘要和内容租约发布。暂停不自动唤醒，取消按稳定键对账，完成先提交就返回原文件；原路径、摘要和请求键不进入快照。首包不持久恢复源任务，不改云盘下载或设备发送线格式，见[上传手册](runbooks/drive-uploads.md)。

管理端业务日志复用 `audit_log`，由 `activity` 模块投影安全的操作人、设备和对象元数据。云盘、传输和影视的数据库触发器保留名称与删除状态，远控只逐项写入安全字段并对生命周期去重；内存远控内容不会序列化进日志。管理员通过同源只读接口筛选记录、查看历史对象，文件与影视按标识深链接到已有详情。日志不开放给普通账户或设备令牌，迁移及读取边界见[管理端手册](runbooks/admin.md#操作日志)。

```text
┌──────────────────────────── apps/desktop（Tauri 2）────────────────────────────┐
│  界面（React）：主窗口 · 发送面板                                              │
│    只调用具名命令、接收状态事件；没有凭据，头像与影视图片按各自受控入口加载，路径操作由 Rust 负责 │
│      │ invoke（具名命令）                              ▲ 事件（完整状态快照）  │
│  应用壳（Rust，src-tauri）                                                     │
│    会话 · 后台任务（收、发、对账）· 传输记录表 · 日程名单                      │
│    通知 · 设置 · 启动入口                                                      │
└──────┼───────────────────────────────────────────────────┼────────────────────┘
       ▼                                                 ▼
  crates/assemble-client ── HTTP 与事件流 ──▶ apps/server（axum + SQLite）
  crates/assemble-transfer ──▶ 文件系统                 账户 · 登录页 · 设备 · 发送 · 云盘 · 日程与提醒
  crates/assemble-device ──▶ 接收目录、右键菜单         blobs/（按摘要存放）
  crates/assemble-store ──▶ 设置文件、系统钥匙串
  crates/assemble-protocol（类型）   assemble-schedule（日程出现规则，两端共用）

  Codex、ZCode ── MCP（标准输入输出）──▶ apps/mcp（assemble-mcp）──▶ crates/assemble-client ──▶ apps/server
                                          具名工具：日程与提醒、通知标已读、私人备忘录、本机下载预览/开始/状态

  手机 ── apps/ios（SwiftUI + AssembleCore）── HTTP：只拉名单，不开事件流 ──▶ apps/server
```

`apps/ios` 按操作系统命名，不按机型；将来的安卓应用放 `apps/android`。两个都不进 Cargo 工作区，有自己的测试与构建方式（见下面"iOS 应用"一节）。

依赖方向是单向的：应用依赖基础库，基础库不依赖应用；`assemble-protocol` 只依赖 `serde`，位于最底层。规则都在 `crates/` 里，脱离窗口与网络就能测试；应用壳只做编排。

## 各部分职责

管理后台与桌面应用内页面共用 `packages/display` 的国际化和外观偏好：首批简体中文/英语，主题为浅色/深色/跟随系统。默认中文、跟随系统，选择只在本机保存，同源桌面窗口同步。两端仍共用 `packages/ui` 的 shadcn 控件、样式和主题入口；不会把语言选择混入账户凭据或 Rust 状态契约。浏览器身份页、托盘和系统通知不在首批范围，约定见[决策 0007](decisions/0007-language-and-appearance.md)。

用户 2026-11-26 另要求浏览器身份页的视觉与两端对齐：登录、注册、验证、账户和设备授权复用共享 shadcn 的构建时静态输出，生成物、字体及许可证随 Rust 二进制内嵌。原生 POST、CSP 样式哈希与精确回环授权保持原边界，没有新增登录前端或密码读取脚本；字体只开放 `/web/ui/` 内嵌白名单。身份页仍沿用中文、跟随系统外观，不扩展首批语言与偏好菜单范围，见[身份页界面说明](runbooks/browser-identity-ui.md)。iOS 真机与推送不属于此次调整。

影视的管理端、桌面端与 `/movies/` 展示站共用 `packages/media` 的 DTO、校验、业务组合和 `media` 中英字典，基础组件仍只有 `packages/ui` 一份，外观复用同一个 display 实例。ToC 自有文案注册 `mediaSite`；同源网页共用本机偏好，桌面保持自己的本机偏好。

## 服务端

远程桌面使用 `assemble-protocol::remote` 与 `assemble-remote`：前者是唯一协议，后者放输入规则、Noise 加密、画质策略及可选原生适配。服务端 `remote` 只保留同账户会话、公开握手和有界密文队列，所有接口逐次核验双方设备；桌面 `remote` 编排握手、核对代码、逐次批准、采集线程与退出收尾。密钥只在 Rust 内存里，快照只含会话元数据和公开核对代码。画面、输入、剪贴板与系统声音在 Rust 加解密；图片/视频、音频 PCM 经主窗口的具名命令交给界面，剪贴板正文不进界面。文件与云盘保持原有管线。方案和边界见[决策 0017](decisions/0017-remote-desktop-first-batch.md)。

`assemble-remote::worker` 将原生对象留在同一线程内，以最多两项的队列处理采集与输入；`assemble-client::remote_host` 并行轮询输入和上传画面，静止画面不重复上传。网络等待不占用原生线程，输入应用后才确认序号，停止时先显式等待原生释放，再通知服务端；新的被控会话等待旧会话收尾。结束原因只保留首次结果，由协议类型及桌面快照样本共同约束。

H.264 使用 OpenH264 软件编码，界面 WebCodecs 解码，丢帧后等待 IDR；不支持时回退 JPEG。声音默认关闭，Windows 使用 WASAPI 输出回环，Mac 使用 ScreenCaptureKit 系统声音，不选择麦克风；原生工作线程做重采样和 Opus 编码，音频网络任务独立于画面。双方经过认证的挑战/应答心跳限制 5 秒存活窗口，旧心跳不能续期；切屏后的旧物理输入按显示器标识丢弃且确认，避免作用在另一块屏幕。显示器与光标位置均随加密内容传送。

### 启动与配置

没有配置文件，全部来自环境变量（业务配置用 `ASSEMBLE_`，邮件与 OAuth 使用 `SMTP_*`、`GITHUB_*`）。没有配置文件、必须显式给出数据目录与对外地址，是因为猜错它们的后果比启动失败更糟。

| 环境变量                                           | 说明                                                     | 默认                          |
| -------------------------------------------------- | -------------------------------------------------------- | ----------------------------- |
| `ASSEMBLE_DATA_DIR`                                | 数据放在哪里                                             | 必填                          |
| `ASSEMBLE_PUBLIC_ORIGIN`                           | 浏览器访问服务端的地址，决定 Cookie 与来源校验           | 必填                          |
| `ASSEMBLE_ADDR`                                    | 监听地址，默认只监听本机、由反向代理转发                 | `127.0.0.1:8787`              |
| `ASSEMBLE_DRIVE_QUOTA_BYTES`                       | 每个账户的云盘上限                                       | 2 GiB                         |
| `ASSEMBLE_STORAGE_BUDGET_BYTES`                    | 全站的内容总量上限：云盘与还没送达的发送一起算           | 10 GiB                        |
| `ASSEMBLE_STORAGE_WARN_PERCENT`                    | 内容预算预警百分比，整数 1～100；磁盘余量另按 2 GiB 预警 | 80                            |
| `ASSEMBLE_CLIENT_IP_HEADER`                        | 反向代理写来源地址的请求头；填了之后按来源的限额才生效   | 不填                          |

| `ASSEMBLE_TMDB_TOKEN` / `ASSEMBLE_TMDB_TOKEN_FILE` | 受保护的 TMDB 凭据；环境值与文件模式二选一               | 可选，不配置时 TMDB 不可用    |

命令行有 `serve`、`check-config`（读取配置并连接数据库，应用迁移和指定管理员初始化后退出）、`create-account`（密码从终端读两遍，永不当参数传入；建立待绑定的旧式账户）、`set-password`、`list-accounts`、`grant-super-admin <已验证邮箱>`，以及停用与恢复账户的 `suspend-account <邮箱>` 和 `resume-account <邮箱>`。管理员配置使用受保护环境变量 `ASSEMBLE_SUPER_ADMIN_EMAIL`；静态管理资源由 `ASSEMBLE_ADMIN_ASSETS_DIR` 指定，本地默认 `apps/admin/dist`，镜像内固定 `/usr/share/assemble/admin`。

### 邮箱、GitHub 与头像

账户规则见[决策 0005](decisions/0005-public-email-accounts-and-github.md)。新增 `email_identity` 负责邮箱归一化、数据库限流与凭据原子消费，`identity_web` 适配浏览器表单，`mail` 通过 Rust SMTP 发信，`github` 核对稳定的外部身份。邮箱和密码在网页验证后使用；桌面端只接收公开邮箱和头像，不接触 SMTP 或 OAuth 凭据。

`0003_email_identity.sql` 为旧账户增加邮箱与头像，新增 `github_identities`、`email_actions`、`email_rate_limits`；不改已有迁移。旧账号保留原 id，通过原密码和邮件验证补绑邮箱。邮箱匹配不能自动合并 GitHub 账户。更换主邮箱需先后确认原、新邮箱，密码找回后撤销网页登录状态；设备凭据保留。

公开网页还包括 `/web/forgot`、`/web/legacy`、`/web/verify`、`/web/github/start`、`/web/github/callback`、`/web/github/profile`；账户页提供 `/web/account/email`、`/web/account/github`。验证表单使用 POST 和成对 CSRF，邮件凭据只有摘要落库；GET 不消费凭据。SMTP/OAuth 配置、限额与代理日志要求见[账户配置手册](runbooks/email-and-github.md)。

### 部署

正式服务在 2026-11-24 上线：<https://as.yxswy.com>，Docker Compose 加 nginx。材料在 `deploy/`；做过的与还没有验证过的见[部署手册](runbooks/deploy.md)。

| 文件                 | 做什么                                                                                                                                           |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `Dockerfile`         | Bun 构建共享 UI 管理端与影视展示站、官方 Rust 编译服务端、Debian slim 以专用账户运行。Rust 版本与工具链一致，SQLite 静态编入，网页资源随镜像发布 |
| `compose.yaml`       | 一个服务。端口只绑在本机的 `127.0.0.1:8787`，交给反向代理；镜像与数据的位置由 `.env` 决定；日志自动轮转                                          |
| `compose.build.yaml` | 只在本机自己构建镜像时叠加到 `compose.yaml` 上                                                                                                   |
| `.env.example`       | 配置模板：镜像、数据位置、对外地址必填，其余都可以不填                                                                                           |
| `nginx.conf.example` | TLS 在这里结束。上传上限 110 MB，请求体不缓冲，`/v1/events` 的长连接关掉缓冲、放宽读超时。与正式服务器上的那一份只差域名                         |
| `push-image.sh`      | 把持续集成构建的镜像经 SSH 送到服务器上。服务器在国内，直接拉 GitHub 的镜像仓库会握手超时                                                        |

服务端默认不读转发头：在它看来所有请求都来自反向代理。只有部署者用 `ASSEMBLE_CLIENT_IP_HEADER` 说明了哪个请求头可信（nginx 写的 `X-Real-IP`），服务端才从那个头里取来源，而且只拿它做一件事：按来源分限额。来源不进日志，不参与授权。配置它就等于相信只有反向代理能连到服务端，所以只在端口不对外时才填。

### 几条规则怎么落地

- **设备的平台是一份会变长的清单，读的时候留了兜底。** 桌面端是 Windows、macOS、Linux，手机应用是 iOS（线上的值是 `ios`，按操作系统命名，和目录 `apps/ios` 对齐）；这一版代码不认识的值归成"其他"，设备名单照常读得出来，不再有哪个平台能让一个账户的接口一起失败。只有电脑上的应用能收文件。加一个新平台的顺序是：服务端先升级，两台电脑再更新应用，然后才有新平台的设备登录。
- **手机扫码配对只能往前走。** `pending → claimed → approved → consumed`，或者在任意一步变成 `denied`。一张票据只能被认领一次；网页上的人点"允许"之后，令牌只发给拿对 PKCE 校验器的手机；拿错的校验器试过一次，这张票据就作废。三分钟内没走完也算作废，由定时清理删掉。
- **内容按摘要存放、按引用计数。** 云盘文件与待接收的发送都只是指向 `blobs` 的一行引用，磁盘上同一个内容只有一个文件；最后一个引用放掉时才删。上传时边收边核对长度与摘要，不一致就丢。
- **发送只能往前走。** `offered → delivered | declined | cancelled | failed | expired`。到达终态就释放内容；重复的回执是幂等的。
- **定时清理**每分钟一轮：过期的发送被标记并通知两边、太久的发送记录与过期的授权码、配对和登录状态被删除、没人引用的内容与中断的暂存文件被清扫。服务端只有一个实例，这里不需要跨进程协调。
- **正式服务与测试服务走同一段启停代码。** 退出信号先让事件流自行结束，再等在途连接，最多等十秒——计时从收到信号开始，不给服务定寿命。
- **被提前拒绝的上传要先读完再拒绝。** 不然连接会在发送方还在上传时被关掉，它只看到"连不上服务"。
- **日程与提醒只有一份名单。** 没有逐条的推送：`GET /v1/planner` 给出"还用得上的那一些"，任何一处改动都把整份重新算一遍，经事件流推给这个账户的每一台在线设备。
- **名单不随时间只增不减。** 它不是账户的全部记录：还可能再提醒的日程与提醒（没到点的；重复且没停的；最近七天里开始的一次性日程）、最近七天里完成或取消的、到点后还没人处理的、没读的通知。早就过去的一次性日程状态仍停在"进行中"，到点七天都没人处理的提醒也一样，但它们不再列出——记录都在，接口按标识取得到。不然记录越积越多，到了条数的上限，按时间排在前面的旧记录会先把新的挤出去。
- **同一场只提醒一次。** 通知的主键就是"哪一条日程、哪一场"（提醒是它自己的标识），登记与生成是同一条插入，任务跑重了、服务端重启了都插不进第二条。调度每十秒一轮；离开提醒时刻超过十分钟、或者这一场已经结束的，不再提醒；提醒不管晚了多久都补。
- **改过之后，旧的提醒不再补发。** 取消、完成、删除之后，还没读的通知作废；只改标题、地点、备注的，通知原地换新；改了时间或重复规则的，按新规则不再成立的那几场作废。
- **通知只标已读，不删除。** 一处标了，别的设备在下一份名单里就看不到它。三十天之前的由定时清理删掉。

### 谁都能来的地方，各有一道闸

注册是公开的，下面这些入口不登录也能碰。每处的限额都分"全站共用"和"按来源"两份，按来源的那份要配了 `ASSEMBLE_CLIENT_IP_HEADER` 才生效；来源分不开时各处退回到只按全站（或者只按账户）的那一层。

| 入口                         | 不按来源的那一层                                    | 按来源的那一层             | 被拦时                                 |
| ---------------------------- | --------------------------------------------------- | -------------------------- | -------------------------------------- |
| 云盘与发送的内容             | 每个账户 2 GiB，全站 10 GiB                         | 无                         | 413 `QUOTA_EXCEEDED`，什么都不留下     |
| 密码核对（登录、改密、绑定） | 同一个来源对同一个账户 15 分钟 5 次                 | 同一个来源对所有账户 30 次 | 429，`Retry-After`                     |
| 申请验证邮件                 | 每个邮箱每分钟 1 次、每小时 5 次；全站每小时 120 封 | 每个来源每小时 5 封        | 429，`Retry-After`                     |
| GitHub 登录的起点            | 同时 256 条没走完的登录                             | 每个来源同时 8 条          | 503，`Retry-After`                     |
| 公开的影视目录查询           | 全站每分钟 60 次、同时 2 个                         | 每个来源每分钟 20 次       | 429 `MEDIA_CATALOG_RATE_LIMITED`       |
| 匿名抓取的影视图片           | 作为缓存的所有者最多 512 MiB，全站的图片 2 GiB      | 无                         | 409 `QUOTA_EXCEEDED`；缓存一小时后过期 |

旁人连错五次锁不住你的账户：拦的是连错的那个来源对那个账户，你从别处来照常能登录。全站的额度也不是一个来源能用的：先看来源那一份，被拦的请求不去占全站的份额。

一个账户真出了事，在服务器上按邮箱停用它：之后哪里都登不进去（密码或 GitHub 授权对了也不行），网页登录状态当场作废，电脑与助手的令牌每一次请求都被拒；数据留着，恢复之后设备照旧能用。已经连着的事件流要等它自己重连才断。

### 影视库与展示站

影视服务在 `apps/server/src/media/`：权限、条目归属、来源适配、资产发布与导入任务分别执行，不让处理器自行拼另一套 DTO。`assemble-protocol::media` 定义共享契约，`assemble-client` 提供桌面方法；Rust 与 TypeScript 共读 `packages/media/contract` 样本。

共享与私人是独立片库，来源身份在各自归属范围内去重，两者均支持 `planned/watching/completed`。匿名可读共享内容，但服务端删除 `magnetUri`，共享备注也只给管理员；私人条目、图集和观看信息只给所属账户。合集只引用共享条目，统计只聚合共享库。来源详情和演员作品不携带某个私人库是否已收录的信息。

公开读取位于 `/v1/media/shared/entries`、`/v1/media/collections` 与 catalog 相关接口，私人读写位于 `/v1/media/private`。共享写入、共享任务与统计位于 `/v1/admin/media`，逐次验证邮箱、管理员、同源与写入 CSRF，设备令牌不能访问。浏览器只使用 HttpOnly Cookie；桌面只经 Rust 具名方法使用设备身份，应用壳拒绝共享写入。

TMDB 凭据仅在服务端的受保护环境或文件里。豆瓣公开来源遇到限制时返回稳定错误，不读取私人 Cookie。来源只访问固定 HTTPS 主机，图片大小、解码与总像素受限，校验后在事务里发布原图及 `200/360/480` 衍生图；响应带长度与摘要。匿名读取资产还必须有共享引用或未过期的公开来源缓存引用，不能猜测 assetId 读取私人或暂存图片。桌面 `media_image` 核对后返回数据 URL，界面不拿到令牌、任意远程图片地址或本地路径；`media_copy_magnet` 按条目标识重新授权后复制。

`0005_media.sql` 新增条目、来源身份、资产、任务、幂等记录与合集，不修改旧迁移。影视图片为 SQLite 的 `media_asset_variants.content` BLOB，备份必须包含数据库本体与已有文件目录，不能将 `blobs/` 当作全部影视资产。导入持久化真实阶段和项目数量，未知进度不造百分比；版本冲突拒绝覆盖，重试按提交结果是否已知区分幂等续查与新尝试。

`apps/media-web` 构建为同源 `/movies/`，运行时默认目录 `apps/media-web/dist`，镜像 `/usr/share/assemble/movies`。它是固定第一方应用，复用本站登录并回到固定 `/movies/`，没有维护操作，也不是任意用户内容托管。2026-11-26 用户另行授权从 Jarvis 线上迁入影视、缓存、封面与旧影视归档，源库与参考仓库仍只读；账号、认证关联与旧站点配置不迁移。维护命令先校验输入，目标必须是空片库，再通过单事务发布。迁移 `0010_media_archive_import.sql` 保存原始清单、逐文件 BLOB、缓存快照及保全引用；保全不等于公开授权，缓存图片另有明确公开引用。已有 TMDB 凭据只进入受保护配置。实现、发布与验收证据分别见[决策 0008](decisions/0008-media-libraries-and-viewer.md)与[影视手册](runbooks/media.md)。

## 桌面端

“网络文件下载”是独立本机能力：`assemble-download` 负责公开来源解析、受控网络、HLS 资源、下载队列、媒体校验与无覆盖发布，壳只对接具名命令、系统选择器和退出清理。它使用本机 FFmpeg/ffprobe，不依赖账户、云盘或服务器媒体工具；历史保存于私有 `network-downloads.json`，来源网址和匿名 Cookie 不进入快照。使用与限制见[网络下载说明](runbooks/network-downloads.md)。

Chrome 开发插件位于 `apps/browser-extension`，只在工具栏操作后检测当前页；用户另行授权才捕获主动启用标签的网络媒体。后台 session 保留有界临时来源，弹窗只接收标题、类型与主机。下载点击经 `assemble-browser-host` 的长度前缀 JSON 具名请求交给桌面进程，不让插件直接改任务文件。宿主精确匹配扩展来源，桌面监听临时回环端口，系统钥匙串保存临时连接凭据；宿主先以挑战验证端口身份，再发送认证请求。没有 CORS 或公开网页调用入口，退出显式停止服务、下载与凭据。启动时这一条凭据是先删再建的：上一回没来得及删的还留着时直接改写它，macOS 会要人输登录钥匙串的密码，应用停在启动上（2026-11-27 真的遇到过）；删除和新建都不用问人。状态只新增任务定位信号 `browserTaskId`，源地址和连接凭据不进入快照。加载与原生登记见[插件说明](../apps/browser-extension/README.md)。

### 界面有两个窗口

主窗口是账户、设备、传输、日程、云盘与本机设置；发送面板是"挑好的文件 + 去处"的小窗口，由 Rust 在需要时创建。它们的能力清单完全一样，都只有"接收状态事件"一项。

界面能看到的状态由 `apps/desktop/contract/snapshots.json` 钉住：Rust 在测试里把样本读进来再原样写出去，TypeScript 在运行时核对每一个字段。任何一边改了形状，都有一侧的测试失败。

### 一次传输怎么走

一条传输只有一份记录，按方向各走各的路：

```text
收到：排队 ─▶ 正在接收 ─▶ 已保存 ─▶（回执确认）
                  └▶ 接收失败 ─▶（把原因报告上去）
发出：排队 ─▶ 正在发送 ─▶ 等对方接收 ─▶ 对方收下 | 拒收 | 过期
            └▶ 发送失败                  └▶ 已撤回 | 对方接收失败
云盘：排队 ─▶ 正在上传 / 正在取回 ─▶ 完成（存进云盘不欠回执；取回与接收同一条路）
```

- **按先来后到，一次一个。** 收排在发前面，因为对面正等着。同名的文件先后到达时自然得到不同序号。
- **本机效果先落盘再回执。** 回执没送到不算完：与服务端对账时会发现它还在等，再补一次。
- **说不准是谁的问题时不怪任何一方。** 取不到内容只是过一会儿从头再来；报告给对面的只有这台电脑确实写不下来，以及内容与声明的对不上。
- **取消要取消到底。** 上传途中取消、文件却已到了服务端的，对账时按内容摘要、文件名和收件人认出来，在服务端撤回。
- 事件流不补送断线期间的事件，所以每次连上、以及之后每隔五分钟，都向服务端问一遍"还有哪些文件在等我"、"哪些发出去的还悬着"。

### 一条提醒怎么走

日程与提醒都存在服务端。桌面端拿一份名单来显示和操作，自己不排程：

- **整份名单来、整份换。** 连上服务时拉一次，之后每隔五分钟随对账再拉一次（过了零点，"接下来七天"要往前挪），服务端每有一处改动就再推一份；改动之后本机也再拉一次，不依赖事件流一定送到。
- **到点由服务端决定。** 规则见上面服务端的"几条规则怎么落地"。
- **接下来七天的场次在桌面端展开**，用的是和服务端同一个规则库（`assemble-schedule`），所以界面上的时间与实际提醒的时间对得上。
- **到点后没人处理的提醒，在"接下来的安排"里留七天。** 之后不再列出；记录还在，助手或接口按标识还找得到它。
- **这台电脑弹不弹，记在本机。** 名单里带着全部还没读的通知；哪几条已经弹过，记在本机设置的有界账本里（最多两千条）。只补弹最近二十四小时之内生成的，更早的只留在列表里；"本机"卡片里的开关关掉之后只记账、不弹，以后打开也不会把积压的全弹一遍。
- **点了系统通知，主窗口打开并定位到那一条。** 通知的标识只在 Rust 里对得上是哪一条。
- **每一次改动都带着看到的版本号。** 别处改过时服务端拒绝，Rust 换上最新的名单；界面只说"在别的设备上改过，请再看一眼"，并把还留着旧值的表单收起来。新建带一个幂等键，超时重试不会建出两条。
- **界面交给 Rust 的只有标题、时间与几句备注。** 表单里的时间是本地时间，交出去之前换成 UTC。地点只填一个名字：没改就原样留着（导航用的地址还在），改了就只剩新写的那个名字。

## iOS 应用（第一期）

原生 Swift，在 `apps/ios`；范围与边界见[决策 0014](decisions/0014-iphone-client.md)。它只做日程与提醒：看名单、到点响、点开通知定位到那一条、扫码登录、退出登录。收发文件、云盘、影视、远程推送、后台刷新都不在手机上。

- **两层。** `AssembleCore` 是不依赖界面的 Swift 包：线上的类型、时间的解析、重复规则的推算、通知的规划、接口、配对与登录的保存。应用壳（SwiftUI）里只有 `AppModel` 一个状态来源，界面只读它、调它的方法；网络、钥匙串、系统通知、时钟都是它指名的依赖，测试换成替身。
- **类型和规则由 Rust 侧钉住。** 线上的类型按各种取值序列化成 `apps/ios/Fixtures/protocol.json`，重复规则的推算结果钉成 `recurrence.json`；两份都由 Rust 侧的测试生成并逐字比对，不手改。Swift 的 `Recurrence` 是 `assemble-schedule` 里 `occurrences.rs` 的逐行移植，样本里的每一问都和 Rust 的答案一致。
- **不开事件流，只拉名单。** 启动、回到前台、前台中每三十秒、下拉时各拉一次 `GET /v1/planner`，每次都是整份。同一份登录里同一时刻只跑一轮：读的时候又有谁要读，记下来，读完再补一轮（补的这一轮必须真的跑——要求它的那个动作改过的东西，前一轮的回应里未必有）；换了登录就另起一轮，旧那一轮的结果一律丢掉。所以手机在设备名单里总是离线。
- **到点靠本机提前排好的系统通知。** 每次拿到名单，按和服务端同一条规矩（`NotificationPlan`，纯函数）算出今后三十天里该响的：提醒在它的时刻，日程在每一场开始前"提前量"那么久；已经结束的场次和离开提醒时刻超过十分钟的不排。取最近的六十条（系统至多留着六十四条待发的）。触发用的是从排的那一刻起算的时间间隔，和时区、夏令时无关；前台中每三十秒对一遍，变了的重排，没动的不动。
- **标识就是服务端通知的标识。** 提醒是 `n-<提醒标识>`，日程是 `<日程标识>-<场次的毫秒>`。交给系统去响的标识记进本机的账本，所以本机响过之后，服务端到点才生成的同一条通知不会再响第二遍；手机既没排过也没弹过的（离线期间服务端生成的），恢复之后补弹一次，只补最近二十四小时之内的。
- **点开一条通知，定位到那一条。** 先在名单里还没读的通知中找；找不到（服务端到点之后十几秒才生成记录，用户抢在了前面）就按标识的构成找回那一条。应用是被这一下点开才启动的时候名单还没读出来：标识先记着，名单到了再定位。通知代理的两个方法用带回调的写法，不用 `async` 的那一种——那一种在后台线程上收尾，UIKit 跟着更新界面快照时会断言崩溃。
- **"看过了"到点的头几秒也能办成。** 提醒到点的那一瞬服务端把它的版本号加一，用户手里多半还是加一之前的那一份。被拒一次之后，名单里它只是变成了已到点的话，就照新的版本号再交一次；别的冲突照旧把说法留给用户。提醒到了点不算办完：点开它到点的通知，详情要留着等用户点"看过了"，不自己关上；详情页上的按钮拿名单里最新的那一条去交。
- **办完一条，它的通知跟着算看过。** 提醒"看过了""不办了"、日程"完成""取消"之后，它到点的通知一并标成已读——包括服务端晚一步才生成的那一条，不然"没读的通知"里会留下一条已经办完的。
- **登录只有扫码配对，令牌只在这台手机的钥匙串里。** 应用不加载登录页、不接触密码。退出登录以服务端确认为准。通知的权限在用户打开"到点提醒"时才申请；系统不让发的时候开关弹回去，账户页上留着一句怎么说。

## 账户独立的文本备忘录

2026-11-26 用户要求桌面端新增备忘录列表，支持新建、粘贴纯文本和每行直接复制；进一步确认不同账号内容独立，切回原账号时恢复。内容保存在服务端 SQLite，具名设备接口与写事务均约束账户；客户端不保存公共文本副本，管理端没有代看入口。`assemble-protocol::memo` 统一校验标题、纯文本长度、版本与分页，新建回执防止重复和删除后的复活。列表仅返回摘要，详情与复制读取完整原文。壳复用会话取消与分界核验，退出或换账号的旧请求不能更新新页面；复制只收标识，由 Rust 重新获取文本后写系统剪贴板。页面草稿随账户或页面卸载清除，已保存内容可重新读取；首批通过页面进入和刷新获取其他设备的变更，不增加离线编辑或实时事件。独立返回样本为 `apps/desktop/contract/memos.json`，不改变主 Snapshot。接口、迁移 0009、备份与 MCP 边界见[备忘录说明](runbooks/memos.md)。

## 系统通知

管理端和桌面端顶部共用 `packages/ui` 的通知铃铛与 shadcn Dialog 居中弹窗，用户主动打开，空列表仅显示文字。通知在后台自动更新和重试，不提供刷新按钮；桌面变更由 Rust 快照更新，管理端在可见时定时同步。系统通知使用独立的 `assemble-protocol::system_notifications`，不扩展日程通知、设备事件、iOS 或远程推送；常规成功反馈不进入历史。

`assemble-store::notifications` 负责按范围和资源合并、恢复版本、已读及有界历史。后台采样更新不会反复变未读，恢复或严重程度变化才产生新版本；已读不表示问题解决。管理通知由维护任务生成并经 `0007_system_notifications.sql` 保存，各管理员独立记已读；同源管理员 API 与 CSRF 保护不变。桌面只读取本机与本人账户范围，原子私有保存，文件损坏或写入失败不确认已读。两端只投影具名内容和资源标识，不返回服务器路径、来源地址或诊断，见[决策 0012](decisions/0012-system-notifications.md)。

## 助手入口

`apps/mcp` 是一个单独的可执行文件 `assemble-mcp`：Codex、ZCode 这样的客户端把它当作 MCP 服务端启动，经标准输入输出调用它的工具。你管理日程的方式是对话——"我明天 9:00 的火车"由助手听懂、算好提前量、想到要带什么；Assemble 只负责存下来、到点提醒。所以这个入口不含模型，也不猜你的意思：理解与排程在助手那边，校验与规则在 Assemble 这边（[决策 0003](decisions/0003-schedule-first-batch-and-conversational-entry.md)）。

### 命令

| 命令                                            | 做什么                                                                                             |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| `assemble-mcp serve --name <名字>`              | 在标准输入输出上提供工具，给客户端用；不带子命令时也是它。名字要和登录时用的一致                   |
| `assemble-mcp login --name <名字>`              | 系统浏览器里走一遍和桌面端相同的授权页，让这台助手登录成账户里的一台设备。已经登录过的先退出再登录 |
| `assemble-mcp logout --name <名字>`             | 服务端确认撤销之后才删掉本机保存的登录；连不上服务端时不退                                         |
| `assemble-mcp status --name <名字>`             | 连的是哪个服务、以哪台设备的身份登录、现在通不通。不显示令牌；没登录或登录已失效时退出码是 1       |
| `assemble-mcp print-config codex --name <名字>` | 打印把这个可执行文件接进 Codex 的配置片段。片段里只有路径和参数，没有任何秘密                      |
| `assemble-mcp print-config zcode --name <名字>` | 同上，给 ZCode 的那一段                                                                            |

名字就是它在账户里的设备名，省略时是"助手"；每一条日程与提醒都记着是哪台设备写的，界面上看得出"这一条是 ZCode 的助手加的"。想收回这台助手的权限，在桌面应用的"设备"卡片里移除它：登录随即作废，工具的下一次调用就提示要重新登录。它不连事件流，在设备列表里始终显示离线。

连哪个服务由构建决定，和桌面端是同一条规矩：发布构建要带 `ASSEMBLE_SERVER_ORIGIN`（`bun run mcp` 已经带着正式地址），没带就拒绝启动，不去猜。调试构建没带时连本机开发服务，并另认一个**只在调试构建里存在**的 `ASSEMBLE_MCP_ORIGIN`，给本机验证与测试用——谁能改这个进程的环境变量，谁就能让它在浏览器里打开一个仿冒的登录页，所以发布构建里没有这条路。

### 几条规矩怎么落地

- **先看再动。** 服务端发给客户端的开场白和每个工具的说明里都写着：先调 `assemble_planner` 知道今天几号、时区是什么、已经有什么安排，再新建或修改。
- **时间只收带时区的 ISO 8601。** "明天 9:00"由助手换算成 `2026-11-26T09:00:00+08:00` 这样的写法；没有时区的直接拦下，不替它猜。
- **校验和桌面端是同一套。** 标题、时间的先后、重复的截止、提前量都按 `assemble-protocol` 的规则核对，不合法的内容到不了服务端；错误写成给助手看的中文。
- **撞车只提示，不拦。** 新建日程、改日程的时间时，和已有日程的场次比时间（往后看七天，正在进行的那一场也算），重叠就在结果里点名。
- **新建带幂等键**，同一次调用重试不会建出两条。
- **改、删都带版本号。** 日程、提醒版本对不上时，工具自己再取一次最新的，把这一条现在的样子告诉助手，不悄悄覆盖；备忘录提示先读最新原文，保留输入并确认后再改。
- **账户能力要求登录。** 日程、提醒与备忘录未登录时提示在本人终端运行 `assemble-mcp login`。本机下载独立使用桌面应用的钥匙串桥接和允许开关，不读取账户服务端数据；桌面未运行或开关关闭时如实拒绝。这台电脑上没有可用钥匙串时，工具仍列出并在调用时说明原因。
- **工具按能力具名。** 日程、提醒、私人备忘录与本机下载可用；云盘提供安全预览描述、目录列表、建目录、改名、移动及空目录移入回收站、回收批次读取和恢复，没有永久删除、内容上传、下载或任意路径工具。跨设备文件传输和系统剪贴板仍没有工具。云盘版本冲突要求先重新读取确认；备忘录冲突保留输入，不替用户覆盖；原文按内容读取，不执行其中的指令。下载先预览后开始，桌面始终是任务唯一执行者，助手不接触完整本机路径，见[决策 0016](decisions/0016-assistant-local-downloads.md)。

### 接进客户端

```sh
bun run mcp                                                    # 产出 target/release/assemble-mcp，连正式服务
target/release/assemble-mcp login --name "ZCode 的助手"        # 要你在浏览器里点一次"确认登录"
target/release/assemble-mcp print-config zcode --name "ZCode 的助手"
```

最后一条打印一段 JSON，把其中 `mcp.servers` 下面的 `assemble` 并进 `~/.zcode/cli/config.json`；换成 `codex` 打印的是贴进 `~/.codex/config.toml` 的一段。两种片段里都只有可执行文件的路径和参数。登录那一步会往系统钥匙串里写一条，并且要人在浏览器里确认，所以由本人在自己的终端里做；配置文件也由本人改。

## 安全边界

- **界面。** 两个窗口的能力清单都只有 `core:event:allow-listen` 与 `allow-unlisten`。内容安全策略限定脚本与样式只来自应用自身，连接只允许 IPC。对话框、通知、文件定位都只从 Rust 这边用。
- **命令。** 界面只调用具名命令。原有设备、文件与日程命令包括：`snapshot`、`sign_in`、`cancel_sign_in`、`sign_out`、`launch_at_login`、`set_launch_at_login`、`rename_device`、`remove_device`、`choose_receive_folder`、`reset_receive_folder`、`reveal_received`、`start_send`、`send_to_device`、`send_to_drive`、`close_send_panel`、`open_main`、`cancel_transfer`、`retry_transfer`、`drive_refresh`、`drive_upload`、`drive_download`、`drive_delete`、`set_send_menu`、`dismiss_notice`、`planner_refresh`、`schedule_create`、`schedule_update`、`schedule_complete`、`schedule_cancel`、`schedule_reopen`、`schedule_delete`、`reminder_create`、`reminder_update`、`reminder_dismiss`、`reminder_cancel`、`reminder_delete`、`notifications_read`、`notifications_read_all`、`planner_focus`、`planner_compose`、`set_planner_muted`。影视另有 `media_capabilities`、`media_list`、`media_get`、`media_create`、`media_update`、`media_remove`、`media_search`、`media_catalog`、`media_actor`、`media_import`、`media_job`、`media_gallery`、`media_sync_gallery`、`media_select_poster`、`media_image`、`media_copy_magnet`；其中写入仅支持私人范围。命令失败只返回稳定错误码。
- **标识，不是操作路径。** 界面引用一条传输、一个云盘文件、一台设备、一条日程、一条提醒、一条通知，用的都是标识。文件的位置由系统选择器、右键菜单或拖放直接交给 Rust；唯一的显示例外是 Windows 的接收目录文字，不能把它传回作为文件操作参数。
- **助手。** `assemble-mcp` 只有上面列出的具名工具，处理日程、提醒、通知、当前账户的私人备忘录、本机下载与本人云盘的安全预览描述，没有"随便调一个接口"的工具。新增能力时在 `apps/mcp` 里加工具并补测试。它不碰窗口、剪贴板，也不接收文件路径。
- **凭据。** 设备令牌存在系统钥匙串里，条目名按服务来源区分；助手的登录是另一条条目，账号位是助手的名字，不会顶掉桌面应用的。令牌、Cookie、密码、SMTP 授权码与 OAuth Secret 不进桌面界面、日志、命令返回值与状态；邮件凭据只存摘要，密钥只在受保护环境或文件中；写操作的网页表单都要来自本站，并带着与 Cookie 或会话成对的随机值；`assemble-mcp status` 与工具的返回值里都不出现令牌，它的标准输出上只有协议消息，日志一律写标准错误。桌面端另有一份本机日志文件，写的是和标准错误上同样的行，这一条对它同样成立。macOS 的钥匙串按程序的签名认人：签名每次构建都变的程序，读以前保存的登录时系统要再问一次用户，所以会读钥匙串的发布构建在这台 Mac 上构建完都自动用本地证书签名。Windows 的凭据管理器不这样认人，那边没有签名。
- **联网。** 客户端只访问构建时确定的那个来源，不跟随重定向；标识符与路径在拼进请求之前先校验。
- **更新。** 桌面应用只从构建时确定的那个服务取更新清单和更新包，公钥编在应用里、关不掉：签名不对的包装不上，不允降级。服务端发布时用同一把公钥再核对一遍，签名的私钥只在发布用的那台 Mac 上。开发运行（`tauri dev`、不带应用包的可执行文件）不自动更新，连的是正式地址也不更新。见[决策 0015](decisions/0015-desktop-auto-update.md)。
- **文件。** 接收目录只能来自默认位置或系统选择器，必须是真实的目录、不能是整块磁盘；文件名来自网络，收敛成单个在 Windows 上也合法的名字。发布之前再确认一次接收目录还是原来那个——下载途中目录被删、被换成链接，文件都不会落到别处。收到的内容按声明的长度与摘要核对，对不上就不出现。通知与"在文件夹中显示"只选中文件，不打开它。
- **公开的入口。** 注册公开之后，谁都能访问的几处各有限额，并且都按来源再分一份（见上面"谁都能来的地方，各有一道闸"）。来源只在配置了可信的代理头之后才读，只用于限额。停用、恢复账户由已验证邮箱的超级管理员在网页详情确认，要求同源与 CSRF，不能停用自己；CLI 仍保留。写事务内复核权限，状态和操作者/目标审计一起提交，重复操作不重复记账；停用撤销网页会话、拒绝设备请求并结束已有事件流，数据保留。详见[决策 0010](decisions/0010-admin-account-operations-and-storage.md)。

| Windows 右键菜单     | `HKCU\Software\Classes\*\shell\AssembleSend`                                                                                                                  | 指向这个可执行文件，不需要管理员权限                                                                     |

传输记录保存在本机应用数据目录的私有 transfers.json，最多 100 条，按服务来源和账户隔离。重启恢复已完成文件的标识定位；未完成记录标为中断，不自动重发旧路径，由后续对账接回服务端有效发送。登录失效时隐藏并保留原账户历史，明确退出且服务端确认撤销后清空历史，已经落盘的文件仍留在接收位置。损坏或未来版本记录不当成空文件覆盖。

## 已知的限制

- **真实验证只走了一小段。** 服务端、替身设备与桌面端的启动是真实跑过的；正式服务上，你本人已经在两台电脑上登录（2026-11-25），从 Mac 发给 Windows 一个文件并确认收到了，助手也经工具建出过一条日程（2026-11-26）。还没有真人做过的：桌面上的到点提醒（2026-11-27 07:30 是第一次）、反方向和大文件的互传、云盘的上传取回删除、拖放、登录之后的发送面板、托盘菜单、开机启动、退出清理。这些目前只有对着真实服务端跑的自动化测试。逐条见运行手册。
- **Windows 上只走过开头几步。** 代码第一次在 Windows 上编译、检查与测试是持续集成的 Windows 那一栏跑起来的（2026-11-24）；2026-11-25 在真机上装好并显示了主窗口，单实例通过，右键菜单点了能唤起应用（没登录时提示先登录），并收到了 Mac 发来的文件。托盘菜单、通知、拖放、开机启动、退出清理，都还没有在 Windows 桌面上试过。
- **收到的文件只有本人可读写。** 暂存文件以 `0600` 建立，发布用的是硬链接，所以落到"下载/Assemble"里的文件也是 `0600`，而浏览器下载的文件一般是 `0644`。在只有一个人用的电脑上没有差别；接收位置如果是和别人共用的文件夹，别人就读不了。Windows 不看这几个权限位。要不要改成跟随系统的默认权限，待定。
- **对外的签名与公证没有做，自动更新有了。** 持续集成能打出不带签名的安装包，两个平台的都成功过多次；没有 Apple 的签名、公证，也没有 Windows 的代码签名。自动更新（2026-11-27，[决策 0015](decisions/0015-desktop-auto-update.md)）用自己的服务器下发、用只在那台 Mac 上的私钥签名，更新包只有 Windows 的 NSIS 安装包和 Apple 芯片的 Mac 两种；Windows 真机上的静默安装与自动重启、换新版之后钥匙串不再问，还没有在真人电脑上验过。开发机上另有一张本地的自签证书，`bun run build`、`bun run mcp` 与 `bun run browser:host` 构建完会自动用它签名（钥匙串里有才签）：它让系统钥匙串认得每一次构建，发出去的 Mac 应用也必须用它签；它不是对外分发用的，见运行手册"本地签名"。
- **云盘目录源码已实现，尚未部署。** 独立 `drive_tree` 契约支持带版本的文件与文件夹改名、移动、空目录删除和指定目录上传；管理端按账户只读浏览。旧平铺入口与类型保持兼容，既有文件在根，文件同名仍允许。目录每账户最多 1000 个、深度 16 层，变更在写事务内复核所属与拓扑，不增加内容引用；桌面和助手只调用具名命令。实际契约、Windows/浏览器与镜像验收见[文件夹手册](runbooks/drive-folders.md)，macOS 与正式发布另记。
- **收到的文件自动收下，不先询问。** 服务端支持拒收，桌面端没有拒收的按钮。
- **单文件 100 MB 以内，不支持文件夹，没有断点续传。** 中断了从头再来。
- **服务端只有一个实例。** 在线状态在内存里，清理也假定只有一个进程在跑。
- **正式服务上真人只用过几步。** 账户是本人用 GitHub 注册的；两台电脑登录过；一个文件从 Mac 到了 Windows；助手建了一条日程。其余的——云盘、通知、片库的导入与维护、网络下载与扩展——都还没有人对着正式地址用过。
- **日程这一部分的桌面端还没有等到过一次真实的提醒。** 服务端的到点调度与推送对着真实运行的服务端核对过（提醒到点后生成通知并推给在线设备、离线的设备重连后拉名单拿到）；带提前量的日程只有注入时钟的测试。2026-11-26 助手建了第一条真实日程（2026-11-27 09:00，提前 90 分钟），它将是第一次在真人电脑上响起来的提醒。桌面端的名单、系统通知与补弹、托盘里的"新建提醒…"目前只有自动化测试。手机上的提醒见下面一条。
- **手机应用只在模拟器里走过。** `bun run ios:simulate` 在模拟器里对着一次性的本机服务端把配对登录、名单、到点的系统通知、点开定位、看过了整条路走通；真机上没有一步是人做过的：用摄像头扫、锁屏上通知的样子、被划掉之后点开通知冷启动、前后台与离线，清单在运行手册。没有远程推送和后台刷新：应用被划掉之后到点照样会响（排进系统的通知），但离线期间别处的改动要等下一次打开才看得到。手机旁边没有电脑时登不了（"系统提供的网页登录会话"那一条路没有做）。图标是和桌面端同一个占位点阵。
- **助手入口只走过前半段。** 真实的登录 2026-11-26 由你本人点了确认、走通了；十个工具、整条登录和经协议的调用都对着真实运行的服务端有自动化测试。那一次建日程是助手按同一条协议直接调的工具，还不算"在 ZCode 里说一句话、由它自己去调"；那一步还没有发生。
- **`assemble-mcp` 没有打进安装包，在 Windows 上只跑过自动化测试。** 它要用 `bun run mcp` 单独构建。2026-11-25 持续集成的 Windows 那一栏第一次跑了它的全部测试，包括起一个真正的 `assemble-mcp` 子进程经标准输入输出握手；但打开系统浏览器、往 Windows 的凭据库里写登录、配置片段里路径的写法，都还没有在真实的 Windows 桌面上试过。那一栏是它唯一的 Windows 环境。
- **完成或取消的日程、办完的提醒，界面里看不到。** 服务端留着它们，接口按标识取得到、也能改回进行中；名单只给还在进行中的。界面上没有撤销的入口，所以取消和删除都要先确认。
- **GitHub 的 macOS 机器有时容量紧张。** macOS 那一栏会排很久的队，安装包流程里的 macOS 任务被整个取消过一次；遇到就重新触发。
- **`assemble-store` 的 `scope` 目前没有任何调用方。** 它是分段隔离用的，留着等有按账户分段的数据时用。
- **网络下载与 Chrome 扩展还没有真人用过。** 代码已进主分支：Windows 上用一份独立的 Chrome 资料走通过扩展、本机桥接与下载；macOS 上 2026-11-26 只跑了那条用真实 FFmpeg 的下载测试，装好的应用里还没有人点过。FFmpeg 没有随安装包捆绑，找不到时页面会说清楚；扩展没有上架，要手动加载，本机桥接也要单独登记。
- **影视片库已上线并完成授权导入。** 既有共享影视和合集继续保留；2026-11-27 新增的个人默认私有、主动公开、全用户管理与个人主页边界属于本轮源码和本地验证，正式升级和私人维护的真人操作需另行记录。
- **总量到了上限时，桌面端的说法不够准。** 服务端的内容总量到了 `ASSEMBLE_STORAGE_BUDGET_BYTES` 时，回答和"云盘空间不够"是同一个码，桌面端照旧提示"云盘空间不够"。删掉一些文件确实能让它恢复，只是没说明白是服务器满了。

## 验证方式

三种证据，不能互相替代：

- **自动化测试**：`bun run verify` 覆盖界面、共享组件、工具脚本、Rust 单元与真实服务集成；数量以对应版本的实际验证日志为准。文件传输集成测试走收发、撤回、对账、云盘与重启恢复；助手入口测试账户隔离、幂等、版本冲突、浏览器授权回环及真实 MCP 协议；本机下载另测经过认证的桌面桥接和安全输出。测试来源和临时账户不等于正式账号或真人操作。 自动更新另有对着真实服务端和签名来源的集成测试（见[决策 0015](decisions/0015-desktop-auto-update.md)）。
- **真实启动**：在 macOS 上构建并运行服务端、替身设备与桌面端。主流程用一条 `bun run acceptance`：它起好整套环境，由人登录之后自动核对收发与退出；只要其中一样的时候怎么单独起，见[运行手册](runbooks/verify-macos-launch.md)。
- **手机应用在模拟器里**：`bun run ios:test` 是核心包的测试（Swift Testing，31 条：样本解码、每一问和 Rust 的推算一致、通知的规划与对账、接口与错误）；`bun run ios:simulate` 起一次性的本机服务端，在模拟器里先跑应用层的单元测试（14 条，跑在应用自己的进程里），再用界面测试把配对登录、名单、到点的系统通知、点开定位、看过了整条路走一遍，并回服务端核对。持续集成的 macOS 那一栏跑前一条；后一条只在装了 Xcode 的 Mac 上由人触发。这一遍抓到过单元测试全绿时照样存在的问题（点开通知必崩、读名单的标记卡住、到点头几秒"看过了"办不成），所以动过应用壳之后要跑它。
- **真机验收**：Windows 与两台真实设备之间的收发，清单在运行手册末尾；iOS 的清单在同一份手册里，还没有人走过。

真实启动抓到过自动化测试没暴露的缺陷——比如服务端启动十秒后自己退出、给离线设备发大文件时发送方只看到"连不上服务"。所以涉及应用壳、服务端或生命周期的改动，要真的把它们跑起来。

仓库是公开的，每次推送由持续集成在 macOS 与 Windows 上各跑一遍 `bun run verify`（`.github/workflows/verify.yml`）。Windows 那一栏是服务端、客户端、助手入口与桌面应用壳唯一的 Windows 环境：六个基础库之外，它们的 Windows 目标在这台 Mac 上检查不了。2026-11-24 它跑起来的第一天，两个平台加起来抓到了十几处只在那边才有的问题，逐条记在决策 0002 的"从真实启动中学到的"里。

## DHT 管理端观测

`assemble-dht` 承担 bencode、BEP-5/51、BEP-9/10 和元数据验证；`apps/server/src/dht` 编排同一 SQLite 的持久化队列和网络生命周期。只有 `/v1/admin/dht/*` 接口和网页 `/admin/#dht` 入口，复用管理员会话、同源与 CSRF 边界。新增 `0008_dht.sql`，不迁移旧数据，默认不启动采集。实现范围见[决策 0013](decisions/0013-admin-dht-observations.md)，配置与验收见[DHT 手册](runbooks/dht.md)。

## 云盘回收站（N3）

N3 新增 `drive_trash` 协议与处理器、0016 迁移、只读活动视图和持久 blob_cleanup 任务。移入与恢复使用子树/目标修订和写事务；回收文件仍计配额，永久删除先事务扣引用后异步清理。内容发布至引用登记持摘要租约，清理重试不能误删重新使用的内容。管理端仅按账户只读回收元数据，桌面通过具名命令组合共享回收站表格与确认弹窗，MCP 仅增加读取和恢复（共 27 个工具）。旧普通删除在新服务上只移入，新桌面不向旧服务退回永久删除。实际契约、兼容、存储口径和发布边界见[回收站手册](runbooks/drive-trash.md)。本轮未部署，未改 iOS 或推送。
