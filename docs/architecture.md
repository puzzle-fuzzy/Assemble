# 架构说明

> **本文已过时，重写排在文件收发打通之后。** 下面描述的是转向之前的结构（对接现有 Jarvis API 的桌面端）。从 2026-11-24 起 Assemble 自带 Rust 服务端，见 [决策 0002](decisions/0002-own-server-replaces-jarvis.md)；其中"从真实启动中学到的"一节是现在仍然成立的经验。下文的"调研中决定设计的几条事实""Electron 版的对应关系""本机网关"等段落只作历史参考。

本文描述 Assemble 当前的实际结构：哪些已经落地、为什么这样划分、与 Electron 版有哪些刻意的不同。计划中的内容在 [路线图](plans/2026-11-23-roadmap.md)，这里不重复。

## 范围

- **只重写桌面这一侧。** 服务端、网页端、小程序、iOS 都不在本仓库；桌面端继续使用现有的 Jarvis API。
- **优先级：文件传输与日程规划。** 宠物、壁纸排在最后。
- **契约基线。** 参考实现是 `jarvis` 仓库 `main` 分支的 `0d6eb5f`。那个仓库声明不保留旧客户端兼容，所以契约变化时这里需要跟着改。

## 调研中决定设计的几条事实

以下都是读 `jarvis` 源码得到的结论，不是推测。

1. **一切经 API 中转。** 没有 WebSocket、SSE 或设备直连。实时性靠 HTTP 长轮询：设备每轮 `GET …/commands?waitSeconds=20`，请求预算 30 秒；另有 15 秒心跳、60 秒命令租约和按连接递增的"代际"围栏。
2. **认证完全不在渲染层。** 桌面端在系统浏览器里登录，经回环地址和 PKCE 交回单次授权码，再换取独立的设备会话。两种令牌都不进页面。
3. **Tauri 的窗口加载不了原来的远程网页。** 原网页依赖同源 Cookie。Tauri 窗口是另一个来源，而服务端有四道彼此独立的限制：Cookie 的 `SameSite=Lax`、只接受 HTTP(S) 来源的 CORS 白名单、写操作的 Origin 校验、`Cross-Origin-Resource-Policy`。所以界面必须是打包在应用里的本地页面，联网全部由 Rust 完成。
4. **本机网关是 MCP 的唯一入口。** 现有的 `apps/mcp` 不访问云端，只通过回环端口调用桌面端。协议（发现文件、三个接口、认证与拒绝规则）必须保持不变。
5. **日程由服务端触发。** 云端每秒检查一次，到点生成通知并给在线设备排一条 `notify` 命令；桌面端只负责投递，不算触发时间。网页端只能创建提醒；日程、任务、目标、计划由 Codex（经 MCP）、语音和管理端写入。
6. **原实现有几处可以借重写改进。**
   - 每次扫描都把所有文件完整哈希一遍，记录下来的修改时间从未被用来跳过。
   - 达到上限的文件每 30 秒被重新哈希一次。
   - 上传与下载都把整个文件读进内存。
   - 库存上报一次只发一条，而接口允许 1000 条。
   - 本机的通知去重列表只增不减。

## 结构

```text
┌────────────────────────────── apps/desktop ──────────────────────────────┐
│  界面（React）                                                            │
│    只调用具名命令、接收状态事件；没有凭据，不联网                          │
│      │  invoke（少量具名命令）                 ▲  事件（完整状态快照）      │
│  应用壳（Rust，src-tauri）                                                │
│    窗口 · 托盘 · 单实例 · 开机启动 · 会话流程 · 本机网关接线                │
└──────────┼──────────────────────────────────────────┼─────────────────────┘
           ▼                                          ▼
   crates/assemble-client ──▶ Jarvis API（HTTPS）   本机工具（如 MCP）
   crates/assemble-device ──▶ 本机网关（回环端口）
   crates/assemble-transfer ──▶ 文件系统
   crates/assemble-store ──▶ 状态文件、系统钥匙串
   crates/assemble-protocol（类型）   crates/assemble-schedule（推算）
```

依赖方向是单向的：应用壳依赖基础库，基础库不依赖应用壳；`assemble-protocol` 只依赖 `serde`，位于最底层。

## 各部分职责

| 单元                     | 负责                                                                                               | 不负责               |
| ------------------------ | -------------------------------------------------------------------------------------------------- | -------------------- |
| `assemble-protocol`      | 线上契约的 Rust 类型与纯校验：九种资源、设备命令、文件定位、本机网关操作目录、桌面登录、账户、探活 | 任何 I/O             |
| `assemble-client`        | 发往云端的唯一出口：固定服务来源、不跟随重定向、凭据头、超时与取消、错误归类、回环登录监听         | 业务规则             |
| `assemble-store`         | 状态文件的原子私有写入；按服务来源与账户分段的文件名；密钥存储抽象（系统钥匙串 / 内存）            | 决定存什么           |
| `assemble-transfer`      | 边读边算的摘要；暂存文件；校验后以硬链接发布，绝不覆盖；本机文件身份                               | 判断目录是否被授权   |
| `assemble-device`        | 路径边界、目录授权账本、命令回执账本、本机网关服务                                                 | 心跳与长轮询的编排   |
| `assemble-schedule`      | 日程出现规则推算（与云端同一套算法）；有界的通知去重账本                                           | 触发提醒             |
| `apps/desktop/src-tauri` | 窗口、托盘、生命周期、开机启动、会话流程、具名命令                                                 | 传输与日程的业务规则 |

## 安全边界

- **界面。** 主窗口的 capability 只有 `core:event:allow-listen` 与 `allow-unlisten`。内容安全策略限定脚本与样式只来自应用自身，连接只允许 IPC。
- **命令。** 界面能调用的只有 `snapshot`、`sign_in`、`cancel_sign_in`、`sign_out`、`launch_at_login`、`set_launch_at_login`。命令失败只返回稳定错误码，技术细节不回显给用户。
- **状态。** 界面收到的状态只有服务是否可达、会话阶段、账户的公开信息、开机启动状态和一条提示。样本在 `apps/desktop/contract/snapshots.json`，Rust 与 TypeScript 两侧各自对着它校验；界面在交界处还会再做一次运行时核对。
- **凭据。** 网页会话 Cookie 只用来换取设备会话，换完立即撤销，不落盘。设备会话存在系统钥匙串里，条目名按服务来源区分。
- **联网。** 客户端只访问构建时确定的那个来源，不跟随重定向；标识符与路径在拼进请求之前先校验。
- **本机网关。** 只监听 `127.0.0.1` 的随机端口，每次启动换一个新的随机令牌；要求主机头精确匹配且不带 `Origin`，所以浏览器页面调用不了。对外只公布本构建真正提供的操作，其余如实回答未提供。发现文件仅本人可读写，应用退出时显式删除。
- **文件。** 所有路径先做边界检查：共享目录必须是真实的绝对路径，路径中任何一段是链接、或实际位置跑出共享目录，都直接拒绝；凭据、依赖与构建产物不参与共享。

## 数据放在哪里

| 内容           | 位置                                                    | 说明                     |
| -------------- | ------------------------------------------------------- | ------------------------ |
| 设备会话与账户 | 系统钥匙串，服务名 `assemble.device-session:<服务来源>` | 退出时删除               |
| 网关发现文件   | 应用数据目录下的 `bridge.json`                          | 应用运行期间存在         |
| 应用数据目录   | 系统为 `com.puzzlefuzzy.assemble` 指定的目录            | 与 Jarvis 的目录互不相干 |

授权账本、回执账本、文件索引和通知去重目前只在内存里；随设备运行时一起落盘是路线图第一阶段的内容。

## 与 Electron 版刻意的不同

1. **界面是本地的。** 原因见上面第 3 条。尚未原生实现的功能暂时不在窗口里出现。
2. **退出登录是"失败即保留"。** 连不上服务、无法确认撤销时，保持登录并提示用户稍后重试。原实现会把撤销放进一个离线加密队列稍后重试。两者都不会留下无人认领的会话；区别是原实现离线也能退出，这里不能。
3. **不保存网页会话 Cookie。** 换到设备会话后立刻撤销它，所以本机始终只有一条有效凭据。原实现保留 Cookie，用于退出应用后重新签发设备会话。
4. **通知去重账本有上限。** 超过 2000 条时淘汰最早的记录；原实现的列表只增不减。
5. **构建类型决定连接目标。** 调试构建连本地开发服务，发布构建连正式服务；两者不会互相读取对方的数据。

## 已知的限制

- 登录流程只做过针对模拟服务的测试，没有对真实服务跑通一遍。
- 应用退出时不会让设备离线，因为设备注册还没有实现。
- 只在 macOS（Apple Silicon）上构建和启动过；Windows 没有验证。
- 发布构建没有签名、公证，也没有自动更新。
- 生成过 macOS（Apple Silicon）的 `.app` 与 `.dmg`。Intel Mac 与 Windows 没有构建，也没有验证。
- 发布构建是临时签名，每次重新构建签名都会变。同一个作者在另一个项目里遇到过这种情况导致系统授予的权限失效；系统钥匙串的访问授权是否也受影响没有在这里验证过，做真机登录验收时要留意。
- 日程规划依赖的规划与生产力接口，在 `jarvis` 里标注为"未发布到正式服务"（见那个仓库的 `docs/personal-continuity.md`）。在它们上线之前，发布构建的 Assemble 只能连接到不提供这些接口的服务。
- 托盘图标确认出现在菜单栏，但托盘菜单本身没有打开过；开机启动开关没有实际拨动过。

## 验证方式

- `bun run verify`：Biome、类型检查、界面测试、前端构建、Rust 格式与静态检查、Rust 测试。
- 契约样本的双向校验做过变异验证：把样本里的一个字段改错，Rust 与 TypeScript 两侧都会失败。
- 日程出现规则与云端原有的 TypeScript 实现做过对照：用同一批两万条确定性生成的用例分别运行两边，结果逐项一致。这是一次性的验证，不是常驻测试。
- `bun run build` 跑通，产出 `Assemble.app` 与 `Assemble_0.1.0_aarch64.dmg`。
- 在 macOS 上实际启动过发布构建，裸二进制与 `.app` 各一次：界面渲染正确，对正式服务的探活成功，托盘图标出现在菜单栏，网关的应答、认证与拒绝行为符合预期，正常退出后发现文件已删除。

实际启动抓到过两个单元测试没暴露的缺陷，都已修复并回归：网关曾对外公布契约里的全部操作；应用退出后发现文件没有被删除。
