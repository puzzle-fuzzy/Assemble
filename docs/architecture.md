# 架构说明

本文描述 Assemble 当前的实际结构：哪些已经落地、为什么这样划分、边界在哪里。为什么选这条路、放弃了哪些备选，见[决策 0002](decisions/0002-own-server-replaces-jarvis.md)；计划中的内容在[路线图](plans/2026-11-23-roadmap.md)，这里不重复。

## 范围

- **服务端与桌面端都在这个仓库里。** 服务端是 Rust（axum + SQLite），桌面端是 Tauri 2；两者共用一份协议类型。Assemble 完全替换 jarvis，不迁移它的数据。
- **优先级：文件传输与日程规划。** 文件传输已落地，正式服务已上线；日程规划的第一批（日程、提醒、到点通知）在服务端与桌面端都已写完并有自动化测试，给助手用的对话入口与手机上的提醒还没有做（[决策 0003](decisions/0003-schedule-first-batch-and-conversational-entry.md)）。宠物、壁纸排在最后。
- **第一期的端：Windows 与 macOS 桌面端。** 网页端只提供登录页与授权确认页。日程要在手机上提醒，而 iPhone 应用还没有做：怎么提醒在[决策 0003](decisions/0003-schedule-first-batch-and-conversational-entry.md)里等你定。

## 结构

```text
┌──────────────────────────── apps/desktop（Tauri 2）────────────────────────────┐
│  界面（React）：主窗口 · 发送面板                                              │
│    只调用具名命令、接收状态事件；没有凭据，不联网，拿不到文件路径                │
│      │ invoke（具名命令）                              ▲ 事件（完整状态快照）  │
│  应用壳（Rust，src-tauri）                                                     │
│    会话 · 后台任务（收、发、对账）· 传输记录表 · 日程名单                      │
│    通知 · 设置 · 启动入口                                                      │
└──────┼───────────────────────────────────────────────────┼────────────────────┘
       ▼                                                 ▼
  crates/assemble-client ── HTTP 与事件流 ──▶ apps/server（axum + SQLite）
  crates/assemble-transfer ──▶ 文件系统                 账户 · 登录页 · 设备 · 发送 · 云盘 · 日程与提醒
  crates/assemble-device ──▶ 接收目录、右键菜单         blobs/（按摘要存放）
  crates/assemble-store ──▶ 设置文件、系统钥匙串
  crates/assemble-protocol（类型）   assemble-schedule（日程出现规则，两端共用）
```

依赖方向是单向的：应用依赖基础库，基础库不依赖应用；`assemble-protocol` 只依赖 `serde`，位于最底层。规则都在 `crates/` 里，脱离窗口与网络就能测试；应用壳只做编排。

## 各部分职责

| 单元                     | 负责                                                                                                                         | 不负责                   |
| ------------------------ | ---------------------------------------------------------------------------------------------------------------------------- | ------------------------ |
| `assemble-protocol`      | 服务端、桌面端、界面之间全部的类型与纯校验：账户、设备、登录、事件流、发送、云盘、日程、提醒、通知、错误码、服务来源         | 任何 I/O                 |
| `assemble-client`        | 桌面端访问服务端的唯一出口：固定来源、不跟随重定向、凭据头、超时与取消、流式上传下载、事件流的重连、系统浏览器登录的回环回调 | 业务规则                 |
| `assemble-transfer`      | 边读边算的摘要；暂存文件；校验后以硬链接发布，绝不覆盖。服务端与桌面端共用                                                   | 判断目录能不能写         |
| `assemble-device`        | 这台电脑落盘的边界：接收目录、文件名收敛、同名加序号、一次接收的落盘规则、清扫中断留下的暂存文件；右键菜单的参数与注册表     | 网络、窗口               |
| `assemble-store`         | 设置文件的原子私有写入；密钥存储抽象（系统钥匙串 / 内存）                                                                    | 决定存什么               |
| `assemble-schedule`      | 日程出现规则的推算：一条日程在某段时间里出现在哪几场、某个时刻是不是它的一场。服务端的调度与桌面端的名单展开共用它           | 决定什么时候提醒、提醒谁 |
| `apps/server`            | 账户、登录页、桌面授权、设备与在线状态、发送、云盘、日程与提醒的存取和到点调度、定时清理                                     | 文件怎么存到用户的电脑上 |
| `apps/desktop/src-tauri` | 窗口、托盘、生命周期、会话、后台任务、传输记录、日程名单、通知、设置与具名命令                                               | 把规则再写一遍           |

## 服务端

### 启动与配置

没有配置文件，全部来自环境变量（前缀 `ASSEMBLE_`）。没有配置文件、必须显式给出数据目录与对外地址，是因为猜错它们的后果比启动失败更糟。

| 环境变量                     | 说明                                           | 默认             |
| ---------------------------- | ---------------------------------------------- | ---------------- |
| `ASSEMBLE_DATA_DIR`          | 数据放在哪里                                   | 必填             |
| `ASSEMBLE_PUBLIC_ORIGIN`     | 浏览器访问服务端的地址，决定 Cookie 与来源校验 | 必填             |
| `ASSEMBLE_ADDR`              | 监听地址，默认只监听本机、由反向代理转发       | `127.0.0.1:8787` |
| `ASSEMBLE_DRIVE_QUOTA_BYTES` | 每个账户的云盘上限                             | 2 GiB            |
| `ASSEMBLE_SEND_TTL_HOURS`    | 未送达的发送保留多久                           | 24 小时          |
| `ASSEMBLE_SEND_HISTORY_DAYS` | 发送记录保留多久                               | 30 天            |
| `ASSEMBLE_WEB_SESSION_HOURS` | 网页登录状态保留多久                           | 12 小时          |

命令行有 `serve`、`check-config`（只读取配置并连接数据库，报告后退出）、`create-account`（密码从终端读两遍，永不当参数传入）和 `list-accounts`（每行一个用户名；账户只能从命令行建，不开放注册，有哪些账户也只能从这里看）。

### 部署

正式服务在 2026-11-24 上线：<https://as.yxswy.com>，Docker Compose 加 nginx。材料在 `deploy/`；做过的与还没有验证过的见[部署手册](runbooks/deploy.md)。

| 文件                 | 做什么                                                                                                                                                                                                   |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Dockerfile`         | 两阶段：官方 Rust 镜像里编译（版本与 `rust-toolchain.toml` 一致），`debian:bookworm-slim` 里以一个没有登录壳的专用账户运行。服务端在 Linux 上只依赖 C 库（SQLite 静态编入，钥匙串依赖不进 Linux 的构建） |
| `compose.yaml`       | 一个服务。端口只绑在本机的 `127.0.0.1:8787`，交给反向代理；镜像与数据的位置由 `.env` 决定；日志自动轮转                                                                                                  |
| `compose.build.yaml` | 只在本机自己构建镜像时叠加到 `compose.yaml` 上                                                                                                                                                           |
| `.env.example`       | 配置模板：镜像、数据位置、对外地址必填，其余都可以不填                                                                                                                                                   |
| `nginx.conf.example` | TLS 在这里结束。上传上限 110 MB，请求体不缓冲，`/v1/events` 的长连接关掉缓冲、放宽读超时。与正式服务器上的那一份只差域名                                                                                 |
| `push-image.sh`      | 把持续集成构建的镜像经 SSH 送到服务器上。服务器在国内，直接拉 GitHub 的镜像仓库会握手超时                                                                                                                |

服务端不读转发头：在它看来所有请求都来自反向代理。

### 几条规则怎么落地

- **内容按摘要存放、按引用计数。** 云盘文件与待接收的发送都只是指向 `blobs` 的一行引用，磁盘上同一个内容只有一个文件；最后一个引用放掉时才删。上传时边收边核对长度与摘要，不一致就丢。
- **发送只能往前走。** `offered → delivered | declined | cancelled | failed | expired`。到达终态就释放内容；重复的回执是幂等的。
- **定时清理**每分钟一轮：过期的发送被标记并通知两边、太久的发送记录与过期的授权码和登录状态被删除、没人引用的内容与中断的暂存文件被清扫。服务端只有一个实例，这里不需要跨进程协调。
- **正式服务与测试服务走同一段启停代码。** 退出信号先让事件流自行结束，再等在途连接，最多等十秒——计时从收到信号开始，不给服务定寿命。
- **被提前拒绝的上传要先读完再拒绝。** 不然连接会在发送方还在上传时被关掉，它只看到"连不上服务"。
- **日程与提醒只有一份名单。** 没有逐条的推送：`GET /v1/planner` 给出还在进行中的日程与提醒、还没读的通知，任何一处改动都把整份重新算一遍，经事件流推给这个账户的每一台在线设备。
- **同一场只提醒一次。** 通知的主键就是"哪一条日程、哪一场"（提醒是它自己的标识），登记与生成是同一条插入，任务跑重了、服务端重启了都插不进第二条。调度每十秒一轮；离开提醒时刻超过十分钟、或者这一场已经结束的，不再提醒；提醒不管晚了多久都补。
- **改过之后，旧的提醒不再补发。** 取消、完成、删除之后，还没读的通知作废；只改标题、地点、备注的，通知原地换新；改了时间或重复规则的，按新规则不再成立的那几场作废。
- **通知只标已读，不删除。** 一处标了，别的设备在下一份名单里就看不到它。三十天之前的由定时清理删掉。

### 应用壳的模块

| 模块          | 负责                                                                                              |
| ------------- | ------------------------------------------------------------------------------------------------- |
| `state`       | 界面能看到的状态、登录会话的更替、设置；改动只在有变化时才推送给界面                              |

| `registry`    | 传输记录表：收发两个方向、待发送的草稿。它同时是后台任务的队列，不碰网络、文件与窗口              |
| `transfers`   | 后台任务：按先来后到收文件、发文件、补回执，并与服务端对账                                        |
| `send_panel`  | 发送面板这个窗口，以及把交给应用的路径核对成可以发送的文件                                        |
| `launch`      | 发起发送的入口：带着文件启动、另一个实例转交来的参数、拖进窗口的东西                              |
| `send_menu`   | Windows 右键菜单在这台电脑上的状态                                                                |
| `planner`     | 日程名单：展开每条日程七天的场次、决定哪几条通知在这台电脑上弹、点通知时定位、托盘里的"新建提醒…" |
| `notify`      | 系统通知。点文件的通知在访达或资源管理器里定位文件；点日程与提醒的通知，主窗口打开并定位到那一条  |
| `commands`    | 界面能调用的具名命令；错误只带稳定错误码                                                          |
| `tray`、`lib` | 托盘与应用生命周期；退出时显式地结束后台任务                                                      |

### 界面有两个窗口

主窗口是账户、设备、传输、日程、云盘与本机设置；发送面板是"挑好的文件 + 去处"的小窗口，由 Rust 在需要时创建。它们的能力清单完全一样，都只有"接收状态事件"一项。

界面能看到的状态由 `apps/desktop/contract/snapshots.json` 钉住：Rust 在测试里把样本读进来再原样写出去，TypeScript 在运行时核对每一个字段。任何一边改了形状，都有一侧的测试失败。

### 一次传输怎么走

一条传输只有一份记录，按方向各走各的路：

```text
收到：排队 ─▶ 正在接收 ─▶ 已保存 ─▶（回执确认）
                  └▶ 接收失败 ─▶（把原因报告上去）
发出：排队 ─▶ 正在发送 ─▶ 等对方接收 ─▶ 对方收下 | 拒收 | 过期
            └▶ 发送失败                  └▶ 已撤回 | 对方接收失败
云盘：排队 ─▶ 正在上传 / 正在取回 ─▶ 完成（存进云盘不欠回执；取回与接收同一条路）
```

- **按先来后到，一次一个。** 收排在发前面，因为对面正等着。同名的文件先后到达时自然得到不同序号。
- **本机效果先落盘再回执。** 回执没送到不算完：与服务端对账时会发现它还在等，再补一次。
- **说不准是谁的问题时不怪任何一方。** 取不到内容只是过一会儿从头再来；报告给对面的只有这台电脑确实写不下来，以及内容与声明的对不上。
- **取消要取消到底。** 上传途中取消、文件却已到了服务端的，对账时按内容摘要、文件名和收件人认出来，在服务端撤回。
- 事件流不补送断线期间的事件，所以每次连上、以及之后每隔五分钟，都向服务端问一遍"还有哪些文件在等我"、"哪些发出去的还悬着"。

### 一条提醒怎么走

日程与提醒都存在服务端。桌面端拿一份名单来显示和操作，自己不排程：

- **整份名单来、整份换。** 连上服务时拉一次，之后每隔五分钟随对账再拉一次（过了零点，"接下来七天"要往前挪），服务端每有一处改动就再推一份；改动之后本机也再拉一次，不依赖事件流一定送到。
- **到点由服务端决定。** 规则见上面服务端的"几条规则怎么落地"。
- **接下来七天的场次在桌面端展开**，用的是和服务端同一个规则库（`assemble-schedule`），所以界面上的时间与实际提醒的时间对得上。
- **这台电脑弹不弹，记在本机。** 名单里带着全部还没读的通知；哪几条已经弹过，记在本机设置的有界账本里（最多两千条）。只补弹最近二十四小时之内生成的，更早的只留在列表里；"本机"卡片里的开关关掉之后只记账、不弹，以后打开也不会把积压的全弹一遍。
- **点了系统通知，主窗口打开并定位到那一条。** 通知的标识只在 Rust 里对得上是哪一条。
- **每一次改动都带着看到的版本号。** 别处改过时服务端拒绝，Rust 换上最新的名单；界面只说"在别的设备上改过，请再看一眼"，并把还留着旧值的表单收起来。新建带一个幂等键，超时重试不会建出两条。
- **界面交给 Rust 的只有标题、时间与几句备注。** 表单里的时间是本地时间，交出去之前换成 UTC。地点只填一个名字：没改就原样留着（导航用的地址还在），改了就只剩新写的那个名字。

## 安全边界

- **界面。** 两个窗口的能力清单都只有 `core:event:allow-listen` 与 `allow-unlisten`。内容安全策略限定脚本与样式只来自应用自身，连接只允许 IPC。对话框、通知、文件定位都只从 Rust 这边用。
- **命令。** 界面能调用的只有这 42 个：`snapshot`、`sign_in`、`cancel_sign_in`、`sign_out`、`launch_at_login`、`set_launch_at_login`、`rename_device`、`remove_device`、`choose_receive_folder`、`reset_receive_folder`、`reveal_received`、`start_send`、`send_to_device`、`send_to_drive`、`close_send_panel`、`open_main`、`cancel_transfer`、`retry_transfer`、`drive_refresh`、`drive_upload`、`drive_download`、`drive_delete`、`set_send_menu`、`dismiss_notice`、`planner_refresh`、`schedule_create`、`schedule_update`、`schedule_complete`、`schedule_cancel`、`schedule_reopen`、`schedule_delete`、`reminder_create`、`reminder_update`、`reminder_dismiss`、`reminder_cancel`、`reminder_delete`、`notifications_read`、`notifications_read_all`、`planner_focus`、`planner_compose`、`set_planner_muted`。命令失败只返回稳定错误码。
- **标识，不是路径。** 界面引用一条传输、一个云盘文件、一台设备、一条日程、一条提醒、一条通知，用的都是标识。文件的位置由系统选择器、右键菜单或拖放直接交给 Rust；状态里有文件名、文件夹名，没有路径。
- **凭据。** 设备令牌存在系统钥匙串里，条目名按服务来源区分；令牌、Cookie 与密码不进界面、日志、命令返回值与状态。
- **联网。** 客户端只访问构建时确定的那个来源，不跟随重定向；标识符与路径在拼进请求之前先校验。
- **文件。** 接收目录只能来自默认位置或系统选择器，必须是真实的目录、不能是整块磁盘；文件名来自网络，收敛成单个在 Windows 上也合法的名字。发布之前再确认一次接收目录还是原来那个——下载途中目录被删、被换成链接，文件都不会落到别处。收到的内容按声明的长度与摘要核对，对不上就不出现。通知与"在文件夹中显示"只选中文件，不打开它。

## 数据放在哪里

| 内容               | 位置                                                    | 说明                                                                       |
| ------------------ | ------------------------------------------------------- | -------------------------------------------------------------------------- |
| 设备会话与账户     | 系统钥匙串，服务名 `assemble.device-session:<服务来源>` | 退出登录时删除                                                             |
| 本机设置           | 应用数据目录下的 `settings.json`                        | 接收位置、右键菜单开关、这台电脑弹不弹提醒、已经弹过哪些通知；不随账户变化 |
| 收到的文件         | "下载/Assemble"，或用户选的文件夹                       | 只在 Rust 里记着完整位置                                                   |
| 服务端的数据       | 数据目录下的 `assemble.sqlite3` 与 `blobs/`             | 结构只经迁移脚本改动                                                       |
| 设备令牌（服务端） | 数据库里只存摘要                                        | 密码只以 argon2id 散列保存                                                 |
| Windows 右键菜单   | `HKCU\Software\Classes\*\shell\AssembleSend`            | 指向这个可执行文件，不需要管理员权限                                       |

传输记录只在内存里：应用重启后名单清空，已经落盘的文件留在接收位置。

## 已知的限制

- **真实验证只做到一半。** 服务端、替身设备与桌面端的启动是真实跑过的，`bun run acceptance` 起环境的那一段也是；但桌面端在应用里一口气走完登录，以及登录之后收发文件、云盘、拖放、发送面板，都还没有真人在真实运行里做过。这些目前只有对着真实服务端跑的自动化测试。逐条见运行手册。
- **Windows 上从来没有运行过真正的应用。** 代码第一次在 Windows 上编译、检查与测试，是持续集成的 Windows 那一栏跑起来的（2026-11-24）：全部 336 个测试在那边通过，Windows 的安装包也构建成功过。但右键菜单、托盘、通知、开机启动这些只有真机才能回答的事，一件都还没有在 Windows 桌面上试过。
- **收到的文件只有本人可读写。** 暂存文件以 `0600` 建立，发布用的是硬链接，所以落到"下载/Assemble"里的文件也是 `0600`，而浏览器下载的文件一般是 `0644`。在只有一个人用的电脑上没有差别；接收位置如果是和别人共用的文件夹，别人就读不了。Windows 不看这几个权限位。要不要改成跟随系统的默认权限，待定。
- **签名与分发没有做。** 持续集成能打出不带签名的安装包：Windows 的（NSIS 与 MSI）成功过，macOS 的那一份第一次因为 GitHub 的机器容量紧张被取消，要重打。没有签名、公证与自动更新。
- **云盘是平铺的一层。** 没有文件夹；改名只有接口，桌面端没有入口。
- **收到的文件自动收下，不先询问。** 服务端支持拒收，桌面端没有拒收的按钮。
- **单文件 100 MB 以内，不支持文件夹，没有断点续传。** 中断了从头再来。
- **服务端只有一个实例。** 在线状态在内存里，清理也假定只有一个进程在跑。
- **正式服务上还没有人登录用过。** 第一个账户要你自己在服务器上建（密码只能你来设）；登录之后的收发、云盘、通知都还没有对着正式地址做过。
- **日程这一部分在桌面端还没有在真实运行里用过。** 服务端的到点调度与推送对着真实运行的服务端核对过（提醒到点后生成通知并推给在线设备、离线的设备重连后拉名单拿到）；带提前量的日程只有注入时钟的测试。桌面端的名单、系统通知与补弹、托盘里的"新建提醒…"目前只有自动化测试。给助手用的对话入口（`assemble-mcp`）与手机上的提醒还没有做。
- **完成或取消的日程、办完的提醒，界面里看不到。** 服务端留着它们，接口按标识取得到、也能改回进行中；名单只给还在进行中的。界面上没有撤销的入口，所以取消和删除都要先确认。
- **GitHub 的 macOS 机器有时容量紧张。** macOS 那一栏会排很久的队，安装包流程里的 macOS 任务被整个取消过一次；遇到就重新触发。
- **`assemble-store` 的 `scope` 目前没有任何调用方。** 它是分段隔离用的，留着等有按账户分段的数据时用。

## 验证方式

三种证据，不能互相替代：

- **自动化测试**：`bun run verify`。界面 103 个测试，工具脚本 14 个，Rust 378 个（单元测试与服务端、桌面端的集成测试）。其中桌面端有 21 个是对着真实运行的服务端跑整条路：收文件、发文件、撤回、对账、存进云盘、从云盘取回；另有 1 个对着一台只会按剧本应答的服务端，用来制造连接中途断开这些情况。
- **真实启动**：在 macOS 上构建并运行服务端、替身设备与桌面端。主流程用一条 `bun run acceptance`：它起好整套环境，由人登录之后自动核对收发与退出；只要其中一样的时候怎么单独起，见[运行手册](runbooks/verify-macos-launch.md)。
- **真机验收**：Windows 与两台真实设备之间的收发，清单在运行手册末尾。

真实启动抓到过自动化测试没暴露的缺陷——比如服务端启动十秒后自己退出、给离线设备发大文件时发送方只看到"连不上服务"。所以涉及应用壳、服务端或生命周期的改动，要真的把它们跑起来。

仓库是公开的，每次推送由持续集成在 macOS 与 Windows 上各跑一遍 `bun run verify`（`.github/workflows/verify.yml`）。Windows 那一栏是服务端、客户端与桌面应用壳唯一的 Windows 环境：五个基础库之外，它们的 Windows 目标在这台 Mac 上检查不了。2026-11-24 它跑起来的第一天，两个平台加起来抓到了十几处只在那边才有的问题，逐条记在决策 0002 的"从真实启动中学到的"里。
