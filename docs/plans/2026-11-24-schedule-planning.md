- 状态：**第一批的服务端、桌面端与对话入口 `assemble-mcp` 都已写完（对话入口是 2026-11-25），有自动化测试，还没有在真实运行里用过。手机上怎么提醒已定为做原生的 iPhone 应用，还没有做。** 范围与对话式入口见[决策 0003](../decisions/0003-schedule-first-batch-and-conversational-entry.md)。
- 日期：2026-11-24
- 依据：[决策 0002](../decisions/0002-own-server-replaces-jarvis.md) 把日程规划列为两大优先级之一，并约定"规则库已经就绪，等服务端的提醒调度，另出方案"。规则库在 `crates/assemble-schedule`。
- 参考实现：`jarvis` 仓库，只读。本文里关于它的说法都来自读它的代码与文档，逐条标了出处；读不出来的如实写在"没能从代码里确定的"。

## 先说结论

1. jarvis 里没有自动排程：日程主要靠对 Codex 说话、经 MCP 写入，计划和目标也是"Codex 提方案、你批准"。Assemble 也不含模型。你管理日程的方式就是对话，所以**第一批要带上对话入口（一个 MCP 服务）**，让 Codex 和 ZCode 能往 Assemble 里写；桌面应用里手建是备用入口，也要做得比 jarvis 的网页顺手。（这一条原先建议"第一批先不做"，你 2026-11-24 纠正了，见决策 0003。）
2. 建议分两批。**第一批**：日程、提醒、到点通知到每一台在线设备。**第二批**：任务、目标与"今天"。工作时段、计划草案、语音、笔记这些等前面站稳了再说，或者不做。
3. 有几处我建议比 jarvis 做得好：日程可以单独设"提前几分钟提醒"；改期之后不再弹旧的；一处标为已读，其余设备同步；新建带幂等键，超时重试不会建出两条。
4. 规则库的推算与 jarvis 逐项对照过（两万条用例），第一批直接用它，界面显示的时间和实际提醒的时间不会对不上。

### 日程与提醒的规则

- 日程的状态只有三种：未开始、已完成、已取消。**"已完成"是整条日程的**，不能只完成重复日程的某一场。
- 每天的重复是固定 24 小时的间隔，每周是固定 7 天，不跟随当地日历；每月按固定的北京时间日历算，短月钳到月末，之后恢复原日号（1 月 31 日 → 2 月 28 日 → 3 月 31 日）。`apps/api/src/jarvis/schedule-occurrences.ts`
- 结束必须晚于开始，重复截止不能早于开始。
- 没有：按星期几重复、隔周重复、某几场例外、重复 N 次后结束、全天事件、优先级、标签、子任务。

### 提醒怎么到设备上

- 服务端每一秒查一次（`apps/api/src/index.ts:183-197`）：到点的提醒生成一条通知；日程在**每一场开始的那一刻**生成一条通知。**没有提前量**——想提前十分钟，只能另建一条提醒。
- 每一场只通知一次：数据库里记着"这场已经通知过了"。
- 只通知最近的一场，再往前的跳过。服务端停机期间错过的那一场，恢复之后的第一次检查会补上：代码里没有"太晚就不补"的判断，隔了多久都会补。`scheduler.ts:418-452`
- 每台在线设备各弹一次，没有"一处看过、其余静默"。
- 设备离线期间产生的通知，在它重新上线时把未读的全部补发一遍；这台设备以前收到过的不重发。`apps/api/src/jarvis/scheduler.ts:61-101`
- 改了日程之后：取消或完成的，把还没弹的通知作废；只改标题、备注的，未读通知原地更新；改了重复规则的，按新规则不再成立的那几场作废。`scheduler.ts:289-351`
- 桌面端在锁屏、睡眠或临时免打扰（30 分钟、1 小时、2 小时）期间先不弹，恢复后再弹。`apps/desktop/src/pet/runtime.ts:85-112`

### 界面上能做什么

- 日常网页（桌面窗口里加载的就是它）：能新建提醒、取消或完成提醒、改任务的状态和计划日、锁定时段、看目标进度和计划草案。**不能新建或编辑日程，不能改提醒的时间，不能新建任务或目标。**
- 新建日程、改期主要靠三条路：对 Codex 说话（经 MCP）、管理端里的通用表格、手机语音。
- 计划只能在 Codex 的对话里批准；网页和手机上都写着"请在 Codex 中查看并决定是否采用"。
- 桌面托盘里有"查看提醒"和"暂停同步 / 恢复同步"；没有全局快捷键。

### 同步与冲突

- 服务端的数据库是唯一的数据源，没有推送：设备长轮询领命令，网页靠手动刷新或每 10 秒轮询。
- 每条记录有一个整数版本号，改的时候带上；对不上就拒绝，提示"资源已更新，请刷新后重试"。
- 任务、目标、计划这些写操作带幂等键，重试不会重复；**日程、提醒的新建没有幂等键**，超时后重试可能建出两条。

### 没有的东西

习惯打卡、贪睡、按条设置提前量、全天事件、邮件或浏览器的网页推送、离线时的写入队列、番茄钟与时间统计、任何报表。

### 没能从代码里确定的

- 目标、计划草案这一套在正式服务上发布了没有。仓库里的文档说法不一（一处写"尚未发布"，另一处写与线上同版发布）。
- 你平时实际上怎么用它：日程主要是对 Codex 说，还是在管理端里手建？任务和目标用得多不多？这决定了第二批该不该做、MCP 这条路要不要留。
- 多台设备同时在线时，每台各弹一次的实际体验如何，仓库里没有记录。

## Assemble 这边打算怎么做

### 第一批：日程、提醒、到点通知

**数据**（服务端，SQLite，经迁移脚本建表）

| 表                  | 存什么                                                                                                                                                                                        |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `schedules`         | 标题、地点（名字与导航地址）、开始与结束（毫秒时间戳）、重复规则与截止、提前几分钟（可空）、状态、备注、版本号                                                                                |
| `reminders`         | 标题、到点时刻、备注、状态、版本号                                                                                                                                                            |
| `notifications`     | 到点后生成的那条通知：来自哪条日程或提醒、哪一场、什么时候生成的、有没有已读、有没有被作废。**主键就是"日程 + 场次时刻"**（提醒是它自己的标识），所以同一场绝不会通知两次，不必另设一张登记表 |
| `planner_mutations` | 新建时带的幂等键：同一个键用过，就拿回原来那一条                                                                                                                                              |

时间在接口里一律是 UTC 的 RFC 3339 字符串，和协议里其余的时间一致（这是做的时候改的：原方案写的是毫秒时间戳）。规则库只留推算部分，进出都是毫秒时间戳。

**接口**（协议类型加在 `assemble-protocol`，服务端处理器只做薄薄一层适配）

- 日程与提醒各一组：列出、新建、修改、删除、完成、取消。
- 通知：列出未读的、标为已读。
- 每次修改带上版本号，对不上返回 409 与一个稳定的错误码，桌面端提示"在别的设备上改过了，已换成最新的"，而不是让人重填。
- 新建可以带一个幂等键：同一个键重试返回原来那一条，不会建出两条。

**服务端怎么调度**

- 一个每十秒醒一次的任务（和现有的定时清理放在一起），每一轮：到点的提醒 → 生成通知；日程到了"该提醒的那一刻"（开始时刻减去提前量）→ 先在这一场登记，登记上了才生成通知。登记与生成在同一个事务里，跑重了也不会通知两次。
- 服务端停机或重启时错过的场次不提醒：离开提醒时刻超过十分钟，或者这一场已经结束，就不再提醒。jarvis 没有这个判断，隔了多久都会补，这是建议改的一处（见下面"需要你定的事"第 6 条）。提醒则相反：不管晚了多久都补——它是一件要做的事，晚到也比不到好。
- 日程被取消、完成、改期之后，还没读的旧通知作废，不再补发给任何设备。
- 生成的通知经事件流推给这个账户**每一台在线的设备**。事件流可能断，所以通知落在数据库里，设备重连之后向服务端要一遍"最近没读过的"，自己在本地记着哪些已经弹过（规则库里那个有界的账本就是干这个的，会存进本机设置）。

**对话入口**（`assemble-mcp`，已写完；十个工具与几条规矩见[架构说明](../architecture.md)的"助手入口"）

- 单独的可执行文件，用 `bun run mcp` 构建，不随桌面应用安装。Codex 和 ZCode 的配置里指向它，就能调这些工具：列出最近的安排；新建日程（标题、开始、结束、提前几分钟、地点、备注）；新建提醒；修改、取消、完成；查最近的安排（也用来回答"我这周有什么安排"）。做的时候另外加上了删除，和把到点的提醒标成已读。
- Assemble 不做理解和排程。"明天 9:00 的火车，几点出门、带身份证"是助手算的；Assemble 负责存下来、到点提醒、把"带身份证"一起弹出来。工具的说明和服务端发来的开场白里写清楚要先看名单（今天几号、时区），时间只收带时区的 ISO 8601。
- 校验在 Assemble 这边，和桌面端走同一套规则；工具的结果里带回冲突（和已有日程撞车），助手可以据此提醒你，但不拦着。不在 Assemble 里做确认流程。
- 每一条都记着是哪台设备写的，界面能看出"这一条是 ZCode 加的"。
- 权限（已定）：让它自己登录一次，成为账户里的一台"设备"（`assemble-mcp login`，走和桌面端一样的浏览器授权），令牌存进系统钥匙串，在设备列表里可以移除。jarvis 是让 MCP 经桌面应用开在本机的入口转发，没有选那条路。

**手机上**：你要日程设好之后 iPhone 上会有提醒。2026-11-25 你定了做原生的 Swift 应用，排在助手入口之后，还没有做；具体方案到那一步再出。

**桌面端**

- 主窗口多一张"日程"卡片：上面是没读的通知，下面是七天之内按时间排好的一份安排（日程与提醒在一起）。新建与编辑是卡片里的一张表单（备用的手建入口），点一下就能完成或取消。做的时候没有做成单独的一页，也没有"今天 / 全部"两个视图：七天之外的和已经结束的，暂时不摆。
- 托盘菜单加"新建提醒…"：主窗口打开，直接摆出新建提醒的表单。做的时候没有另开一个小窗口——那要多一个窗口和一份能力清单，而主窗口本来就登录着。
- 点系统通知，主窗口打开并定位到那一条。
- 桌面端在睡眠或离线时收不到；重新上线后补弹过去一段时间里没弹过的。这一段的宽窄见下面"需要你定的事"。

**和 jarvis 不一样的地方**

| 事项           | jarvis                         | Assemble（建议）                                      |
| -------------- | ------------------------------ | ----------------------------------------------------- |
| 建日程         | 主要靠 Codex、管理端表格、语音 | 同样靠对话（MCP），桌面应用里也能直接建和改           |
| 提前量         | 没有，到点才响                 | 每条日程可以单独设"提前几分钟"，不设就是到点          |
| 改期后的旧通知 | 作废                           | 作废（相同）                                          |
| 停机期间错过的 | 隔了多久都补上                 | 场次超过十分钟或已结束的不提醒；提醒照补              |
| 推送           | 设备长轮询                     | 事件流，已经有了                                      |
| 新建的幂等     | 日程与提醒没有                 | 有                                                    |
| 锁屏与免打扰   | 应用自己压住，恢复后再弹       | 交给系统：macOS 与 Windows 自己会把通知留在通知中心里 |
| 多设备         | 每台在线的各弹一次             | 相同，另加一个"这台电脑不弹日程提醒"的开关（见下）    |

### 第二批：任务、目标与"今天"

- 任务：标题、备注、计划日、截止日、预估分钟数；未完成、已完成、已取消三种状态；逾不逾期是算出来的，不存。**不要求带来源**（jarvis 要求每条任务都出自一段语音或文字）。
- 目标：一层，任务可以归到目标下，进度是条数的计数。
- "今天"：把今天的日程场次、提醒、到期与逾期的任务合成一张单子。
- 任务排进日历（jarvis 的工作时段）放不放，等用一阵子再说。

### 以后再说，或者不做

计划草案（给外部规划器用的"提案—预览—采用"）、语音、笔记、工作陪伴（上下班、喝水、站立、发薪、今日收入）。工作陪伴属于宠物与陪伴那一块，按你定的优先级排在最后。

## 做起来之后和方案不一样的地方

都在上面各自的段落里改过了，这里列个清单：

| 事项             | 方案里写的                   | 实际做的                                                                       |
| ---------------- | ---------------------------- | ------------------------------------------------------------------------------ |
| 场次的登记       | 单独一张 `occurrences` 表    | 通知的主键就是"日程 + 场次时刻"，不必另设一张表                                |
| 接口里的时间     | 毫秒时间戳                   | UTC 的 RFC 3339 字符串，与协议里其余的时间一致                                 |
| 桌面端的"日程"   | 单独一页，有今天、七天、全部 | 主窗口里的一张卡片：没读的通知，加七天之内的安排                               |
| 托盘"新建提醒…"  | 另开一个小窗口               | 主窗口打开并摆出表单                                                           |
| 取消与删除       | 没提                         | 界面上先点一次确认：已完成、已取消的不在名单里，界面上没有撤销的入口           |
| 重复日程的"完成" | 整条完成                     | 同上，所以界面上只有不重复的日程才有"完成"；重复的要停就取消                   |
| 对话入口怎么装   | 随桌面应用一起安装           | 单独的可执行文件，`bun run mcp` 构建；配置片段由 `print-config` 打印，你自己贴 |
| 对话入口的工具   | 查、建、改、取消、完成       | 十个：另加删除，和把到点的提醒标成已读；每个都标明只读、破坏性还是幂等         |
| 对话入口里的时间 | 没提                         | 只收带时区的 ISO 8601；没有时区的拦下，不替助手猜                              |
| 改和删           | 没提                         | 都带版本号；对不上时工具自己取最新的一条，把现状告诉助手                       |
