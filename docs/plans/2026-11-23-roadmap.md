## 现在在哪

已经写完并有测试的：

- 服务端：账户与登录页、桌面授权、设备与在线状态、事件流、发送到设备、云盘、定时清理。

## 接下来

按先后排。前两步不需要再写多少代码，但后面每一步都建立在它们之上。

### 1. 在 macOS 上真实验收一遍

在你自己的终端里运行 `bun run acceptance`（运行手册第 1 节）。它起好本机的服务端、账户和一台叫"工作电脑"的替身设备，构建并启动桌面应用；要你亲手做的只有三件：在应用里登录、往回发一个文件、从菜单栏退出。其余的（发文件过来、核对落盘的摘要与回执、确认退出后离线）由它自动核对并打印结果，大约 15 分钟。主流程之外的不顺利情况（只读的接收文件夹、取消、重发、云盘空间不够）在运行手册第 3 节，有空再逐条试。

完成标准：`bun run acceptance` 的每一项都是 ✓；运行手册"还没有做过的"一节里，属于 macOS 的那几条都被划掉，或者变成写清楚的缺陷。脚本看不见的几样（通知、拖文件夹的提示、云盘、应用挂在后台十几分钟之后窗口是否正常）要你看一眼。

### 2. Windows 真机验收并修到能用

按运行手册末尾的清单走：安装、右键菜单、单实例、开关、拖放、登录与收发、开机启动、退出。

完成标准：清单上的八条都走通。Windows 专用的代码目前只做过类型检查，这一步是它第一次真的运行，预计会有要改的地方。

### 3. 打包、签名与分发

- macOS 的签名与公证；Windows 的安装包与签名。
- 持续集成：每次提交跑 `bun run verify`。
- 自动更新：需要先确认要不要（原来的 Electron 版没有）。

完成标准：一台没装过开发环境的电脑能装上并用第 1 步的全部功能。

### 4. 部署到服务器

要先由你定两件事：域名（DNS 要你本人操作）与方式（Docker Compose 或 systemd）。定下来之前不动服务器。

- 准备 Dockerfile、compose 与反向代理片段（正式服务只接受 HTTPS）。
- 按实际磁盘容量复核云盘配额与保留期。
- 迁移到服务器上之后，两台真实设备之间走一遍收发。

完成标准：两台真实设备（一台 Windows、一台 Mac）对正式地址收发文件成功。

### 5. 日程规划

另出方案。规则库（`assemble-schedule`）已经就绪并有测试，缺的是服务端的提醒调度与推送、读模型和界面。动手之前需要先确认 jarvis 那边日程、任务、目标所依赖的接口是否已发布。

### 6. 补齐文件传输的边角

都不大，排在日程之后或者见缝插针：

- 桌面端的拒收：收到文件时可以选择不收（服务端的接口已经在）。
- 云盘改名在桌面端的入口；要不要文件夹需要你定。
- 断点续传：现在中断了从头再来。
- 传输记录跨重启保留。

## 不在本路线图里

- 局域网直传与大文件分片。你选了服务端中转、单文件 100 MB 以内；要改是另一个决定。
- 迁移 jarvis 的账户与数据。新产品、新数据。
- Windows 11 右键菜单的第一层、访达的右键菜单、网页端、管理端、iOS、小程序。
- 宠物、壁纸。

## 需要你决定的事

1. **什么时候做第 1 步。** 在你的终端里运行 `bun run acceptance`，十几分钟；后面每一步都在等它。
2. **部署的域名与方式**（第 4 步）。
3. **云盘要不要文件夹。** 现在是平铺的一层。
4. **要不要自动更新。**
5. **日程规划什么时候开始**，以及它依赖的接口在 jarvis 那边是否已发布。
