## 排序的理由

1. **设备上线是一切的前提。** 心跳、命令长轮询和目录授权不接通，文件传输无从谈起。
2. **文件传输的底层规则已经写好并测过。** 路径边界、暂存发布、授权与回执账本都在，缺的是把它们串起来的循环和界面。
3. **日程的难点在推算，而推算已经与云端对照过。** 剩下的主要是通知投递与读取模型。
4. **宠物、壁纸依赖独立的窗口与渲染，和前两项没有共用部分。** 放到最后不影响主线。

## 阶段 1：设备上线与目录授权

目标：让这台电脑在云端成为一台可被指派的在线设备，并能安全地共享目录。

- 设备注册：首次连接时创建 `devices` 记录并保存编号；换服务或换账户时清除。
- 连接意图：连接、主动脱离、恢复、正常退出下线；意图跨重启保存，主动脱离后不会悄悄恢复。
- 心跳循环：15 秒一次。收到 `409 DEVICE_DISCONNECTED` 就停下，直到用户明确恢复；收到 401 清掉会话。
- 状态落盘：授权账本、回执账本、文件索引、通知去重写入状态文件，按服务来源与账户分段；换号清空。
- 目录授权：系统目录选择器 → 创建云端记录 → 写入本机私有授权。只接受选择器给出的路径；取消不创建任何记录。
- 云端目录与本机授权取交集，在连接时和每次扫描时重算。
- 本机网关补上 `roots.*`、`device.connect`、`device.disconnect`、`config.update`。

完成标准（把 `jarvis` 里对应的测试逐个移植并通过）：

- `packages/jarvis-device/tests/grants.test.ts`：云端记录与远程改路径都不能授权本机；`roots.add` 与 `roots.update` 拒绝直接传路径；换账户清空授权；确认选择器之后才写授权；取消返回 `{ cancelled: true }`。
- `packages/jarvis-device/tests/runtime.test.ts` 第 188 条：登记过的设备编号跨重启保留；主动脱离后保持停止。
- `packages/jarvis-device/tests/review-regressions.test.ts` 第 188、264 条：远端脱离会中止后台工作并跨重启保持；同账户重新登录保留目录，换账户清空。
- `apps/desktop/tests/runtime-connection.test.ts`：未激活的设备可以重试首次心跳；脱离之后不自动恢复。

## 阶段 2：文件传输

目标：与 Electron 版功能对齐，并把调研中发现的几处低效一并解决。

- 命令循环：长轮询 20 秒、请求预算 30 秒、两轮之间间隔 250 毫秒。领取 → 上报 `running` → 执行 → **先把回执落盘** → 终态回执；每轮之后对账。
- 上传命令：流式读取；与命令给的摘要不一致时报告 `SOURCE_CHANGED`；上传后核对云端摘要。
- 取文件：本机 → 云副本 → 其它在线设备。云副本流式写入暂存、校验、发布；发布前再校验一次路径边界。
- 下载命令：只接受不带账户信息的 HTTP(S) 链接；使用独立的匿名传输；进度每 5% 上报一次并续租。
- 扫描：遍历、哈希、库存上报。四处改进——先用修改时间与大小跳过没变的文件；达到上限的文件在哈希之前就跳过；并行哈希；库存按批上报，每批最多 1000 条。
- 传输登记：进行中的传输登记成表，供界面订阅进度；取消与远端脱离会中止在途传输并清掉暂存文件。
- 本机网关补上 `files.*`、`downloads.*`、`resources.*`、`cloud.request`。

完成标准：

- `packages/jarvis-device/tests/runtime.test.ts` 第 210、244、264、309、499、517、629 条：本机优先于云端；远端补传不被当成已取到；不覆盖已存在的不同文件；哈希不符不发布；中止不留 `.part`；脱离会中止在途下载且绝不报告完成；真实下载只在字节校验并发布之后才算完成；不向上游携带凭据。
- `packages/jarvis-device/tests/command-receipts.test.ts` 全部：租约丢失后重发回执而不重复执行；回执跨重启保留；授权失败、迟到的观察与迟到的终态报告不能改动回执；只有明确的 `COMMAND_NOT_FOUND` 才注销回执。
- `apps/api/tests/command-receipt-query.test.ts`、`command-receipt-retention.test.ts` 中属于设备一侧的行为。
- 四处改进各有新增测试：未变的文件不重新哈希；超限文件不哈希；批量上报不超上限；并行结果与串行一致。
- `paths.test.ts` 已移植并通过。

## 阶段 3：日程规划

目标：到点提醒能可靠地送到，并在界面里看得到接下来的安排。

前提：任务、工作时段、目标、计划所依赖的规划与生产力接口，在 `jarvis` 里目前标注为"未发布到正式服务"。提醒与日程走的是早已上线的通用资源接口，不受影响；其余部分要等那边发布之后才能对正式服务联调。

- 通知投递：`notify` 命令 → 去重账本 → 系统通知 → 回执。只有系统确认显示之后才记入去重；等待显示超过 10 秒视为失败，允许云端重发。
- 点击通知：重新核验会话与通知记录，再定位到对应的提醒或通知；已删除或已取消的不打开。
- 读取模型：提醒、日程、任务、工作时段、目标、计划、笔记、每日简报。客户端补上规划与生产力两组接口。
- 界面：今天、日程、任务、目标、计划。
- 原生创建：提醒先做到与网页端一致（可创建、可取消、可完成）。

完成标准：

- `apps/desktop/tests/notifications.test.ts`：显示确认之前保持等待；中止会关掉未显示的通知；失败与超时按失败处理且不带平台细节；失败的通知不进去重账本、可以重试；成功投递的跨重启保留；点击只触发一次。
- `apps/desktop/tests/activation.test.ts` 中关于点击跳转的部分：点击前重新核验；已中止、已删除或失败的点击不跳转。
- 日程推算已与云端原实现对照一致。

需要先确认：日程、任务、目标是否也开放原生创建（现在只能经 Codex、语音和管理端写入）。

## 需要你决定的事

[决策记录里的"待确认"] ../decisions/0001-rust-tauri-desktop.md#待确认 共十项，其中影响最大的三项：

1. **服务端是否完全不动。** 不动的话，桌面端的能力上限就是现有接口。
2. **过渡期未原生实现的功能怎么办。** 默认是继续用原来的 Electron 应用或浏览器。
3. **会话语义。** 退出登录与退出应用时，设备会话是撤销还是保留。我采用的默认比原来保守，但离线时不能退出登录。

另外三项：

4. 日程、任务、目标是否开放原生创建。
5. 是否需要离线可用的本机日程缓存。
6. 现有的 MCP 服务器何时指向 Assemble。在网关只提供部分操作期间，不建议切换。
