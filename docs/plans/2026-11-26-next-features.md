## 所有工作包共用的规矩

### 契约怎么改

改动如果涉及设备之间来回的数据，或者界面上看得到的状态，固定按这个顺序，两侧的测试一起改：

1. `crates/assemble-protocol` 里改类型。只加不删；新字段能缺省就缺省，别让旧数据读不出来。
2. 服务端的处理器，和 `apps/server/tests` 里对着真实服务端的集成测试。
3. `crates/assemble-client` 的方法。
4. 桌面端：`apps/desktop/src-tauri/src/commands.rs` 加具名命令，`apps/desktop/src/lib/bridge.ts` 加桥接和桥接测试，`apps/desktop/contract/snapshots.json` 改样本，`apps/desktop/src/locales` 的中英两份字典都补。
5. 助手入口：`apps/mcp/src/tools.rs` 加工具的输入和实现，`apps/mcp/src/server.rs` 注册，`apps/mcp/tests/stdio.rs` 里那份精确的工具清单同步。
6. 文档：架构说明里对应的那一句、相关的运行手册；改变了边界的另起一份决策，编号接着目录里现有的往后（2026-11-26 晚最大的是 0013，动手前再看一眼）。

### 迁移

编号接着仓库里现有的往后，按合并的先后定，这一份里不要写死编号（2026-11-26 晚已经用到 `0010`；同一天下午计划之外新增的四个占了 `0007` 到 `0010`）。一个工作包一份脚本，只属于它；提交之后不再改（库里记着每个脚本的校验和）。测试都要从空库走一遍。

### 并行时谁动哪些文件

两个会话同时在改的时候，下面这些文件最容易撞。规矩是：**以先推上去的为准，后推的先拉取、在自己的改动上重放，再推**；谁都不强推，也不改写已经公开的历史。

| 文件                                         | 谁会改               | 怎么避免撞车                       |
| -------------------------------------------- | -------------------- | ---------------------------------- |
| `apps/server/src/http.rs`（路由表）          | 几乎每一项           | 每次只加自己的那几行，不改别人的行 |
| `crates/assemble-protocol/src/error.rs`      | A2、C1、C3、D3       | 只在末尾加常量                     |
| `commands.rs`、`bridge.ts`、`snapshots.json` | 所有碰桌面端的项     | 同上；样本只加自己的那几条         |
| `package.json`、`biome.json`                 | 加脚本或排除项的项   | 改完当场跑 `bun run verify`        |
| `docs/architecture.md`、路线图               | 每一项               | 只改和自己相关的那一句             |
| `AGENTS.md`                                  | 只有 B3 会改两条边界 | 动手前先说一声                     |

在同一个目录里另开会话的，先看 `git status` 和远端；要并行就各用各的工作树，并给 Cargo 另指编译目录（`CARGO_TARGET_DIR` 指回主仓库的 `target`，不然磁盘会被第二份编译产物占满）。

### 错误码

新增的错误码放在 `crates/assemble-protocol/src/error.rs`，名字是大写加下划线。旧版应用读到不认识的码时，命令层会把它原样交给界面（`commands.rs` 的 `is_server_code`），界面查不到说法就显示通用失败。所以新码上线不需要先升级所有客户端，但每加一个码都要想一下旧版会把它说成什么。

### 验证的三个证据

每一项都要分开报，不能互相替代：

- 自动化测试：`bun run verify`，本机一次，推上去之后两栏持续集成各一次。
- 真实启动：碰了应用壳、服务端或生命周期的改动，要真的把它们跑起来。Windows 上由做那一项的会话验；macOS 上由我在更新这台 Mac 上的应用时验。桌面端的登录和钥匙串那一段，要人在浏览器里点、在系统的框里点，留给用户。
- 真机验收：两台真实设备之间的事（收发、通知、托盘、开机启动），只有用户的电脑和手机能回答。每一项的验收标准里都单列了这一条。

### 助手入口

新增能力就是新增具名工具：在 `apps/mcp` 里加工具并补测试。工具不接收任何本机路径；令牌只进系统钥匙串；工具的返回值里不出现令牌。工具的说明文字（`server.rs` 的 `INSTRUCTIONS`）现在写着日程、提醒与私人备忘录，能力扩大时一起改。

### A1 管理端：停用与恢复账户

**目标。** 超级管理员在 `/admin/` 的用户详情里点一下就能停用或恢复一个账户，不用登服务器敲命令。

**现状。** `admin::set_suspended`（`apps/server/src/admin.rs`）已经有了：同一个事务里写审计，停用时删掉网页会话。只有命令行 `suspend-account` / `resume-account` 在调它。管理 API 目前全是 GET，并且有一条测试钉着"对 `/v1/admin/users/{id}` 发 POST 得到 405"（`apps/server/tests/admin.rs`）。网页端 `lib/api.ts` 的 `request()` 写死了 GET。

**设计。**

- 协议：`AdminUser` 加 `suspended: bool`。
- 服务端：`POST /v1/admin/users/{id}/suspend` 和 `…/resume`，都返回更新后的 `AdminUser`。放在子路径上，上面那条 405 的测试继续成立。放行条件照 `apps/server/src/media/auth.rs` 里 `writer()` 的做法：管理员、已验证邮箱、恰好一个 `Origin` 且等于正式地址、`x-csrf-token` 等于会话的令牌。把 `writer()` 抽成一个两边共用的提取器，不抄第二份。
- 规则：重复停用或恢复是成功的空操作。**不能停用自己**，否则管理员把自己锁在外面，回 `INVALID_REQUEST`。审计由 `set_suspended` 自己写。
- 网页：`lib/api.ts` 的 `request()` 支持方法、请求体和 `X-CSRF-Token`（令牌在 `/v1/admin/session` 的回应里，影视那边的 `packages/media/src/browser-client.ts` 已经这么用）。用户详情页（`apps/admin/src/components/pages.tsx` 的 `UserDetail`）加"停用账户"和"恢复账户"，点了先出确认框，写明后果：这个账户的所有设备立刻下线，网页登录被拒。名单里显示状态。两种字典都补。
- 命令行那两条留着：网页进不去的时候用。

**测试。** `apps/server/tests/admin.rs`：成功、重复、停用自己、缺 `Origin`、错的令牌、非管理员、停用后设备令牌变成 401、审计里有两行。`apps/admin/src/App.test.tsx`：按钮只在详情里出现，点了先确认，请求的路径和头都对。

**真机验收。** 你在管理端停用一个账户，再用那个账户试一次登录，然后恢复。

**文档。** `docs/runbooks/admin.md`；架构说明"公开的入口"那一条，现在写着"停用账户只在服务器的命令行上做"。

**实施记录（2026-11-26）。** 已增加两个专用 POST、`AdminUser.suspended`、详情确认框和名单状态，中英同步。账户操作与影视写入复用同一 Origin/CSRF 校验函数，各自保留权限提取器；不额外扩展请求体接口。写锁内复查操作者，审计区分操作者与目标，重复操作不重复写审计，审计失败回滚。停用撤销网页会话、拒绝设备请求并结束已有事件流；CLI 保留且心跳复查账户状态。临时数据库的真实 HTTP 测试和 Windows 隔离服务浏览器均验证停用、取消、恢复；默认焦点在取消，成功后名单与弹窗同步更新。未创建正式测试账户，未修改 iOS、推送或迁移。详情见[决策 0010](../decisions/0010-admin-account-operations-and-storage.md)。

### A2 "服务器存储已满"与"云盘空间不够"分开说

**目标。** 服务器的总量到了上限时，桌面端说"服务器满了"，不再说成"云盘空间不够"。

**现状。** 两种情况服务端都回 413 `QUOTA_EXCEEDED`，只有附带的文字不同（`drive.rs`、`sends.rs`）。桌面端 `transfers.rs` 的 `refusal()` 按这个码一律显示"云盘空间不够"。架构说明的已知限制里记着这一条。

**设计。**

- 协议：加一个码 `SERVER_STORAGE_FULL`，状态码仍是 413。
- 服务端：区分是哪一道闸拦下的。账户配额回 `QUOTA_EXCEEDED`，全站总量回 `SERVER_STORAGE_FULL`。`apps/server/src/error.rs` 多一个变体。
- 桌面端：`refusal()` 多一条分支，`TransferFailure` 多一个 `ServerFull`；`commands.rs` 的映射；文案"服务器的存储空间满了，暂时存不下这个文件。"，英文字典同步。`TransferFailure` 是界面看得到的状态，样本要加。
- 旧版应用读到没见过的码、状态是 413 时，会落进"超过单文件上限"那条分支：说法不对，但不会坏。这一项可以单独上线。

**测试。** 服务端两条路各一条集成测试（把预算调到刚够，再传一个）；桌面端 `refusal()` 的单元测试、文案、样本。

**真机验收。** 没法在正式服务上真的把存储填满，以集成测试为准；上线后等它自然发生。

**文档。** 架构说明已知限制里删掉这一条。

### A3 传输记录跨重启保留

**目标。** 重启应用之后，"文件传输"里原来的记录还在，已收到的文件还能"打开"和"在文件夹中显示"。

**现状。** `Registry`（`apps/desktop/src-tauri/src/registry.rs`）只在内存里，最多 100 条，重启就空了，落盘的路径也跟着丢了。只有对方发来、还没收的会经 `resync` 回来（每五分钟一次）。

**设计。**

- 规则留在 `registry.rs`，它不碰网络、文件和窗口：加一对纯函数，把记录写成可保存的样子、再读回来。
- 持久化由应用壳做（`state.rs`、`transfers.rs`）：每次记录变化后，用 `assemble-store::json` 里现成的"仅本人可读写、原子替换"写进应用数据目录的 `transfers.json`。Windows 上替换文件不是原子的，是踩过的坑（决策 0002 第 21 条），所以只用那个现成的函数。
- 存什么：标识、方向、对方的名字、文件名、大小、阶段、失败原因、时间、落盘后的完整路径。完整路径只在这份本机文件里，不进界面，界面用标识。
- 读回来：已完成和已失败的照旧显示，"打开""在文件夹中显示"又能用了。没完成的（排队、进行中、等对方接收）一律标成"中断"。对方还没收的由 `resync` 接手，按服务端的发送标识去重。草稿不恢复，文件可能已经变了。
- 退出登录时清空这份文件，记录跟着账户走，和现在内存里的行为一致。上限仍是 100 条。
- 退出时的清理显式地做。

**测试。** `registry.rs` 的读写和"中断"的映射；`transfers/tests.rs` 里重建一次应用状态之后名单还在。

**真机验收。** 传一个文件，从托盘退出，再打开，记录还在，"在文件夹中显示"能定位到文件。

**文档。** 架构说明里"传输记录只在内存里"那一句。

### A4 云盘改名

**目标。** 云盘里给一个文件改名。

**现状。** 服务端 `PATCH /v1/drive/files/{id}` 和客户端的 `drive_rename` 都有，桌面端没有命令和入口。

**设计。** 具名命令 `drive_rename`，只收文件标识和新名字。云盘的每一行多一个"重命名"。校验和服务端同一条规则（`clean_file_name`：不能为空，不能带 `/` 和 `\`）。成功后刷新名单。云盘本来允许同名，所以重名不算错。错误只有两种：`NOT_FOUND`（别处已经删了）和 `INVALID_REQUEST`。

**测试。** 桥接测试、界面测试、两种字典。

**真机验收。** 改一个名字，另一台电脑刷新后看到新的。

**文档。** 架构说明里"云盘是平铺的一层"那一条。

### A5 拒收

**目标。** 收到文件时可以选择不收，发送方看到"对方拒收了"。

**现状。** 收到的文件自动收下、不先问。服务端有 `POST /v1/sends/{id}/decline`，客户端有 `send_decline`，桌面端从不调，只有测试在用。下载途中取消是按"失败"上报的。

**设计。** 默认行为不变，加一个每台电脑自己的开关"收到文件先问一声"（`settings.json` 里加 `ask_before_receive`，默认关，和"这台电脑不弹提醒"是同一类设置）。开着的时候：

- 对方发来时不动手下载，记录进一个新的阶段 `Awaiting`（"等你确认"）。系统通知照常弹，文字提示到 Assemble 里确认。
- 点"接收"走原来的路。点"拒收"调 `send_decline`，记录进 `Declined`，对方那边显示"对方拒收了"。这个阶段和文案都已经有了。
- 对方撤回或者过了时限（服务端默认 24 小时），照旧变成 `Cancelled` 或 `Expired`。
- 把开关关掉时，还在等确认的立刻按自动收下处理。
- 重启后等确认的由 `resync` 拿回来。
- 下载途中取消仍然按"失败"上报，不改，那是另一件事。

`Awaiting` 是新的阶段，样本要加；`is_active()` 这些按阶段判断的地方都要看一遍。

**测试。** `registry.rs`：等确认之后接收、拒收、撤回、过期、关开关。`transfers/tests.rs` 对着真实服务端：拒收之后发送方收到 `declined`。界面测试两种按钮。桥接测试。

**真机验收。** 一台电脑打开开关，另一台发一个文件，点"拒收"，发送方看到"对方拒收了"。

**文档。** 决策 0002 假设表里"自动收下"那一条补一句；架构说明里对应的那一条。

### B1 服务端：手机当一台设备

**目标。** 一台 iPhone 能作为账户里的一台设备登录，并且不让旧版桌面应用出问题。

**现状，和两个坑。**

- 登录的回调只认 `http://127.0.0.1:<端口>/callback`（`crates/assemble-protocol/src/login.rs` 的 `is_desktop_redirect_uri`）。手机给不出一个回环地址上的监听。
- 设备的平台是一个封闭的枚举，只有 Windows、macOS、Linux（`primitives.rs` 的 `Platform`）。旧版桌面应用读到不认识的值，设备列表就再也不能解码：它不会被登出，但名单不再更新，发送面板里的目标也跟着不更新。
- **服务端必须先升级。** 现在的服务端读到库里不认识的平台会回 500：那个账户的 `/v1/devices`、`/v1/me` 和管理端的设备列表一起坏掉，事件流被掐断。

**设计。**

1. 平台。`Platform` 加 `Iphone`，再加一个兜底的 `Other`（`#[serde(other)]`）。兜底是给以后用的：从这一版起的应用，读到没见过的平台不会再读不了设备列表，服务端也不会再因为它回 500。一起改的地方：服务端的 `platform_from`、`register`、`platform_label`（中英两种说法）；桌面端的 `types.ts`、`guard.ts`、`App.tsx`、`SendPanel.tsx`；管理端的 `api.ts` 和字典（它早就有 `"other"`，只是服务端从来没有过）。
2. 回调。多认一个固定的值 `assemble://auth/callback`，在协议里定成常量，不接受别的路径和查询串。`callback_origin()` 对它返回 `assemble://auth`，授权页的 `form-action` 跟着带上。授权页上"以设备某某登录"的那一行按平台显示，多一种"iPhone 上的 Assemble"。**开工时先核实**：在真实的浏览器里，表单提交之后跳转到自定义的地址，授权页的 `form-action` 放不放行。2026-11-25 就是栽在这一条策略上的（决策 0002 第 24 条）。
3. 第一期手机不能收文件。服务端拒绝以 iPhone 为目标的发送（`INVALID_REQUEST`）；新版桌面端的发送面板不把它列成目标，旁边一句"手机第一期还不能收文件"。
4. 手机不开事件流（原因见 B3），所以它在设备名单里总是离线；协议里的 `lastSeenAt` 是它最近一次离线的时间。
5. 令牌和桌面端一样不过期。手机丢了，在桌面端的"设备"里移除它。

**顺序，不能乱。**

1. B1 合并，部署到正式服务。
2. 两台电脑都更新到带 B1 的应用。
3. 然后才能有手机登录。

**测试。** 协议的单元测试（新回调、兜底的变体、旧样本仍然能读）。`apps/server/tests/desktop_login.rs`：用新回调走完授权和换码，别的自定义地址被拒。设备和发送的测试：iPhone 登记成功，发给 iPhone 被拒，库里出现不认识的平台时接口不再 500。桌面端 `guard` 和标签的测试。样本。

**真实启动。** 授权页改了表单的跳转目标，要在真实的浏览器里走一遍（运行手册第 2 节有替身的做法）。

**文档。** 架构说明里的设备平台；运行手册里的升级顺序；新决策 `iphone-client`（编号到时候接着目录里现有的往后）：手机是一等客户端，第一期的范围，两条边界在手机上怎么算（见"需要你决定的事"第 1 条）。

**实施记录（2026-11-26）。** 提交 `d8f0e4f`，决策写在[0014](../decisions/0014-iphone-client.md)。第 2 条（回调）没有做：它属于"系统提供的网页登录会话"那一条路，等你答复（见"需要你决定的事"第 1 条）。其余照设计做了。做起来和设计不一样的地方：兜底的 `other` 顺带让服务端读库里不认识的值时不再回 500（原来只想到旧版应用读不了名单）；桌面端的平台显示名挪进了 `i18n.ts`，认不出的那一种走字典。没有另做真实浏览器的一遍：授权页只是多显示一种平台的名字，表单和跳转都没变。正式服务 2026-11-27 01:32 升级到 `c79edf0` 时已经带上了这一半（另一个会话部署的，记录在部署手册）；两台电脑更新应用还没有发生。2026-11-27 平台的值从 `iphone` 改成 `ios`：用户纠正目录名之后，线上的值也按操作系统命名对齐；那时还没有手机登录过，库里没有旧值。正式服务为此再升一次。

### B2 服务端：扫码登录

**目标。** 电脑上的网页已经登录着的时候，手机扫一下就成为一台设备，不用在手机上输密码。手机旁边没有电脑时，走 B1 的回调，在系统的网页登录会话里用邮箱密码或 GitHub 登录。

**设计。** 照 jarvis 走通过的路子，存进库里而不是内存里。

- 网页：账户页 `/web/account` 加一块"添加手机"。`POST /web/pairing` 建一次配对，页面上显示二维码和一个"取消"。二维码由服务端生成，内联成 `<svg>`：页面不放宽内容安全策略，也不用脚本。载荷是 `assemble://pair?ticket=<43 位随机串>`，库里只存它的散列。
- 手机：扫到之后 `POST /v1/pairing/claim`，带上票据和 PKCE 的挑战。得到账户名和一个六位的确认码，显示在屏幕上。然后每两秒 `POST /v1/pairing/complete` 一次，带上 PKCE 的验证串，等结果。验证串从头到尾只在手机上。
- 网页：配对被认领之后显示同一个六位码。页面用 `<meta http-equiv="refresh">` 自己刷新，两秒一次，认领之后停。本人核对是同一串之后点"允许"（`POST /web/pairing/{id}/approve`，同源加 CSRF），或者"拒绝"。**令牌只在"允许"之后发给手机，网页从头到尾不接触它。**
- 库：新表 `device_pairings`，字段是码的散列、账户、PKCE 的挑战、确认码、状态（已认领、已允许、已拒绝、已用掉）、到期时间、用掉的时间。三分钟内没走完就作废，由维护任务清理。每个账户同时最多五次。
- 两个 `/v1` 接口谁都能调，按来源限速，沿用 `Source` 那一套。错误码沿用 `INVALID_AUTH_CODE` 和 `TOO_MANY_ATTEMPTS`。
- 审计：成功时和桌面登录一样记一条"已注册设备"。
- 二维码的生成要引入一个纯 Rust 的依赖。选版本时看 crates.io 的接口，`cargo info` 会把预发布版本排在最前。

**测试。** `apps/server/tests/`：整条配对；错的验证串；没有点允许就拿不到令牌；过期；重复使用；网页会话中途失效；限速。账户页和授权页在真实的浏览器里走一遍。

**真机验收。** 你的 iPhone 扫电脑上的码，核对六位数字，点允许，手机登录成功，桌面端的"设备"里多出这台手机。

**文档。** 架构说明里登录的一节；`docs/runbooks/browser-identity-ui.md`。

**实施记录（2026-11-26）。** 照设计做了。做起来和设计不一样的地方：

- 问结果的接口叫 `POST /v1/pairing/finish`，回应是一个带 `state` 的对象（`pending`、`complete`、`denied`）；"被拒绝"是正常的回应，不是错误。
- 认领时手机不拿到账户名，只拿到确认码和到期时间：拍下二维码的人拿账户名没用，不给。
- 配对是单独的一页 `/web/pairing`，账户页上只放一个入口；网页上做决定的接口是 `POST /web/pairing/{id}`（`allow`、`deny`，还没被认领时另有 `cancel`）。

设计里没写到、做的时候补上的：库里只存票据的摘要，可页面每两秒刷新一次要重画二维码，所以还没被认领的票据另在服务进程的内存里留三分钟（服务端在那之内重启，这一张就作废）；页面上同时给出二维码编码的那一串地址，扫不了码的人可以粘贴，模拟器里的手机应用也靠它；拿错的校验器试过一次，票据就作废。迁移是 `0011_device_pairings.sql`，二维码用的是 `qrcodegen 1.8.0`（只有算法，没有别的依赖）。

测试：协议的类型，服务端的单元测试，十二条对着真实服务的集成测试。真实浏览器里整条路走过一遍，做法和结果在运行手册 `browser-identity-ui.md`。自动化测试里没有"限速"的一条：测试起的服务端没有配置可信的代理头，来源未知时不限速，这一条只有单元测试。留给你的：真机上用摄像头扫。正式服务已随 `c79edf0` 上线（2026-11-27 01:32）。

### B3 iOS 应用

只在 Mac 上做。开工前要你先答复"需要你决定的事"的第 1 到 3 条。

**目标（第一期）。** 手机上看日程和提醒，到点响；点通知定位到那一条；扫电脑上的码登录；碰一下 NFC 标签唤起应用做一件事。

**范围。** 日程与提醒的名单；提前排好的本地通知；标已读、"看过了"、完成日程；退出登录；能在桌面端的"设备"里被移除。**不做**：收发文件、云盘、影视、远程推送、后台刷新。

**怎么写。**

- 位置：`apps/ios/`。两个目标：`AssembleCore`（模型、接口、通知的规划，不依赖界面，`swift test` 在 Mac 上直接跑）和应用本身（SwiftUI）。工程文件用 XcodeGen 从 `project.yml` 生成，`*.xcodeproj` 不进仓库，和 jarvis 的做法一样。这个目录不进 Cargo 工作区，`bun run verify` 在 Windows 上不碰它；持续集成加一栏 macOS 专跑它的测试。
- 模型：手写的 `Codable`，对着 `assemble-protocol`。为了两边不同步走样，Rust 这边加一条测试，把关键的类型序列化成 JSON 样本提交到 `apps/ios/Fixtures/`：名单、日程、提醒、通知、设备、账户、换码的回应、错误的形状。Swift 的测试必须能把它们解码出来。协议一改，Rust 那条测试先红；样本更新之后，Swift 的测试再守一道。
- 接口层：`URLSession`，临时配置，不带 Cookie、不存凭据、不缓存；不跟随重定向，令牌不会被带到别的站点；15 秒超时；回应有大小上限；`Authorization: Bearer`；错误按 `{error:{code,message}}` 读。服务地址在构建时定下，和桌面端同一条规矩，应用里没有可以填地址的地方。
- 令牌：只进系统钥匙串，通用密码项，`AfterFirstUnlockThisDeviceOnly`，服务名和桌面端一样按服务地址区分。界面和日志里不出现。
- 同步：不开事件流。原因有两个：事件流一断一连就会向这个账户的每台设备广播一次"设备变了"，手机频繁进出前台会把这个账户的其它设备刷个不停；而第一期只需要拉名单。启动、回到前台、前台中每三十秒、下拉刷新时各拉一次 `GET /v1/planner`，重叠的请求合并。每次都拿回完整的名单，不做增量。
- 本地通知：一份纯逻辑的"通知规划"，把日程按重复规则和提前量展开，加上提醒，取今后三十天里最近的六十条（系统上限是 64 条待发）。标识用服务端通知的标识：提醒是 `n-<提醒标识>`，日程是 `<日程标识>-<场次的毫秒>`。这个构成现在只写在服务端的代码里，要写进协议的注释，并由测试钉住。这样本地排好的通知和以后从名单里读到的"没读的通知"是同一个标识，不会响两遍。触发用固定 UTC 日历的 `UNCalendarNotificationTrigger`，和手机的时区、夏令时无关。每次同步之后对一遍：没变的不动，新的加，过时的删，失败就整批回退。离线了一阵之后，把名单里 24 小时内、本机没弹过的没读通知补弹一次，和桌面端同一条规矩。权限在用户打开"提醒"开关的时候才申请。
- 界面：今天与近七天；详情（备注、地点）；账户（账户名、这台手机的名字、提醒开关、退出登录）；登录（扫码，或者用浏览器登录）。
- NFC：后台读 NDEF 标签，地址形如 `assemble://nfc/<名字>`。一个标签对应哪个动作记在手机本地，第一期只有"新建提醒"和"打开 Assemble"。**开工时先核实**：免费账户能不能开 NFC 读取能力。
- 构建与安装：这台 Mac 有 Xcode 26.6、XcodeGen 和 iOS 26.5 的模拟器。免费账户签出来的安装七天要重装一次；买了开发者账户之后改走 TestFlight（路线图第 3 步）。

**测试。** `AssembleCore` 的单元测试：时间解析、通知的规划与对账、样本解码、错误的映射。应用层的测试：登录流程对着一个假的接口走一遍，退出之后钥匙串和通知都清掉。界面测试一条，从名单进到详情。

**真机验收。** 只有你的 iPhone 能回答：到点响不响，扫码顺不顺，碰标签唤不唤得起，锁屏和飞行模式下表现如何。清单写进运行手册。

**文档。** `apps/ios/README.md`：怎么生成工程、怎么装到手机、免费账户的限制。`AGENTS.md` 里"凭据"和"登录"两条边界补上手机上怎么算。运行手册加一份 iOS 清单。

**实施记录（2026-11-27）。** 第一期照设计做了，位置 `apps/ios`。做起来和设计不一样的地方：

- NFC 标签那一条没有做，也没有核实免费账户能不能开读取能力：要真机到手才谈得上，留给真机之后。
- 登录只有扫码，外加"粘贴配对地址"这一条给没有摄像头的设备和模拟器；没有"用浏览器登录"，那属于"需要你决定的事"第 1 条。
- 排进系统的通知用的是从排的那一刻起算的时间间隔，不是设计里写的固定 UTC 日历触发：时刻同样和时区、夏令时无关，代码更短。手机改了系统时间的话，那一批要等下一次同步才纠正。
- 名单是"没读的通知""日程""提醒"三段，不是设计里的"今天与近七天"；日程只列近七天里有场次的，提醒列还没到点和过了点还没办完的。
- 目录叫 `apps/ios`，不叫 `apps/iphone`：按操作系统命名，将来的安卓版是 `apps/android`。用户 2026-11-27 纠正的；脚本目录、命令、样本测试和文档一起改了名。
- 设计里没写、做的时候补上的：办完一条，它到点的通知跟着算看过（包括服务端晚一步才生成的那一条）；"看过了"碰上服务端刚把提醒标成到点（版本号加一）时，照新的版本号再交一次；应用是被点开的那一下才启动的，名单读出来之后再定位；账户页上"打开设置"；一个占位的图标（和桌面端同一个字母点阵，根目录 `bun run icons` 顺带生成）。

## 第三波：助手与本机

### C1 助手发起下载

**目标。** 对助手说"帮我把这个视频下了"，下载在你自己的电脑上跑，任务出现在桌面应用"网络文件下载"的名单里。

**现状。** 浏览器扩展经本机的桥接程序找到桌面应用在回环地址上的监听（随机端口，端口和令牌在钥匙串里）。桥接程序先做一次挑战应答，确认对面是本应用；监听拒绝一切 `Origin`；同一个请求标识十分钟内只算一次。然后应用自己解析、下载。`assemble_download::browser::send` 是公开的，但 `apps/mcp` 现在不依赖这个 crate。[网络下载的方案](2026-11-25-network-downloads.md)里留过一句话：助手发起下载时要先定一个"本机任务协调"，不能让两个进程各自改同一份任务文件。

**设计。** 复用这条本机通道，**桌面应用始终是下载任务唯一的主人**。

- 协议：`BrowserDownload` 加一个可缺省的 `via: "assistant"`，浏览器扩展不带它。桥接多两条路由：`GET /v1/downloads/{id}` 看一条任务，`POST /v1/downloads/{id}/cancel` 取消。`/v1/download` 原来是"解析并直接开始"，对助手拆成两步：第一次带 `via` 的请求返回预览（标题、时长、可选的清晰度），第二次请求选定之后再开始。浏览器那条路不变。
- 桌面应用：`settings.json` 加"允许助手让这台电脑下载"，默认开着。关着的时候，带 `via: "assistant"` 的请求回一个稳定的错误码。任务上标"由助手发起"。
- 助手入口三个具名工具。`assemble_download_preview`：输入来源的种类和地址，返回标题、时长和清晰度列表，只读。`assemble_download_start`：选定清晰度开始，返回任务标识。`assemble_download_status`：返回阶段、进度和错误，完成之后带文件名。三个都不收任何本机路径，存到哪儿由桌面应用自己的设置决定。
- 桌面应用没有在运行的时候，工具如实说"Assemble 桌面应用没有在运行"，不替用户启动它。
- 说明文字和 `tests/stdio.rs` 里那份精确的工具清单一起改。
- 提示词注入：助手可能被网页的内容骗去下不该下的东西。已有的闸都还在，只连公网地址、只走 80 和 443、不代理、并发和大小有上限、磁盘余量不够不开始；再加上面那个开关和名单上的标记。

**测试。** 桥接：带 `via` 的两步、开关关着、状态和取消。`apps/mcp/tests` 对着一个假的桥接服务把三个工具各走一遍，包括应用没在运行、开关关着、任务失败。界面测试"由助手发起"。

**真机验收。** 在 Windows 和这台 Mac 上各对助手说一句话，下载开始，文件落盘，能播放。

**文档。** `docs/runbooks/network-downloads.md`；架构说明里"助手"那一条；记一份决策：助手的能力从日程扩大到下载。

### C2 存储监控

**目标。** 一眼看到服务器存了多少、还剩多少，快满之前就知道。

**现状。** 全站的内容用量、磁盘余量、数据库的大小，哪里都不报。`check-config` 只报账户数，管理端的概况只有用户数和设备数。

**设计。**

- 服务端新模块 `apps/server/src/storage.rs`。`report()` 算出内容总量（`SUM(blobs.size)`，和预算同一个口径）、数据库文件的大小（影视的图片在里面）、数据目录所在磁盘的余量、预算、用量最大的前十个账户。磁盘余量用 `fs4`，工作区里已经有这个依赖。
- 两个出口：管理端的 `GET /v1/admin/overview` 多一个 `storage` 对象；`check-config` 多打这几行，升级之后照例看它的时候就有了用量。
- 告警：预算用到八成，或者余量低于 2 GiB 的时候，维护任务里打一条警告日志，一小时最多一条；管理端的概况页顶上一条提示。不发邮件，服务器上没有管理员的邮箱配置，D1 做好之后可以并进去。
- 阈值做成配置：`ASSEMBLE_STORAGE_WARN_PERCENT`，默认 80。正式服务的值由我在部署时写进受保护的配置。
- 管理端网页：概况页加一张"存储"卡片，已用和预算的条、磁盘余量、前十个账户。

**测试。** `storage.rs` 的单元测试，在临时目录里放几个文件算总量和余量；管理接口的集成测试；`config_report` 的测试；网页卡片的测试。

**真机验收。** 部署之后在管理端看到数字，和服务器的 `df`、`du` 对得上。

**文档。** 部署手册：去哪里看用量，多少的时候该扩盘；管理端手册。

**实施记录（2026-11-26）。** `storage::report` 已接入概览、自检和维护日志，包含内容预算、SQLite 主文件/WAL/SHM、数据卷余量与按账户去重的前十用量。空测量返回 null；默认 80% 和 2 GiB 预警，日志以单调时钟每进程一小时最多一次。单元和真实 HTTP 测试覆盖重复/跨账户引用、未清理内容、停用数据保留、前十稳定排序、配置边界和空值；浏览器核对了隔离数据目录中的实际 80 KiB 内容、100 KiB 预算、预警与中英文切换。正式服务器 `df` 与数据库文件长度的对照留待部署后验收，本轮未连接正式数据库或改变服务器配置。

### C3 断点续传

**目标。** 一个大文件传到一半断了，接着传，不从头再来。单文件 100 MB 的上限不变。

**现状。** 上传是一个请求把整个文件发完：元数据在查询串里，正文是原始字节，服务端一路流式写进暂存，末尾核对长度和摘要。断了就从头再来。下载这一边服务端已经支持 `Range`，客户端没有用。

**设计。** 顺序续传就够，不做分片并行。

- 新表 `uploads`：标识、账户、发起的设备、种类（发送或者云盘）、目标、名字、大小、摘要、MIME、已经收到的字节数、建立和最后活动的时间。暂存文件放在数据目录下自己的 `uploads/` 里。
- `POST /v1/uploads`：声明元数据，返回标识和到期时间。粗查配额和预算，**并且把没传完的也计入预算**，否则几个并行上传能一起把总量撑爆。
- `PUT /v1/uploads/{id}`：带 `Content-Range: bytes N-M/total`，N 必须等于已经收到的字节数，否则回 409 并告知现在收到了多少。
- `GET /v1/uploads/{id}`：断了之后问一句收到哪儿了。
- `POST /v1/uploads/{id}/complete`：核对整份的长度和摘要，发布成 blob，生成发送或者云盘文件，返回 `Send` 或者 `DriveFile`。
- `DELETE /v1/uploads/{id}`：放弃。
- 只有发起的那台设备能续传和完成。维护任务清理 24 小时没有动静的上传。
- 客户端：上传在网络错误之后先问收到多少，从那里接着发。接收这一边留下暂存文件，重试的时候带 `Range`。
- 旧的两个上传接口留着不动，旧版应用照常能用。"收到的内容不信任"不变：摘要在声明的时候就定死，完成时核对整份。

**测试。** 服务端的集成测试：传一半断开再续；摘要不符不发布；别的设备来续传被拒；过期清理；预算把没传完的算进去。桌面的传输测试对着真实服务端中断一次。

**真机验收。** 在网络不稳的时候传一个几十 MB 的文件，中途关掉再打开应用或者断网几秒，最后传完，摘要一致。

**文档。** 架构说明里"中断了从头再来"那一条；部署手册里反向代理的超时。

## 第四波：要你先说一句话

三项的设计都写到了能开工的程度，但各有一个只有你能回答的问题（见文末"需要你决定的事"）。答复之后放进第一波到第三波的队列里。

### D1 邮箱简报

**目标。** 每天固定时间给账户的邮箱发一封信：今天的安排、没读的通知、昨天收发了什么。

**设计。** 先由规则拼，服务端不含模型；要不要让助手来写，以后再定。

- 设置跟着账户：要不要发、几点发、用哪个时区（IANA 的名字，网页按浏览器的时区预填）。入口有两个：网页的账户页，和助手的两个工具（`assemble_digest_get`、`assemble_digest_set`），这样你可以直接说"每天早上七点给我发简报"。
- 新表 `digest_log`：账户、当地的那一天、发出的时间，两者合起来是主键。重启、重复的滴答都不会发第二封。
- 调度：一个周期任务，每一分钟看一次，写法和 `maintenance::start` 一样，时钟可以注入。到了当地时间的账户就拼信、发信、记一行。换算当地时间要一个带时区库的依赖，现在的 `chrono` 没有开时区的功能；选哪个、哪个版本是稳定的，开工时看 crates.io 的接口再定。
- 内容是纯文本：今天的日程和提醒；明天要出发的；没读的通知；昨天收到和发出的文件（名字和数量）；以后加上逾期的任务。
- 发信走现成的 `Mailer`。不走验证邮件那套防滥用的限额，自己有一道：每个账户一天一封，每一轮最多发两百封。只发给验证过的邮箱。发失败了下一轮再试，当天过去了就不再补。

**测试。** 规划的单元测试（拨时钟、跨时区、月末）；集成测试（只发一次、停用的账户不发、邮箱没验证的不发）；两个工具对着真实服务端。

**真机验收。** 你给自己开一个两分钟后的时间，收到信。

### D2 云盘文件版本

**目标。** 云盘里的一个文件可以有几个版本，能看、能取回旧的、能把旧的恢复成当前的。

**设计。**

- 新表 `drive_versions`：版本、所属的文件、内容的摘要、大小、上传的时间、是哪台设备传的、备注。`drive_files` 多一列"当前的版本"，迁移时每个已有的文件生成它的第一个版本。每个版本各自保住自己那份内容的引用计数，删文件时一起放掉。
- 接口：列出版本；上传一个新版本（走现在的上传协议，多带一个文件标识；配额按所有版本的字节算）；取回某个版本；把某个版本恢复成当前的（不上传，只改指向）。
- 多少算满：每个文件最多二十个版本，到了就拒绝，不自动删最旧的。
- 桌面端：文件那一行多一个"版本"，里面是列表和三个动作。
- **要你定的（第 6 条）**：只在明确点"上传新版本"的时候才产生版本，还是上传同名文件时自动算作新版本。我建议前者：云盘现在允许同名，各自是各自的文件，自动合并会改变这个行为。

**测试。** 迁移把已有的文件各生成一个版本；配额的口径；恢复之后下载到的是旧内容；删文件放掉所有版本。

**真机验收。** 上传两次，取回第一版，恢复它。

### D3 静态站点托管

**目标。** 从电脑上选一个文件夹，发布到网上，得到一个地址，能马上打开给别人看。

**现状。** 网页资源是构建时放进镜像、由服务端从磁盘上给的；反向代理把所有请求转给同一个端口，只有一个 `server` 块。用户上传的内容现在只有影视图片会送到浏览器，带所有权的检查。

**设计。**

- **必须是另一个来源。** 用户上传的是任意的网页，不能和登录状态同源，否则别人发来的一个页面能带着你的登录状态做事。所以要在正式地址之外另起一个子域名：域名由你加解析和证书，反向代理加一个 `server` 块，转到同一个服务端口，并在转发时带上一个标记。服务端只在请求的 `Host` 是这个子域名时才应答 `/sites/…`，在正式地址上不存在这条路。**改服务器上共用的 nginx 之前先问你。**
- 存储：内容进现有的内容寻址的 blob 存储，计入全站预算。新表 `sites`（名字在账户内唯一）和 `site_files`（站点、路径、摘要、大小、MIME）。路径在入库前收敛：不许 `..`、不许绝对路径、长度有上限。默认文档是 `index.html`。
- 应答：按扩展名给 `Content-Type`，摘要当 `ETag`。HTML 一律带 `Content-Security-Policy: sandbox allow-scripts allow-forms allow-popups`（不给同源，页面拿不到这个域上的任何存储）和 `X-Content-Type-Options: nosniff`。会话 Cookie 是只发给本主机的，不会跟到子域名，开工时用测试钉住这一点。
- 上传：桌面端用系统的选择器选文件夹，逐个文件走现有的上传（单文件 100 MB 以内），界面只拿到站点标识和地址。
- 限额：每个站点 100 MB、每个账户五个站点、全站合计 500 MiB。
- **开放范围（第 7 条）**：公开注册的网站加上任意内容的托管，等于谁都能用你的域名挂页面，服务器又在境内。我建议第一版只给超级管理员自己的账户用，代码里用一个账户上的开关控制，以后再放开。

**测试。** 路径收敛；`Host` 不对时 404；响应头；Cookie 不跨域；限额；删站点放掉内容。

**真机验收。** 发布一个只有一页的站点，在手机浏览器里打开那个地址。

**文档。** 部署手册（新的 `server` 块和证书）、架构说明里新增的一节、一份决策。

## 需要你决定的事

我的建议写在前面；你不答复，我就按建议做，并在这里记下"按建议"。

1. **手机上登录规则的写法。** 现在的边界是"登录只发生在系统浏览器里，应用不加载登录页、不接触密码"。手机上没有"打开系统浏览器再回来"的好办法，通行做法是系统提供的网页登录会话（`ASWebAuthenticationSession`）：由系统开一个隔离的网页，密码只输给这个网页，应用只收回一个回调地址。**建议：把它算作系统浏览器，边界改写成"登录只发生在系统提供的网页里"，凭据那一条补上"手机上是 Swift 这一侧和系统钥匙串"。** 验证串只在本机，所以就算别的应用抢注了回调的地址，拿到的码也换不出令牌；买了开发者账户之后换成通用链接，连这个口子也堵上。
2. **手机怎么写。** 纯 Swift，规则和类型手写一份、用样本钉住；或者把 Rust 的基础库编译到 iOS 上，经一层绑定给 Swift 用，类型和规则只有一份。**建议第一期用纯 Swift**：第一期只有日程这一小块，绑定的工具链和持续集成要另搭一套，等手机上要收文件、看云盘的时候再上 Rust 内核。
3. **手机的最低系统版本。** 建议 iOS 17。（2026-11-26 从这台 Mac 上配对过的设备看到：iPhone 17 Pro，iOS 26.5.2。）
4. **助手下载完之后，要不要把文件的完整路径告诉助手。** 建议告诉：不然助手没法接着处理那个文件。路径里带着你的用户名，会随对话发给模型的提供方。
5. **邮箱简报。** 要不要做；几点发；内容里要不要别的。
6. **文件版本怎么产生。** 建议只在明确点"上传新版本"的时候。
7. **静态托管。** 子域名用什么；第一版只给超级管理员自己用行不行；服务器在境内，挂任意内容之前备案和内容责任你想过没有。
8. **还在等着的旧决定。** 签名证书买不买（E2；自动更新 2026-11-27 已经定了）；收到的文件要不要只有本人可读、云盘要不要文件夹（E4）；jarvis 里的目标与计划你用不用（E1）。
9. **手机装到真机上时连哪个服务。** 本来列了两条路，核实之后只剩一条（2026-11-27）：真机只连得上 HTTPS 的服务——回环地址上的明文 HTTP 除外，可真机上没有通往这台 Mac 的回环地址（`iproxy` 只能把 Mac 的端口转到手机那头，方向反了），局域网里的明文 HTTP 又是服务端和客户端都定死不收的。所以是：正式服务先升级到带 B1、B2 的版本，两台电脑更新应用，手机再连正式服务、用你自己的账户。第一步 2026-11-27 01:32 已经发生：另一个会话部署 `c79edf0` 时把 B1、B2 一并带上了正式服务。想先不动正式服务，就得在手机上装一张自己签的根证书并设成信任，步骤多、容易出错，不建议。你 2026-11-27 凌晨让我接着往下走：平台值随后也改成了 `ios`（正式服务 02:48 再升一次，到 `8986d0a232a6`），这台 Mac 上的应用 02:49 换成了 `8986d0a`。还剩 Windows 的安装包由你来装（持续集成运行 `45876106313`，`assemble-windows-x64`），装好了告诉我，我再往手机上装。

下面这些是我采用的做法，你没有逐条确认过，看到不对的直接说：

- 拒收的开关默认关，收到的文件照旧自动收下（A5）。
- 手机第一期不能收文件，也不开事件流，所以不会显示在线（B1、B3）。
- 手机的令牌和桌面端一样不过期（B1）。
- "允许助手让这台电脑下载"默认开着（C1）。
- 存储的告警线是预算的八成和 2 GiB 的余量（C2）。
- 断点续传只做顺序的，不做分片并行（C3）。
- 静态站点的限额：每个站点 100 MB，每个账户五个，全站 500 MiB（D3）。

## 这一批不做

- 远程推送（第二期）、后台刷新、手机上的文件与云盘。
- 局域网直传、大文件分片；单文件 100 MB 的上限不变。
- 把磁力或者别的重活放到服务器上跑。
- 迁移 jarvis 的账户与数据。
