# 远程中转加密实施方案

状态：2026-11-27 已实现源码，尚未发布与双机验收。用户明确选择保留同账户、逐次批准和服务端中转；本次在此范围内增加远程内容加密。现状与验证见[决策 0017](../decisions/0017-remote-desktop-first-batch.md)和[远程手册](../runbooks/remote.md)。

## 认证与批准

采用标准 Noise XX（25519/ChaChaPoly/SHA256），每次申请生成临时密钥，只留在 Rust 内存，不存服务端、不传给界面。三步握手通过已认证的本项目 HTTP 中转；握手绑定会话标识和双方设备标识。握手准备不创建屏幕或输入对象。

同账户设备目录仍来自受信任的账户服务，但中转不得因此获得业务明文。双方界面显示由本地 Noise 握手摘要生成的核对代码；被控端核对后批准，代码不同则拒绝。只有握手完成且本机明确批准后才启动采集。不能把“自动生成并显示代码”写成用户已经核验身份；每场新会话仍需核对与批准。

## 消息与生命周期

- 画面、键鼠、剪贴板与系统声音使用分类型密文信封。信封内部绑定会话、消息类型、序号或请求标识，防止跨会话、跨方向和跨类型替换。
- 使用标准 Noise 无状态传输的显式 nonce；每个方向只有一个递增分配器。大帧按标准消息大小分片，加密前后都有总长度和分片数量上限。内部类型必须在 Rust 解密后重新验证。
- 输入依旧逐次确认、去重，剪贴板继续保留请求 ID、期限和成功确认；原生失败不能变成粘贴成功。解密失败立即停止控制并显式释放输入。
- 双端发送经过认证的新心跳。只看到中转 HTTP 成功不代表对方仍在控制；超过期限没有新心跳即结束，防止中转重放旧状态延长控制。新连接不会重放旧输入，也不会恢复旧密钥。
- 服务端只保留有界密文队列与会话元数据，结束立即清空。文件仍复用原有发送服务，不宣称这会自动使现有云盘或文件存储变成端到端加密。

## 必须验证

真实 HTTP 双端握手与双方摘要相同、不同会话及方向不能解密、篡改与截断失败、重试不重复应用、心跳重放不能延长控制、结束后密文不可再用、批准前不能采集、密钥不在桥接/快照/日志里。更新桌面快照中的核对代码样本与两侧测试。原生视频和音频探针、整仓检查、真实启动及双机核验分别记录。
