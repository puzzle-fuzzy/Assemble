# 0015：桌面端自动更新——整包更新、自己的服务器下发、空闲时换上

- 日期：2026-11-27
- 状态：服务端这一半已实现（清单与更新包两个只读接口、`publish-update` 子命令），有对着真实运行的服务端的测试。桌面应用那一半、发布脚本和第一次发布还在做。
- 起因：换一版桌面应用要人手来——这台 Mac 由助手手动替换，Windows 要你自己下载安装包再装。你 2026-11-27 定了三件事。做法是**整包自动更新**，和 VS Code、ZCode 一样：Tauri 把界面编进了可执行文件，换界面就是换整个应用，"界面只来自应用自身"这条边界不动，不选"界面从服务器加载"。更新包从**我们自己的服务器**下发，**签名的私钥只在这台 Mac 上**，持续集成照旧只出没签名的安装包。**空闲时自动换上**：主窗口收起、又没有文件在传的时候自动重启换新版，有传输就等，退出应用时也会换上。

## 决定

- **用官方的更新插件，整包更新。** `tauri-plugin-updater` 2.14.1。应用里只编进公钥；更新包没有正确的签名就一律不装，这一条关不掉；不允降级。
- **私钥只在一台 Mac 上。** `~/.assemble/updater.key`，只有本人可读。它不进仓库、日志、界面和持续集成。丢了，装出去的应用就再也更新不了，只能重装。公钥是仓库里的 `deploy/updater.pubkey`，编进服务端（发布时核对）和桌面应用（下载后验签）。
- **更新包由这台服务端托管。** 两个谁都能读的接口：`/updates/latest.json` 是清单，照 Tauri 的格式；`/updates/<平台>/<版本>/<文件>` 是更新包。都按来源限速。两台电脑都在国内，不依赖 GitHub。
- **发布走命令行，不开写的接口。** `assemble-server publish-update <目录>`：缺省只校验，`--apply` 才发布。校验用同一把公钥：签名不对的、不是为清单上的版本签的、版本不比已发布的新、少了已发布的平台、目录里有多余的文件，都发不出去。发布是人在那台 Mac 上手动跑的一条命令，不随每次推送自动发。
- **更新包每个平台只留最新的一版。** 放在数据目录的 `updates/` 下，不在 `blobs/` 里：不受每分钟的清扫影响，也不计入云盘预算；备份时随数据目录一起打包。
- **什么时候换上。** 启动 15 秒后查一次，之后每 6 小时；查到就在后台下载。macOS 下载完立刻原地替换应用包，下一次启动就是新版；Windows 的安装包要等应用退出才能跑，所以先把包留着。主窗口收起、又没有文件在传、持续 3 分钟就自动重启换上，重启后只在托盘里；从托盘退出时也会换上；托盘和"关于"页可以立刻换。
- **只有连正式地址的构建会更新。** 连本机回环地址的构建显示"这个构建不自动更新"。
- **版本号是 `0.1.<提交数>`。** 每次提交自动加一；同一个提交在 Mac 和 Windows 上是同一个号。

## 我采用的，你没有逐条确认

- 私钥放在 `~/.assemble/` 下，不设口令。
- "空闲"指主窗口收起、没有收发文件、没有网络下载，并且持续 3 分钟。
- 第一版只做 Windows 的 NSIS 安装和 Apple 芯片的 Mac。不做 MSI、Linux、多渠道、分批推送，也不自动更新 `assemble-mcp` 那个独立程序。
- 带更新器的第一版要在两台电脑上各手动装一次，之后的版本才会自己更新。

## 验证边界

- 自动化测试（2026-11-27，服务端这一半）：签名的核对（对的是哪把钥匙、是哪个版本、包有没有被改）；路径上做手脚到不了磁盘；对着真实运行的服务端的五条测试——没发布时什么都读不到、发布之前逐项核对、只有更新的版本才能替换已发布的、两个接口按来源限速、子命令用的是编进服务端的公钥。做法写在[部署手册](../runbooks/deploy.md)的"发布桌面端的更新"里。
- 还没有做过的：桌面应用那一半；本机从发现、下载、替换到空闲时重启的端到端；Windows 真机上的静默安装与自动重启；换新版之后钥匙串不再问；正式服务上的第一次发布。
