# 0015：桌面端自动更新——整包更新、自己的服务器下发、空闲时换上

- 日期：2026-11-27
- 状态：已实现（服务端、桌面应用、发布脚本），本机端到端在 macOS 上走通过一次；正式服务已经升到带更新接口的版本（`873131d75607`），这台 Mac 上的应用换成了带更新器的 `0.1.116`，第一版 `0.1.117` 已经发布（2026-11-27 11:39）。还没有做过的：看着装出去的应用真的自己换上新版（两台电脑都是）；Windows 真机上的静默安装与自动重启；换新版之后钥匙串不再问。见下面的"验证边界"。
- 起因：换一版桌面应用要人手来——这台 Mac 由助手手动替换，Windows 要你自己下载安装包再装。你 2026-11-27 定了三件事。做法是**整包自动更新**，和 VS Code、ZCode 一样：Tauri 把界面编进了可执行文件，换界面就是换整个应用，"界面只来自应用自身"这条边界不动，不选"界面从服务器加载"。更新包从**我们自己的服务器**下发，**签名的私钥只在这台 Mac 上**，持续集成照旧只出没签名的安装包。**空闲时自动换上**：主窗口收起、又没有文件在传的时候自动重启换新版，有传输就等，退出应用时也会换上。

## 决定

- **用官方的更新插件，整包更新。** `tauri-plugin-updater` 2.14.1。应用里只编进公钥；更新包没有正确的签名就一律不装，这一条关不掉；不允降级；签名不是为清单上的那个版本签的、或者签名里没写版本，也不装（`requireSignedVersion`）。插件只从 Rust 这边用，窗口的能力清单不动：界面读状态里的 `update`，动手走 `update_check`、`update_restart` 两条具名命令。
- **私钥只在一台 Mac 上。** `~/.assemble/updater.key`，只有本人可读，没有口令。它不进仓库、日志、界面和持续集成。丢了，装出去的应用就再也更新不了，只能重装。公钥是仓库里的 `deploy/updater.pubkey`，编进服务端（发布时核对）和桌面应用（下载后验签）。
- **更新包由这台服务端托管。** 两个谁都能读的接口：`/updates/latest.json` 是清单，照 Tauri 的格式；`/updates/<平台>/<版本>/<文件>` 是更新包。都按来源限速。两台电脑都在国内，不依赖 GitHub。
- **发布走命令行，不开写的接口。** 缺省只校验，`--apply` 才发布。校验用同一把公钥：签名不对的、不是为清单上的版本签的、版本不比已发布的新、少了已发布的平台、目录里有多余的文件，都发不出去。发布是人在那台 Mac 上跑的一条命令（`bun run release:publish`），不随每次推送自动发。
- **更新包每个平台只留最新的一版。** 放在数据目录的 `updates/` 下，不在 `blobs/` 里：不受每分钟的清扫影响，也不计入云盘预算；备份时随数据目录一起打包。
- **什么时候换上。** 启动 15 秒后查一次，之后每 6 小时；查到就在后台下载、验签。macOS 下载完立刻原地替换应用包，运行中的进程不受影响，下一次启动就是新版；Windows 的安装包要等应用退出才能跑，所以先把包留着。主窗口收起、又没有文件在传、持续 3 分钟就自动重启换上，重启后只在托盘里；从托盘退出时也会换上；托盘和"关于"页可以立刻换。
- **只有装出来的应用才更新。** `bun run dev`、验收脚本和 `tauri build --no-bundle` 跑的是 target 目录里裸的可执行文件，不更新，连的是正式地址也不更新：它的版本号一直是配置里的那一个，让它更新，就是用下载来的新版本把开发用的可执行文件替换掉。连回环地址的发布构建也不更新。例外只有一个：装在应用包里的调试构建也认回环地址，留给本机的端到端测试。
- **版本号是 `0.1.<提交数>`。** 每次提交自动加一；同一个提交在 Mac 和 Windows 上是同一个号。一律经 `bun run build` 打包，不要直接调 `tauri build`。

## 我采用的，你没有逐条确认

- 私钥放在 `~/.assemble/` 下，不设口令。
- "空闲"指主窗口收起、没有收发文件、没有网络下载，并且持续 3 分钟。
- 第一版只做 Windows 的 NSIS 安装和 Apple 芯片的 Mac。不做 MSI、Linux、多渠道、分批推送，也不自动更新 `assemble-mcp` 那个独立程序。
- 带更新器的第一版要在两台电脑上各手动装一次，之后的版本才会自己更新。
- 发布时不要求打标签：取"安装包"流程为当前提交成功地跑过的那一次（手动触发或推标签都行），只要它已经跑完。
- 清单里的说明文字缺省是 `Assemble <版本>`；应用里现在没有地方显示它。
- 开发运行不更新（见上面"只有装出来的应用才更新"）。原方案写的是"连正式地址就更新"，做的时候发现那样会连 `bun run dev` 一起更新掉，改掉了。

## 验证边界

- **自动化测试。** 服务端这一半：签名的核对（对的是哪把钥匙、是哪个版本、包有没有被改）；路径上做手脚到不了磁盘；对着真实运行的服务端的五条——没发布时什么都读不到、发布之前逐项核对、只有更新的版本才能替换已发布的、两个接口按来源限速、子命令用的是编进服务端的公钥。桌面端这一半：什么时候换上、忙碌判定、哪些构建会更新、错误码，是不碰网络的单元测试；另有四条对着进程内真实运行的服务端、带着这个应用真正的配置（`apps/desktop/src-tauri/src/update/against_server.rs`）——签名正确的新版查得到、下载得下来、过得了验签；改坏一个字节的包被拒；清单上的版本和签名里的对不上被拒；版本更低或者一样的都不算更新。发布脚本：版本号怎么算、发布目录的样子、签名是为这个版本签的、压缩包顶层就是应用包、不是本地证书签的应用包发不出去。发布用的私钥只在那台 Mac 上，所以"真签一次"的那条测试在持续集成上跳过。
- **真实启动（2026-11-27，这台 Mac）。** 另一个应用标识的调试构建 0.1.1000，对着一个一次性的本机服务端：启动 16 秒后自己发现 0.1.1001，1 秒内下载并验签，应用包原地换成了新版，运行中的进程没有受影响；空闲满 3 分 14 秒后静默重启，新进程带着 `--background` 起来、没有弹窗口，15 秒后查到已是最新。做法和它的代价见[运行手册](../runbooks/verify-macos-launch.md)的"自动更新的本机端到端"。这一遍前后抓到并修掉四处：开发运行会更新自己；从托盘菜单重启时 Tauri 不发退出事件，显式的退出清理会被跳过；本来就带着后台参数启动时，静默启动的记号没有被读掉；启动日志记的是 cargo 包的版本，不是应用的版本。
- **正式服务上的第一次发布（2026-11-27 11:39，`0.1.117`）。** 先只校验、再发布，两遍都成：取 Windows 安装包、构建并签名 Mac 应用、给两个包签名、传到服务器，服务器用编进去的公钥验签通过；清单和更新包在正式地址上读得到。经过记在[部署手册](../runbooks/deploy.md)的"发布桌面端的更新"里。
- **还没有做过的。** 看着装出去的应用真的自己换上新版——这台 Mac 上是 `0.1.116`，要等它的下一次检查；Windows 上还是旧版，要先手动装带更新器的第一版。Windows 真机上的静默安装、自动重启、开机启动和退出时换上新版；换新版之后钥匙串不再问——本机端到端用的是另一个应用标识和临时签名，证明不了这一条，要在"应用程序"里那一个第一次自动更新时看；托盘菜单和"关于"页的两个入口（和自动换上共用同一段代码，但没有真人点过）；从托盘退出时换上新版（只在 Windows 上有这一步）。
- **我知道的一处不完美。** "空闲"不看屏幕有没有锁：锁屏时主窗口也算收起，应用照样会换上新版并重启；换完之后要等人回来解锁才恢复登录（锁屏时登录钥匙串也锁着）。比起来说这是最不打扰人的时机，只是锁屏期间应用不在线。要不要等解锁再换，等真的遇到过再说。
- **手动换上带更新器的第一版时顺带查出来的一处**（不是自动更新的问题，但换新版会撞上）：应用每次启动都改写钥匙串里浏览器桥接的临时凭据，正常退出时才删掉它；旧应用是被杀掉的（或者崩溃）时那一条还留着，新应用改写它，macOS 就要人输登录钥匙串的密码，应用停在启动上。已经改成先删再建（`crates/assemble-download/src/browser.rs`）。带这一改动的版本装上之前，换应用要让旧的应用正常退出，或者先手动删掉那一条。
- **做本机端到端时踩到的。** 换了应用标识的构建真跑会惊动人：应用一启动就访问"下载"文件夹、往登录钥匙串里写浏览器桥接的临时凭据，新的标识因此得到系统的隐私询问框；临时签名的构建每换一次二进制，在钥匙串眼里就是另一个程序，第二次启动弹了钥匙串的确认框，应用停在启动上。两个框在把应用停掉之后还留在屏幕上。所以要真跑，挑用户在的时候先说一声；不碰窗口的那部分交给上面那四条测试。装在"应用程序"里的那一个用的是稳定的本地证书，不在这条里。
