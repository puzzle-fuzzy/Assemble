## 背景

0001 把"服务端完全不动、继续使用现有的 Jarvis API"当成了默认，而且只写在它"待确认"表的 A 项里。你看到架构说明和 README 里出现"服务端沿用现有的 Jarvis API"之后追问："你是用的人家的 api 吗，不是自己重新搭建的吗"，随后明确：Assemble 是**全新的、自带服务端的项目，用来完全替换 jarvis**。

这个假设是我采用的，不是你提的要求。它决定的是整个仓库的边界，本该在动手前单独说明、等你答复，而不是埋在一张默认值表的某一行里。以后凡是会改变项目边界的假设（要不要服务端、要不要迁移数据、要不要动别的仓库），开工前都要单独说出来。

你同一天还要求先用 Git 初始化项目，对应 0001 的 J 项，已于 2026-11-24 执行：仓库在 `main` 分支，起初不建远程。当天晚些时候你定了仓库公开：[github.com/puzzle-fuzzy/Assemble](https://github.com/puzzle-fuzzy/Assemble)。

## 你要的文件传输

两台设备装好 Assemble 并登录同一个账户。在公司的 Windows 电脑上右键一个文件，选"发送"，弹出一个面板，里面是"云盘"和"我的 MacBook 电脑"这样的目的地；点一下就结束。选云盘，文件存到服务端；选 MacBook，文件送到这个账户另一台在线的设备。单个文件 100 MB 以内，不考虑特别大的文件。

| 接收位置     | 默认存到"下载/Assemble"；同名不覆盖，自动加序号；弹系统通知；可以在设置里改                                                         |

## 技术选择及理由

**事实**（查文档、读源码或运行得到的）

- Windows 允许普通用户在 `HKCU\Software\Classes\*\shell\<名称>` 下登记右键菜单项，不需要管理员权限。Windows 11 上这类入口只出现在"显示更多选项"里。
- 要进 Windows 11 右键菜单的第一层，应用必须有包标识（MSIX 或稀疏包）、一个实现 `IExplorerCommand` 的 COM 组件和受信任的签名。Tauri 2 没有打包 MSIX 的目标。
- `sqlx 0.9.1` 要求 Rust 1.94；本机是 1.98。工作区其余部分声明的是 1.90，只有服务端这个包需要声明更高的下限。
- 单实例插件会把第二个进程的完整参数转交给已经在运行的那个，包括被右键的文件路径。

**推断**

- **事件流用 SSE，不用 WebSocket。** 设备发给服务端的内容全部走普通 HTTP，服务端只需要单向推送（设备上下线、有文件送达、发送状态变化）。这样少一个依赖，反向代理也不用为升级连接单独配置。
- **在线的定义是"持有事件流连接"。** 不需要另写心跳：连接断开即离线，重连即上线。
- **密码用 argon2id。** 0.6 版的默认参数符合 OWASP 的最低建议。
- **文件内容按摘要寻址并计数引用。** 同一个文件存进云盘、再发给设备，磁盘上只有一份；最后一个引用释放时才真正删除。
- **授权码一次有效、60 秒过期。** 桌面端登录沿用 0001 的做法：系统浏览器登录，经回环地址和 PKCE 交回授权码，换码时顺便完成设备注册。
- **接收方一次只收一个文件，按先来后到。** 同名的文件接连到达时自然得到不同序号，不必处理两个接收互相抢名字。
- **先落盘，再回执。** 服务端一收到"已收下"就释放文件，所以回执只能在文件真的存好之后发。回执没送到不算完：每次与服务端对账都会发现它还在等，再补一次。
- **云盘是平铺的一层，同名不冲突。** 第一版不做文件夹；两个文件可以同名，靠标识区分。内容按摘要存放，所以同名与否不影响磁盘上存几份。
- **云盘里的文件靠标识引用，取回时再核对。** 取回与接收走同一条路：流式下载、核对长度与摘要、落到接收位置、通知用户。取回之前文件被删了，这一条如实写"云盘里已经没有这个文件了"，不悄悄消失。
- **取消要取消到底。** 上传途中按了取消，文件其实可能已经到了服务端，只是回执没送到。所以取消之后记录不改回"等对方接收"，而对账时会把这样的发送在服务端撤回：按内容摘要、文件名和收件人认出它。不然对面会收到一个本机已经放弃的文件。
- **说不准是谁的问题时，不怪任何一方。** 取不到内容（连接断了、服务端出错）只是过一会儿从头再收，不向发送方报告失败——报告的只有这台电脑确实写不下来（磁盘满、目录不能用），以及收到的内容与声明的长度或摘要对不上。为此失败原因多了一种 `verification_failed`：它不是接收方磁盘的问题，发送方看到它就知道该重发。
- **文件交给应用，只有一条路。** 右键菜单执行的命令、拖进窗口的东西、启动参数，最后都变成 Rust 手里的一组路径：逐个核对（大小合规、算出摘要）后排进发送面板。界面拿不到路径；拖放也不靠网页去接，原生的拖放处理器直接交给 Rust。右键菜单只在 Windows 上的打包运行里登记（开发运行的可执行文件位置不固定），默认开着，设置里可以关。
- **大文件被提前拒绝时，要让对方把话说完。** 服务端在读完正文之前就拒绝，连接会在发送方还在上传时被关掉，发送方只看到"连不上服务"。所以拒绝之前先把正文读完丢掉。小文件暴露不了这个问题：它们在拒绝之前就全部进了连接的缓冲区。

## 放弃的备选

| 备选                             | 不选的原因                                                        |
| -------------------------------- | ----------------------------------------------------------------- |
| 只给 Jarvis 换桌面端，服务端照旧 | 这是 0001 的假设，已被你否决；目标是替换整个产品                  |
| 服务端用 Bun + Elysia            | 协议类型要在 Rust 与 TypeScript 之间再对一次；你选了 Rust 服务端  |
| 数据库用 PostgreSQL              | 单机、单用户量级，SQLite 够用，少一个要运维的服务                 |
| 用 `rusqlite` 访问数据库         | 同步接口要包一层阻塞线程；`sqlx` 自带迁移，而且是异步的           |
| 设备之间直连（局域网或打洞）     | 公司与家里的网络不一定互通；你选了服务端中转                      |
| 目标离线时先存服务端、上线后再送 | 你选了"只能发给在线设备"，服务端不必替离线设备长期保管文件        |
| Windows 右键直接进第一层菜单     | 需要包标识、COM 组件和签名证书，Tauri 2 又打不出 MSIX；留到第二步 |
| 沿用 Jarvis 的账户与数据         | 新产品、新账户；`jarvis` 仓库只读参考，不迁移它的数据             |
| 用 WebSocket 推送事件            | 见上面"事件流用 SSE"                                              |

## 后果

- 0001 里围绕"对接现有 API"写的东西都要改：协议、客户端、应用壳、界面和文档。只为对接 Jarvis 而写的模块（本机网关、授权账本、回执账本、设备命令）已经删除。
- `assemble-transfer`（边读边算摘要、暂存、校验后发布）和 `assemble-schedule`（日程推算）与具体服务端无关，两端继续共用。
- 服务端要自己承担账户、登录页、设备管理、文件存储和清理。
- 部署成了这个项目的一部分：域名、DNS、反向代理和服务器容量都要定。没有你的同意不会动服务器。

## 从真实启动中学到的

下面几条都是自动化测试全绿、把服务端和桌面端真的跑起来之后才暴露的。记在这里，是为了下次别只信测试。

1. **持着锁时不要再调会加锁的函数。** 状态更新函数原先拿着状态锁，又去调一个会再次加锁的"取快照"，线程把自己锁死，并且永远占着那把锁。后果比"一个后台任务卡住"大得多：Tauri 对界面发来的小请求会**直接在主线程上执行命令**，界面一启动就调用的 `snapshot` 也要拿这把锁，于是主线程跟着卡死，页面连第一份资源都加载不出来——窗口一片空白，对读屏软件也没有任何应答。现在"比较并取快照"收在一个不依赖窗口的函数里（`state::revise`），不给在锁内回调的机会。排查手段：`sample <进程号> 1` 看主线程停在哪。
2. **页面不能用 `Referrer-Policy: no-referrer`。** 按 Fetch 标准，在这个策略下浏览器对同源的 POST 也会把 `Origin` 发成 `null`，写操作的 Origin 校验于是把登录表单自己拒了。集成测试没发现，因为测试里的"浏览器"是 HTTP 客户端，`Origin` 是人为构造的。页面的来源策略改成 `same-origin`：同样不向别的站点泄露地址，但 `Origin` 如实发送。校验本身不放松——接受 `null` 等于给防伪开了口子。
3. **事件流会让"优雅退出"挂住。** 事件流是永不主动结束的长连接，服务端收到 `SIGTERM` 后会一直等它收尾。现在退出信号先让所有事件流自行结束，再等在途连接，并且最多等十秒。本机实测带着一条打开的事件流也能在 0.02 秒内退出。
4. **按时间排序要给并列留后手。** 设备按注册时间排序，而标识是随机的；两台设备在同一毫秒内注册时先后顺序就是随机的。同一时间之内改用 SQLite 的行号分先后。
5. **"最多等十秒"包住了整个服务。** 上一条的修法把十秒的上限包在了整个服务外面，结果服务端启动十秒后自己退出。集成测试用的是另一条启动路径（`TestServer`），完全碰不到。现在两条路径走同一个 `serve_until`，计时从收到退出信号开始，并有测试盯着"上限只管退出，不给服务定寿命"。教训不只是这一处：同一件事有两份实现，测试就只会测到其中一份。
6. **提前拒绝一个上传，要等对方把话说完。** 给离线的设备发一个大文件，服务端在读完正文之前就回了绝，连接在发送方还在上传时被关掉，发送方只看到"连不上服务"，看不到真实原因。原来的测试用的是一万字节的小文件，小到连接层自己就把剩下的正文读完了，所以一直是绿的。现在服务端拒绝之前先把正文读完丢掉（`http::refuse_upload`）。回归测试要同时满足两个条件才复现得出来：文件够大，服务端与发送方真的同时运行（多线程的测试运行时）。
7. **测试辅助函数里的异步文件要等它真的写完。** 一个测试用异步文件写完就丢句柄、接着改修改时间；异步文件的写入其实在句柄丢弃之后才落盘，那次迟到的写入把刚改旧的时间刷新成现在，测试时过时不过。清扫逻辑没有问题，问题在测试自己。遇到"偶尔失败"先重复跑它，别当成噪声。
8. **只在 Windows 上才出现的编译错误与静态检查错误，只有对着 Windows 目标检查才看得见。** 装了 Windows 的 Rust 目标之后，对着它检查不依赖窗口的 crate，一次就抓到五处：注册表代码里多余的解构、只在类 Unix 上用到的变量、Windows 上恒返回成功却被声明成可能失败的函数、一个在 Windows 上留了没用的变量的测试。这种检查不做交叉编译，几秒钟就跑完。带本机依赖的 crate（TLS、SQLite）这样检查不了，它们只能到 Windows 环境里去验。
9. **时限是按毫秒比的，测试别卡在同一毫秒上。** 过期测试把时限设成零，以为"任何发送都算过期"；可清理是按"建立时刻早于现在减去时限"来比的，记录刚建好的那一毫秒里两者相等。八次里挂一次。等时钟走过那一毫秒再清理，结果才每次都一样。

下面八条来自 2026-11-24 建公开仓库、让持续集成在 macOS 与 Windows 上各跑一遍的那一天。此前所有"全绿"都只是在一台 Mac 上得到的。

10. **本机的编译器和持续集成的不一样，新的检查本机就看不见。** 本机是 Rust 1.98，持续集成装的是最新的稳定版 1.100，多了一条检查，十处测试代码在远端变红，而本机一直是绿的。现在工具链钉在 `rust-toolchain.toml`，本机、持续集成与镜像构建用同一个版本，升级时一起改。声明的工作区最低版本也改成同一个数：声明一改，编译器就按新版本的标准打开了一批原本被最低版本压住的检查。
11. **函数的"会不会失败、要不要可变"不能取决于平台。** Windows 那一栏连续抓到四条同源的：一个异步函数的 `await` 全在 `#[cfg(unix)]` 里，到了 Windows 上成了"没有 await 的异步函数"；改成同步之后函数体还整个藏在那里，又成了"永远不失败的 `Result`"；托盘的 builder 只有 macOS 上会再赋值；右键菜单那个函数在 Windows 上永远只返回 `Some`。修法都一样：让读、写这些可能失败的步骤在哪个平台上都执行，按平台不同的只是细节；只在某个平台上才有的一步，用遮蔽接上去，不要给变量标 `mut`。
12. **测试别和定时器赛跑。** 一条界面测试在替身让命令"零毫秒后返回"的那个瞬间断言按钮消失，谁先谁后在 macOS 和 Windows 上不一样。让替身可以把命令一直按住、断言完再放行，时序就确定了。
13. **桌面应用壳的测试程序在 Windows 上根本加载不了。** 退出码是 `0xc0000139`，找不到入口点，一个测试都没跑。原因：Tauri 运行时用到了只有通用控件库 6.0 才有的 `TaskDialogIndirect`，而用 6.0 版需要可执行文件里嵌着应用清单；Tauri 只把清单链进主程序，库的单元测试是另一个可执行文件，没有清单，Windows 给它的是 5.82 的旧版。发布版的应用不受影响。cargo 没有"只给库的单元测试程序链东西"的指令（`rustc-link-arg-tests` 只管独立的集成测试目标，没有这种目标时会被判为非法指令），所以关掉了 Tauri 默认 feature 里的 `common-controls-v6`：它只服务于预置的"关于"菜单项和运行时的消息对话框，这两样我们都没用。诊断的经过：加载失败的程序在没人看着的机器上会弹一个系统对话框一直等，所以别"直接运行一次看看"，去列它的导入表，逐个核对系统的 DLL 里有没有。
14. **测试里别用原始错误码。** "磁盘已满"在类 Unix 上是 28，在 Windows 上 28 是"打印机没纸了"。按错误的种类来造，把系统的错误翻译成种类是标准库的事。
15. **`cargo test` 要一次把所有包跑完。** 默认遇到第一个失败的包就停，每个平台每一轮只暴露一个问题；加上 `--no-fail-fast`，一轮把剩下的都看到。
16. **没有真的构建过，就不算验证过。** Dockerfile 写完之后只做了不依赖容器的检查（compose 能不能解析、环境变量认不认、健康检查命令对不对），并在文档里写下了"镜像还没有构建过"。真的构建时暴露了三处：构建上下文里少了桌面端的清单与入口文件，cargo 解析不了工作区；建了专用账户却忘了写 `USER`，容器以 root 运行；手册里 `docker compose exec` 的命令少了可执行文件名。前两处不运行就发现不了，第三处照着手册做就会撞上。2026-11-25 又来一次：送镜像的脚本写完之后一直没跑过（上一次部署是手工送的），第一次真跑就因为变量后面紧跟全角括号而倒下。写完的脚本、流程、手册步骤，都要真的走一遍才算数。
17. **服务器在国内，拉不到 GitHub 的镜像仓库。** 清单取得到，数据所在的地址握手超时。镜像由能访问 GitHub 的开发机拉下来，再经 SSH 传过去。
18. **"上一步看得见了"不等于"下一步也做完了"。** 2026-11-25 日程规划写完、整套验证通过之后又跑了一遍，桌面应用壳的一条云盘测试红了；单独重跑是绿的，前后三处都是同一类：两条云盘的测试在传输刚标成完成时就去看名单（名单是传完之后才去拿的），收文件的那条在文件刚落地时就数目录（发布是先链接、再删暂存名）。平时机器不忙看不出来；给机器加上负载、把整套测试循环跑了二十多轮，才各失败过一次。都改成等那件事发生为止。以后遇到"整套里偶尔红、单独跑是绿的"，先这样压一轮把它抓出来，不要当成偶发放过。同一天晚些时候又来第四处：持续集成的 macOS 那一栏在一个只改了文档的提交上红了——清扫上次中断留下的暂存文件的那条测试，等默认位置清完就去看用户设置的文件夹，而两处是先后清的。上一轮压了二十多轮它没有露头，这次是翻持续集成的日志才抓到的（`gh run view <编号> --log-failed`，找 `panicked at`）；那次红了我隔了一整个步骤才看见。所以每次推送之后都要去看那一轮的结果，不能只看最新的一轮是不是绿的。
19. **已经跑过的迁移脚本不要再改。** 2026-11-24 凌晨迁移 1 提交后二十分钟被原地改过（去掉授权码表的两列）。当时还没有任何部署，看着没事；但 sqlx 在每个库里记着脚本的校验和，那二十分钟里建的本机开发库从此就打不开了。没人发现，是因为之后没有再用那个库启动过——直到 2026-11-25 做日程规划的真实启动，服务端一启动就报"migration 1 was previously applied but has been modified"。正式服务的库是用改完之后那一版建的，不受影响。规矩：迁移脚本一经提交就不再改，结构要变就加新的脚本；本地开发库打不开时挪走重建，不要去改库里的记录。
20. **测试别依赖机器的时区。** 2026-11-25 一条新写的测试把时刻写死成带 `+08:00` 的，再去和按本机时区格式化出来的文字比：在这台 Mac 上是绿的，持续集成的两个平台都在 UTC 上，同时变红。按本机时区的"年月日 时:分"去构造那个时刻，测试在哪个时区都一样。改完把整套测试放到 UTC、纽约、基里巴斯三个时区下各跑了一遍。
21. **Windows 上"替换文件"不是原子的，并发写入要自己排队。** 同一天晚些时候，Windows 那一栏里 `assemble-store` 一条与当天改动无关的测试红了一次（之前十几轮都是绿的）："八个线程同时写同一个状态文件"，一个写入者替换失败，最后目标文件不见了。类 Unix 上 `rename` 覆盖是原子的；Windows 上两个替换撞在一起会两败俱伤。临时文件的名字再唯一也隔不开这最后一步，所以同一个进程里的写入者排成一队（`write_private_json` 的一把锁），杀毒与索引造成的短暂占用仍由原来的重试去等。本机压不出来：这台 Mac 上替换本来就是原子的。
22. **回环回调只在有人等它的时候才应答。** `assemble-mcp` 第一次对着真实运行的服务端走整条登录时卡住了。`LoginListener` 在回环地址上的监听，要等 `wait` 被轮询到才开始应答；桌面端先让系统打开浏览器（这一步只是把请求交给系统，立刻就返回），再去等回调，靠的一直是"浏览器总比下一行代码慢"。助手入口原本也是这个顺序，可测试里的"浏览器"在"打开浏览器"那一步里就把回调访问了，这一头还没开始等，于是两边互相等。测试里给访问回调加的十秒超时把它抓了出来（不设上限的话它只会表现成"这一条测试很慢"）；代码改成开浏览器与等回调同时进行，不再依赖谁先谁后。两步之间要是隐含着"上一步一定比下一步慢"，就让它们同时进行。
23. **"本来就没有"不是错误。** 同一天，头一次登录必败：登录是从"先把旧的登录退掉"开始的，而"退出"把"本机没有保存任何登录"当成错误往上传。工具的单元测试个个从"已经登录"起步，所以看不见；真实世界里一台新电脑上的第一次登录，走的恰恰是这条路。集成测试从空存储开始走整条登录，第一次跑就红了。凡是"先清理、再做"的流程，要让测试从什么都没有的状态开始。
24. **内容安全策略管的不只是表单提交到哪里，还有提交之后被送到哪里。** 2026-11-25 正式服务上第一次真人登录：在授权页点"确认登录"，没有任何反应。服务端的审计里是五次"已授权"、零次"已注册"——码签出来了，浏览器却从没把它送回本机。缘故是所有页面共用的那一份策略里有 `form-action 'self'`：表单提交到本站没问题，可服务端回的是"跳到 `http://127.0.0.1:<端口>/callback`"，而浏览器对 `form-action` 的规矩是提交之后的跳转目标也要落在允许之列，于是悄悄拦掉了这次跳转，页面原地不动。自动化测试全是绿的：测试里的"浏览器"是 HTTP 客户端，不看内容安全策略；真实浏览器里只核对过登录页，授权页的确认那一下从来没有走完过。修法是授权页用自己的那一份，放行这一次登录正在监听的那个回环端口，不是整个回环地址。三条教训：浏览器参与的页面，每一步跳转都要在真实浏览器里走完，"各段分别验过"不算数；用户说"没有反应"时先去看服务端留下了什么，审计能把"没点到"和"点了但被拦"分开；替浏览器看规矩的测试要照着浏览器真的会做的事来写——加的那一条，对着没修的代码是红的。

另外三条与验证方法有关，见[运行手册](../runbooks/verify-macos-launch.md)：模拟浏览器的 HTTP 客户端复现不了真实浏览器的行为；屏幕锁定时做不了界面层面的验证（读窗口之前先查锁屏状态——"读不到网页内容"在锁屏时必然出现，2026-11-24 曾经把它当成了应用的疑点）；不要替桌面端往系统钥匙串里预置会话——那会在用户的屏幕上弹一次钥匙串确认框（2026-11-24 发生过一次，惊动了你）。

收发这两条路没法在没有人看着屏幕的时候做真实启动（桌面端得先经浏览器登录），所以它们的"整条路"验证放在 `apps/desktop/src-tauri/src/transfers/tests.rs`：用 Tauri 的模拟应用装真实的 `AppState`，对着真实的服务端收文件、发文件、撤回、对账、存进云盘、从云盘取回。这比单元测试强得多，但它仍然不是真实启动——窗口、通知、钥匙串那几样只有真的跑起来才算数。
