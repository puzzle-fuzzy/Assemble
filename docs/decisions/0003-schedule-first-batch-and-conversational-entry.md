## 背景

方案里列了十件要你定的事。2026-11-24 你答复了最要紧的两件，并对第二件做了说明。

## 决定

| 事项         | 决定                                                                                        |
| ------------ | ------------------------------------------------------------------------------------------- |
| 第一批的范围 | 日程、提醒、到点通知                                                                        |
| 对话式入口   | 保留，并且是第一批的一部分：你和 Codex、ZCode 对话，由它们分析内容、安排时间、写进 Assemble |
| 其余八条     | 你没有异议，按方案里的建议做。它们是我的建议，你没有逐条确认；要改随时说                    |

按建议采用的八条：任务、目标与"今天"放第二批；每条日程可以设"提前几分钟"；每台在线设备都弹，另给每台电脑一个"不弹"的开关；设备重新上线后补弹过去 24 小时内没弹过的，离开提醒时刻超过十分钟或已结束的场次不提醒、提醒不管多晚都补；重复日程整条完成；时区沿用 jarvis 的规则；不迁移 jarvis 里的日程与提醒；工作陪伴不算日程规划。

## 你怎么用

你的原话（2026-11-24）：

> 我一般都是会和 Codex 和 ZCode 进行对话，然后由这俩个 AI 来分析我的内容和处理日程，比如我会告诉你我明天 9:00 的火车，Codex/ZCode 你需要分析我的这个内容，然后定好提前的时间，告诉我需要携带的内容（比如身份证），然后设定好时间。设定好时间后会同步到我的 IOS 手机上面同步的设置好闹钟或者是提起提醒方式。请你仔细分析一下，并不是我手动的在管理段或者页面端进行设置，而是我通过文本和你对话，你来处理我所有的内容。这就是之前 MCP 存在的一部分意义。

这纠正了方案里的一个倾向。我当时建议第一批先不做对话入口、把桌面里手建做好，理由是 jarvis 的日常网页不能新建日程是个短板。你说的是：**对话就是你管理日程的方式**，手建只是备用。所以对话入口不是"以后再说"，而是第一批必须有；桌面里的新建与编辑降为备用入口。

## "明天 9:00 的火车"这句话，谁负责什么

| 步骤                                | 谁来做            | Assemble 要提供什么                                                    |
| ----------------------------------- | ----------------- | ---------------------------------------------------------------------- |
| 听懂这句话：哪一天、9:00 是发车时间 | Codex 或 ZCode    | 知道今天几号、你的时区；工具的说明里写清楚                             |
| 推算提前量：几点出门、几点到站      | Codex 或 ZCode    | 可以存下你的偏好（"火车提前 90 分钟出门"），换哪个助手都一致——放第二批 |
| 想到要带什么（身份证）              | Codex 或 ZCode    | 日程带备注或清单；提醒弹出来的时候带着它们                             |
| 写进系统                            | Codex 或 ZCode    | MCP 工具：建、改、取消、完成、查最近的安排                             |
| 到点提醒                            | Assemble 的服务端 | 调度与推送（第一批本来就有的）                                         |
| 手机上响                            | 还没定            | 见下面                                                                 |

Assemble 不做任何"理解"和"排程"：不含模型，不猜你的意思。这与 jarvis 的设计一致——它的设计稿把"Codex 理解与规划、Jarvis 保存与执行"定为唯一方向，明确否决了自己加模型或自动排程。Assemble 沿用这条分界。

## 打算怎么做对话入口

一个小的可执行文件 `assemble-mcp`，随桌面应用一起安装。Codex 和 ZCode 的配置里指向它，它们就能调下面这些工具。

- **工具**：列出最近的安排；新建日程（标题、开始、结束、提前几分钟、地点、备注）；新建提醒；修改、取消、完成；查最近的安排（也用来回答"我这周有什么安排"）。
- **校验在 Assemble 这边**：时间合不合法、长度超没超，和桌面端走同一套规则。工具的结果里带回冲突（和已有日程撞车），助手可以据此提醒你，但不拦着。
- **不在 Assemble 里做确认流程**：你在对话里已经说过要建，助手在聊天里向你确认。jarvis 里"语音动作待确认"那一套不搬。
- **每一条都记着是哪台设备写的**：界面能看出"这一条是 ZCode 加的"。

**助手怎么拿到权限**：建议让它自己登录一次，成为账户里的一台"设备"。

1. 你运行一次 `assemble-mcp login`，系统浏览器打开和桌面端一样的授权页，名字随你起（比如"ZCode 的助手"）。
2. 令牌存进系统钥匙串。它出现在桌面应用的设备列表里，想收回就在那里移除。
3. 之后 Codex、ZCode 调工具，走的是和桌面端同一个接口、同一套权限；桌面应用开没开着都行。

jarvis 走的是另一条路：MCP 先连到桌面应用开在本机的一个入口，由桌面应用代为转发。我没有选它——那要在桌面应用里再开一个只在本机可达的端口，而且桌面应用不运行时助手就用不了。这一条是我的建议，你没有确认过。

## 还没有定的

1. **手机上怎么提醒。** 你要的是日程设好之后，iPhone 上会有闹钟或提醒。Assemble 现在没有 iPhone 应用：决策 0002 把 iOS 排在"以后再说"。这件事会改变项目的范围，所以要你定：
   - 做 Assemble 的 iPhone 应用。最完整，但它是一个全新的端，工作量相当于再做半个项目。另外 iOS 不允许第三方应用去设系统闹钟，jarvis 的 iPhone 应用做的也是定时通知。
   - 先借一个现成的推送类应用：服务端到点往你手机上推一条通知。不用开发 iOS 应用，很快能通；代价是依赖一个第三方应用，样式固定，手机上也没有完整的日程列表。具体选哪一个、能力边界如何，我还没有核实。
   - 两个都要：先用推送应用顶上，iPhone 应用单独排一个阶段。

   我的建议是第三个。
2. **jarvis 里的目标与计划在正式服务上发布了没有、你用不用。** 这决定第二批从简还是往后放。
3. **MCP 这条路的权限范围。** 上面的建议只覆盖日程与提醒；以后任务、目标、计划草案的工具等做到那一步再加。

## 后果

- 第一批的工作量比原方案大：除了服务端与桌面端，还多一个可执行文件。
- 协议里要为"助手也是一台设备"留位置：它不连事件流，在设备列表里始终显示离线，也不能给它发文件。
- iOS 的决定会决定第一批"手机上会响"这一条能不能算完成。
