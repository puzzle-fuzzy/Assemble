按建议采用的八条：任务、目标与"今天"放第二批；每条日程可以设"提前几分钟"；每台在线设备都弹，另给每台电脑一个"不弹"的开关；设备重新上线后补弹过去 24 小时内没弹过的，离开提醒时刻超过十分钟或已结束的场次不提醒、提醒不管多晚都补；重复日程整条完成；时区沿用 jarvis 的规则；不迁移 jarvis 里的日程与提醒；工作陪伴不算日程规划。

## 你怎么用

你的原话（2026-11-24）：

> 我一般都是会和 Codex 和 ZCode 进行对话，然后由这俩个 AI 来分析我的内容和处理日程，比如我会告诉你我明天 9:00 的火车，Codex/ZCode 你需要分析我的这个内容，然后定好提前的时间，告诉我需要携带的内容（比如身份证），然后设定好时间。设定好时间后会同步到我的 IOS 手机上面同步的设置好闹钟或者是提起提醒方式。请你仔细分析一下，并不是我手动的在管理段或者页面端进行设置，而是我通过文本和你对话，你来处理我所有的内容。这就是之前 MCP 存在的一部分意义。

这纠正了方案里的一个倾向。我当时建议第一批先不做对话入口、把桌面里手建做好，理由是 jarvis 的日常网页不能新建日程是个短板。你说的是：**对话就是你管理日程的方式**，手建只是备用。所以对话入口不是"以后再说"，而是第一批必须有；桌面里的新建与编辑降为备用入口。

## "明天 9:00 的火车"这句话，谁负责什么

| 步骤                                | 谁来做                                | Assemble 要提供什么                                                    |
| ----------------------------------- | ------------------------------------- | ---------------------------------------------------------------------- |
| 听懂这句话：哪一天、9:00 是发车时间 | Codex 或 ZCode                        | 知道今天几号、你的时区；工具的说明里写清楚                             |
| 推算提前量：几点出门、几点到站      | Codex 或 ZCode                        | 可以存下你的偏好（"火车提前 90 分钟出门"），换哪个助手都一致——放第二批 |
| 想到要带什么（身份证）              | Codex 或 ZCode                        | 日程带备注或清单；提醒弹出来的时候带着它们                             |
| 写进系统                            | Codex 或 ZCode                        | MCP 工具：建、改、取消、完成、查最近的安排                             |
| 到点提醒                            | Assemble 的服务端                     | 调度与推送（第一批本来就有的）                                         |
| 手机上响                            | Assemble 自己的 iPhone 应用，还没有做 | 2026-11-25 定了做原生的 Swift 应用；怎么做，到那一步再出方案           |

Assemble 不做任何"理解"和"排程"：不含模型，不猜你的意思。这与 jarvis 的设计一致——它的设计稿把"Codex 理解与规划、Jarvis 保存与执行"定为唯一方向，明确否决了自己加模型或自动排程。Assemble 沿用这条分界。

## 对话入口怎么做

一个小的可执行文件 `assemble-mcp`。方案里写的是随桌面应用一起安装；做的时候（2026-11-25）没有这样做：安装包里只有桌面端，它用 `bun run mcp` 单独构建。Codex 和 ZCode 的配置里指向它，它们就能调下面这些工具。

- **工具**：列出最近的安排；新建日程（标题、开始、结束、提前几分钟、地点、备注）；新建提醒；修改、取消、完成；查最近的安排（也用来回答"我这周有什么安排"）。做的时候另外加上了删除，和把到点的提醒标成已读，一共十个。
- **校验在 Assemble 这边**：时间合不合法、长度超没超，和桌面端走同一套规则。工具的结果里带回冲突（和已有日程撞车），助手可以据此提醒你，但不拦着。
- **不在 Assemble 里做确认流程**：你在对话里已经说过要建，助手在聊天里向你确认。jarvis 里"语音动作待确认"那一套不搬。
- **每一条都记着是哪台设备写的**：界面能看出"这一条是 ZCode 加的"。

**助手怎么拿到权限：已定**（2026-11-25）。让它自己登录一次，成为账户里的一台"设备"。

1. 你运行一次 `assemble-mcp login`，系统浏览器打开和桌面端一样的授权页，名字随你起（比如"ZCode 的助手"）。
2. 令牌存进系统钥匙串。它出现在桌面应用的设备列表里，想收回就在那里移除。
3. 之后 Codex、ZCode 调工具，走的是和桌面端同一个接口、同一套权限；桌面应用开没开着都行。

jarvis 走的是另一条路：MCP 先连到桌面应用开在本机的一个入口，由桌面应用代为转发。没有选它——那要在桌面应用里再开一个只在本机可达的端口，而且桌面应用不运行时助手就用不了。这一条原先是我的建议，你批准第一步的方案时定了（见下面）。

工具的说明、几条规矩和怎么接进客户端，写在[架构说明](../architecture.md)的"助手入口"里。

## 2026-11-25 的三条决定

你对照 jarvis 列了后面想做的九项（文件传云、远程控制、iOS 用 NFC 唤起、M3U8 与抖音地址下载、服务器存储监控与静态预览与版本管理、邮箱简报、日程配合 iOS、电影/封面/磁力链、手机二维码登录）。我给了看法，并请你在开工前定三件事。你的原话（2026-11-25）：

> 批准。手机走原声 swit，远程控制就是 俩台电脑互相控制，文件传输以及画面，远程控制可以放到最后

| 事项       | 决定                                                                                                                                   |
| ---------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 手机       | 走原生 Swift，也就是做 Assemble 自己的 iPhone 应用。它回答了下面第 1 件"手机上怎么提醒"：不借第三方的推送类应用，iPhone 成为一等客户端 |
| 远程控制   | 是两台电脑互相控制——文件传输和画面；不是"助手远程给电脑下任务"（jarvis 是那样做的）。在九项里排在最后                                  |
| 助手的权限 | 批准第一步的方案，而方案里写明"批准这份方案就等于定了助手自己登录成一台设备"。第一版只做日程与提醒，不碰文件                           |

"原声 swit"按"原生 Swift"理解。它比"先借一个推送类应用顶上"（我原先的建议）多出整整一个端，是你明确要的。

**顺序是我的建议，你没有逐条确认。** 我按这个次序排进路线图：先在正式服务上把已有的用起来，再是助手入口，然后是 iPhone 应用，之后是下载、片库、服务器状态与版本管理、静态预览、邮箱简报，远程控制最后。九项里的"iOS 用 NFC 唤起""日程配合 iOS""手机二维码登录"都并入 iPhone 应用那一步，具体怎么做到了那一步再核实。要调整，直接说。

## 2026-11-26 又定的两件：手机

规划下一步时你选了"先把已上线的验收修好"，不急着做手机；顺带把手机那一步的两件事定了：

| 事项             | 决定                                                                                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Apple 开发者账户 | **先不买，以后会买。** 手机那一步做到不买也能做的那一步为止（服务端与协议的改动、模拟器里的应用）                                                             |
| 手机上的提醒     | **先做本地通知，远程推送放第二期。** 应用打开时同步，把之后的提醒排进系统，关着应用也会响；助手新建日程之后，手机要打开过一次应用才会响。推送等你买了账户再加 |

具体方案到手机那一步再出。届时只剩一个小问题要问：你的 Apple ID 现在用的是免费账户还是付费账户。

## 还没有定的

1. **jarvis 里的目标与计划在正式服务上发布了没有、你用不用。** 这决定第二批从简还是往后放。
2. **MCP 这条路的权限范围以后怎么扩。** 现在只有日程与提醒；任务、目标、计划草案，以及下载、片库、简报这些要靠助手的工具，做到哪一步加到哪一步，每次都是新的具名工具。
3. **静态预览放在哪个域名下。** 不能挂在 `as.yxswy.com` 下面（同源会带着登录状态），要单独的子域名，需要你加解析。到那一步再定。

## 后果

- 第一批的工作量比原方案大：除了服务端与桌面端，还多一个可执行文件。
- 协议里要为"助手也是一台设备"留位置：它不连事件流，在设备列表里始终显示离线，也不能给它发文件。
- `assemble-mcp` 没有打进安装包，要单独构建；这个入口写进协作约定：助手也只有具名工具，令牌只进系统钥匙串。
- iPhone 应用成了项目的一部分。它是一个全新的端，排在"把已上线的验收修好"之后；"手机上会响"这一条要等它做出来才算完成。第一版只有本地通知：手机要打开过应用才会知道新的日程。
