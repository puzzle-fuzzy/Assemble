# 0001：桌面端以 Rust 为核心、Tauri 2 只做壳

- 状态：部分被 [0002](0002-own-server-replaces-jarvis.md) 取代（2026-11-24）。第 3 条与"待确认"的 A、J 两项不再有效，其余仍然成立。标注"待确认"的其它条目是我采用的默认，需要你确认或否决。
- 日期：2026-11-23
- 范围：Assemble 仓库

## 背景

Jarvis 的桌面端以 Electron 为主：主进程与设备运行时都是 TypeScript，窗口里加载的是远程网页。目标是把桌面端换成 Rust + Tauri 2，并优先做好文件传输与日程规划；宠物、壁纸不是重点。

动手之前只读调研了 `jarvis`（`main`，`0d6eb5f`），结论当时写在架构说明里。转向之后[架构说明](../architecture.md)已经按新的结构重写，那一节不再保留；它对 jarvis 的结论本身没有变，只是对 Assemble 已经不适用。

## 决定

1. **Rust 负责全部业务规则，Tauri 2 只提供窗口、托盘与系统集成。** 规则放在不依赖界面、可以单独测试的基础库里；应用壳只做编排。
2. **界面是打包在应用里的本地页面。** 界面通过少量具名命令调用 Rust、接收状态事件，不持有凭据，也不直接联网。
3. ~~**服务端不变。** Assemble 是桌面端，继续使用现有的 Jarvis API。~~ 已被 [0002](0002-own-server-replaces-jarvis.md) 取代：Assemble 自带 Rust 服务端，用来完全替换 jarvis。
4. **认证沿用原方案。** 系统浏览器授权、回环回调、PKCE，换取独立的设备会话；令牌不进界面。
5. **连接目标由构建类型决定。** 调试构建连本地开发服务，发布构建连正式服务。

## 依据

**事实**（读源码或运行得到的）

- 原实现的所有请求都经 API 中转，没有设备直连，也没有 WebSocket；实时性靠 HTTP 长轮询。所以桌面端不需要常驻连接，重写不涉及传输协议。
- Tauri 窗口加载不了原来的远程网页：原网页依赖同源 Cookie，而服务端有四道彼此独立的限制（见架构说明）。这条直接排除了"继续套远程网页"的做法。
- MCP 服务器不访问云端，只通过回环端口调用桌面端。本机网关的协议必须原样保留。
- 日程由服务端触发，桌面端只投递通知。所以桌面端不需要自己实现一套调度器。
- 原实现在扫描、大文件处理、库存上报和通知去重上有明确的改进空间。

**推断**

- 把规则放进不依赖界面的基础库，测试会更快、更稳：现有 Rust 测试全量跑完约 2 秒，不需要窗口或网络。
- 用样本做双向契约校验，比生成代码更轻：没有额外的构建步骤，两边各自对着同一份样本失败。

**假设**（为了往下走而采用的默认）

- 见下面"待确认"。

## 放弃的备选

| 备选                                                    | 不选的原因                                                                                             |
| ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 继续用 Electron，只做重构                               | 目标本身是换掉 Electron                                                                                |
| Tauri 窗口里继续加载远程网页                            | 事实表明走不通；要改服务端的 Cookie、CORS 与 Origin 策略才能绕开，等于削弱安全边界                     |
| 服务端一并用 Rust 重写                                  | 不在本次范围内；API 已有大量经过测试的行为，重写的风险与收益不匹配                                     |
| 由 Rust 直接访问数据库、绕过 API                        | 违背原架构"API 是数据库唯一入口"的约定，也会丢掉服务端的校验与审计                                     |
| 用生成代码（如从 Rust 类型生成 TypeScript）保证契约一致 | 需要额外的生成步骤与工具链；样本校验已经能在两侧拦住漂移，成本更低                                     |
| 用时区库重新实现日程推算                                | 云端的算法是纯整数运算加固定的北京时间偏移。换一种算法就有两边结果不一致的风险，所以选择逐步移植并对照 |
| 引入 Turborepo 编排                                     | 目前只有一个 TypeScript 应用，没有可编排的东西；出现第二个再说                                         |

## 后果

**好的方面**

- 应用体积小：未打包的发布二进制约 6 MB。
- 文件相关的核心规则（路径边界、暂存发布、授权与回执账本）可以脱离窗口测试，并且已经测过。
- 日程推算与云端原实现对照过两万条用例，结果一致。

**代价与限制**

- 文件传输与日程的后台循环、界面都要重写，现在还没有。
- 尚未原生实现的功能不在窗口里出现，过渡期仍要用原来的 Electron 应用或浏览器。
- 登录流程只对模拟服务测过，没有对真实服务跑通。
- 只在 macOS（Apple Silicon）上构建和运行过。

## 从实际运行中学到的两条

这两条都是单元测试通过、实际启动后才暴露的，记在这里避免再犯。

1. **对外公布的能力必须由实现方决定。** 网关库最初自己用契约里的静态目录应答 `/capabilities`，结果公布了一百多个操作，而当时只有三个可用。现在这条路由交给后端回答。
2. **退出时的清理不能依赖析构。** 起初假设应用退出时托管的网关句柄会被释放、顺带删掉发现文件；实际正常退出后文件还在。现在在退出事件里显式停止网关。
