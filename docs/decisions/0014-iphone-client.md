# 0014：iPhone 第一期——手机当一台设备，扫码登录

- 日期：2026-11-26
- 状态：服务端这一半和手机应用第一期都已实现，服务端这一半 2026-11-27 01:32 随 `c79edf0` 上了正式服务。服务端在真实浏览器里走过一遍；手机应用在模拟器里对着一次性的本机服务端把整条路走通（2026-11-27），真机上还没有人用过。"系统提供的网页登录会话"那一条登录的路等你答复，没有做。
- 起因：你 2026-11-25 定了手机走原生 Swift，2026-11-26 定了 Apple 开发者账户先不买、手机先做本地通知；同一天晚上让 Mac 会话直接开始 iOS 手机端，用模拟器开发和验证，真机上的验收留给你。范围、架构与分工在[下一批要做的东西](../plans/2026-11-26-next-features.md)的 B1 到 B3。

## 决定

- **手机是账户里的一台设备。** 协议里的平台多了 `iphone`，另加一个兜底的 `other`：这一版代码不认识的值归到它那里，设备名单照常读得出来。以前遇到不认识的值，服务端回 500，那个账户的设备名单、自检和管理端会一起失败，事件流也被掐断；旧版应用则是读不了设备名单。
- **加一个新平台的顺序不能乱。** 服务端先升级，两台电脑再更新应用，然后才有新平台的设备登录。
- **第一期的手机不能收文件。** 手机应用只有日程与提醒，发给它的文件没人收。服务端拒绝这种发送，回"目标设备上的应用收不了文件"；桌面端的发送面板不把它列成目标，并说一声为什么。规则只有一条：`Platform::can_receive_files`。
- **登录的第一条路是扫码配对，密码不进手机应用。** 已登录的网页生成一张二维码，里面是一次性的票据；手机扫到之后认领它，交上自己的 PKCE 挑战，得到一个六位的确认码并显示出来；网页那边显示同一个码，本人核对是同一串之后点"允许"；手机再拿着校验器来取令牌。
- **令牌只在"允许"之后发出，而且必须拿对校验器。** 网页从头到尾不接触令牌。票据只能被认领一次；拿错的校验器试过一次，这张票据就作废；三分钟内没走完也算作废。
- **票据在库里只存摘要。** 页面每两秒刷新一次，刷新时要把二维码重画出来，所以还没被认领的票据另在服务进程的内存里留三分钟。服务端在那之内重启过，这一张就作废，页面上会说重新生成。
- **配对页不用脚本，也不放宽页面的策略。** 二维码是服务端画的一段内联 SVG，等手机来扫的那一段靠 `<meta http-equiv="refresh">` 刷新。页面共用的内容安全策略原样不变。
- **两个谁都能调的接口按来源限速。** 认领一分钟十次，问结果一分钟九十次；来源未知时（没有配置可信的代理头）不限，理由和登录失败的第二层一样。
- **到点靠本机提前排好的系统通知，远程推送留到第二期。** 每次拿到名单，按和服务端同一条规矩算出今后三十天里该响的，取最近的六十条交给系统；标识就是服务端通知的标识（提醒 `n-<提醒标识>`，日程 `<日程标识>-<场次的毫秒>`），所以本机响过之后，服务端到点才生成的同一条通知不会再响第二遍。手机既没排过也没弹过的，恢复之后补弹一次。通知的权限在用户打开"到点提醒"时才申请。
- **办完一条，它的通知跟着算看过。** 提醒"看过了""不办了"、日程"完成""取消"之后，它到点的通知一并标成已读，服务端晚一步才生成的那一条也算：名单的"没读的通知"里不该留下一条已经办完的。
- **手机第一期不开事件流。** 开了的话，手机每次进出前台都会向这个账户的每台设备广播一次"设备变了"；而第一期只需要拉名单。所以手机在设备名单里总是离线。

## 还没有定的

- **手机旁边没有电脑时怎么登录。** 通行做法是系统提供的网页登录会话（`ASWebAuthenticationSession`）：由系统开一个隔离的网页，密码只输给这个网页，应用只收回一个回调地址。这要把"登录只发生在系统浏览器里"那条边界改写成"登录只发生在系统提供的网页里"，所以等你点头再做。服务端为它要改的地方（多认一个固定的回调地址）也还没有动。

## 我采用的，你没有逐条确认

- 手机应用第一期用纯 Swift 写，类型和规则手写一份，用 Rust 侧导出的样本钉住；等手机要收文件、看云盘时再考虑 Rust 内核。
- 手机的最低系统版本是 iOS 17。
- 手机的令牌和桌面端一样不过期；手机丢了，在桌面端的"设备"里移除它。

## 验证边界

- 自动化测试：协议的类型；服务端对着真实运行的服务的十二条集成测试（整条配对、票据只能认领一次、拿错校验器就作废、拒绝与取消、别的账户看不也决定不了、来源与防伪值、过期清理、同时配对的上限、账户页的入口）；桌面端的守卫、发送面板和契约样本；管理端的字典。
- 真实浏览器（ZCode 的内置浏览器，对着本机一次性起的服务端）：登录、账户页的"添加手机"、生成二维码、二维码在深色模式下白底黑格、自动刷新之后二维码还在、认领后换成核对数字的页面、点"允许"、最后一页"添加好了"。响应头里的内容安全策略和别的页面一样，没有放宽。
- 手机应用的自动化测试：核心包 31 条（样本解码、重复规则每一问和 Rust 的答案一致、通知的规划与对账、接口与错误）；应用层 13 条单元测试，对着替身把配对、恢复登录、退出、通知的排布、点开通知、"看过了"走一遍。
- 模拟器里整条路（`bun run iphone:simulate`，2026-11-27 连跑四遍都过，最后一遍对着推送出去的提交）：粘贴配对地址、显示六位数字、网页点允许、名单、打开到点提醒（系统的"允许通知"框由测试替人点）、切到后台、系统通知弹出、点它回到前台并定位到那一条、看过了、它迟到的通知不再出现、回服务端核对状态。其中一遍是不卸应用重跑的，走的是"通知权限还在、不再问"的那条路。这一遍抓到过单元测试全绿时照样存在的问题，逐条记在运行手册 2026-11-27 的记录里。
- 还没有做过的：真机上的一切（摄像头扫、锁屏上通知的样子、被划掉之后点开通知冷启动、离线）；两台电脑上的应用更新（正式服务 2026-11-27 01:32 已经随 `c79edf0` 升级，手机登录之前两台电脑都要先更新）；NFC 标签。这些都记在[下一批要做的东西](../plans/2026-11-26-next-features.md)的进度表里。
